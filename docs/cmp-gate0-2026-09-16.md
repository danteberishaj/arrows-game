`BUILD FAILED in 9m 54s`.

What this means:
- INFERRED: 16.5.0 pins `play-services-ads` 25.4.0 and `user-messaging-platform` 4.0.0 in its `package.json` `sdkVersions.android`. Its `android/build.gradle` reads those values and offers no `rootProject.ext` override for the ads version. `play-services-ads` 25.4.0 ships Kotlin 2.3 metadata. The project's Kotlin compiler is RN 0.86.3's (`node_modules/react-native/gradle/libs.versions.toml:32` `kotlin = "2.1.20"`), and it rejects that metadata. The failure comes from the toolchain, not from the new architecture's codegen, which never got to run for this module.
- Not measured, because no APK exists: APK size, the permission diff and LevelPlay init.
- The dependency resolution did run (`./gradlew :app:dependencies --configuration releaseRuntimeClasspath`, exit 0). Its conflicts with LevelPlay are below.

Workarounds that were **not tried**, so they are UNTESTED. They are listed for W7-03 only.
- (a) Raise the project Kotlin version through `expo-build-properties` `android.kotlinVersion`. The v57 docs describe that option as "Override the Kotlin version used when building the app." It changes the compiler for every native module, including Reanimated, Skia and expo-modules-core, so it is a toolchain change and not a CMP change.
- (b) Pin an older `react-native-google-mobile-ads` whose `play-services-ads` has pre-2.3 metadata. Compatibility with RN 0.86.3 is unknown.
- (c) A thin local module that depends only on `com.google.android.ump:user-messaging-platform`, without `play-services-ads`.

Why they were not tried: the brief bounds the spike to two candidates. After the Usercentrics build, `df -h /` showed 5.2Gi, which is under the 7 GB gate for another W7-02 build.

## What this does NOT prove

- **Consent reaching LevelPlay.** Nothing here passes the Usercentrics TCF string or decisions into `LevelPlay.setConsent` / `LevelPlayPrivacySettings`. That is W7-01/W7-03 work.
- **The consent form.** The sample settings ID returned `shouldCollectConsent: true` and 5 services. No banner was shown (`showFirstLayer` was not called), and the owner's own configuration does not exist yet.
- **Physical devices.** UNVERIFIED-DEVICE: a physical device with Play Services, iOS (BLOCKED-ON-DISK), and a production Usercentrics settings ID.
- **Network use.** `status()` contacted Usercentrics with the vendor's sample ID over the emulator's network. Its geolocation result was not validated against a known location.
- **Pricing and account terms.** Usercentrics requires an account and plan (its README says "you will need a Usercentrics Account"). Pricing was not checked.

## Recommendation for W7-03's owner decision

1. **Usercentrics is the only candidate proven on this exact stack.** It is Google-certified (CMP id 5), passes the release build with R8 and the new architecture, round-trips over the bridge, and coexists with LevelPlay init in the same process. It adds no permissions, bumps no Play Services version, and costs about 0.8 MB of APK (upper bound). Recommended as the W7-03 default **if** the owner accepts a paid vendor account.
2. **Google UMP through `react-native-google-mobile-ads` 16.5.0 does not compile here** (Kotlin 2.3 metadata vs RN 0.86.3's Kotlin 2.1.20). It is free and is the CMP LevelPlay reads natively. If the owner prefers it, a second bounded spike is needed before W7-03 plans on it. That spike would test workaround (c), a UMP-only local module, which avoids `play-services-ads` entirely, or (a), a project Kotlin bump. It must also re-check LevelPlay on `play-services-basement` 18.9.0.
3. **Didomi was not tried.** It is certified (id 7). Its `@expo/config-plugins ^54` dependency against the project's 57 is an open risk.
4. **Option (d), keeping the ad SDK off in the EEA/UK.** It is not needed on the evidence, since one certified CMP passes, but it stays available. Geography must come from an SDK or CMP (the Usercentrics `status().location` shown above is such a source), never from the device locale.
