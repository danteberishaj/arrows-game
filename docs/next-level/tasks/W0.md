## W0-01 — Strip the simulated TEST AD out of production builds

- **Status:** READY

- **Files:** `src/ui/ads.tsx`, `App.tsx`

### Context

## W0-02 — Make rewarded ads honest when no ad can be served, and make ad init recoverable

- **Status:** READY
- **Effort:** M
- **Depends on:** W0-01. It must land in the same release as W0-01.
- **Flag:** none (defect fix). The new copy needs owner acceptance from screenshots before merge.
- **Files:** `src/ui/ads.tsx`, `App.tsx`, `src/ui/GameScreen.tsx`, `src/ui/HeaderButton.tsx`,
  `src/ui/adInit.ts` (new), `src/ui/adReadiness.ts` (new), `src/ui/__tests__/adInit.test.ts`
  (new), `src/ui/__tests__/adReadiness.test.ts` (new)

### Context
This task has three defects, and they have to ship in one commit. Each one can only be verified
through the others.

- **(a) Silent no-op.** `GameScreen.tsx:172` (`if (!earned) return; // stay on the lose panel`)
  and `:188` (`if (!earned) return;`) do nothing and show nothing when `Ads.showRewarded()`
  (`ads.tsx:296-312`) resolves `false`. It resolves `false` both on no-fill (`:299`) and on a show
  failure (`:302-305`). The hint button (`GameScreen.tsx:226-231`) and "Continue +♥ (ad)"
  (`:273-290`) look available whether or not an ad exists.
- **(b) One failed request disables the SDK for the session.** `lpInterstitial`, `lpRewarded` and
  `levelPlayApi` are assigned only at `ads.tsx:228-230`, after `await inter.loadAd()` (`:202`)
  and `await rew.loadAd()` (`:226`). A rejected first `loadAd()` jumps to the catch (`:231-236`)
  and nulls all three, even though `LevelPlay.init` succeeded and the listeners' 15 s reload
  retries (`:189`, `:207`) are already wired.
- **(c) Init is never retried.** `App.tsx:35` calls `initAds()` exactly once, un-awaited, with no
  `.catch`. `grep -rn AppState src/` returns 0 hits, so a device that boots before its network is
  up earns nothing for the whole session.

Whether LevelPlay's `loadAd()` ever rejects, or only reports through `onAdLoadFailed`, is not
documented in `node_modules/unity-levelplay-mediation/lib/typescript/src/models/LevelPlayInterstitialAd.d.ts`.
Whether `LevelPlay.init` can be called again after `onInitFailed` is also undocumented. Both are
premises this task must check, not assume.

### Change
1. **Readiness store** (`src/ui/adReadiness.ts`, pure TS with no react-native import):
   `createReadiness()` returns `{ get(): boolean; set(v: boolean): void; subscribe(cb): () => void }`.
   It notifies only when the value changes.
2. **Wire rewarded readiness** in `ads.tsx` from the listener callbacks that already exist:
   - `onAdLoaded` sets `true`.
   - `onAdLoadFailed`, `onAdDisplayed` (the loaded ad is consumed), `onAdDisplayFailed` and
     `onAdClosed` set `false`.
   - The existing reload calls flip it back to `true` through `onAdLoaded`.
   - In `__DEV__` with no native SDK, readiness is `true` exactly while the simulated host is
     mounted (`fakeAdListener !== null`). This keeps the web preview testable.
   - In a release build with no native SDK, readiness is `false`.
   - Expose it as `Ads.rewardedReady` and `Ads.subscribeRewardedReady(cb)`. No polling and no new
     interval.
3. **Handle-assignment fix.** Assign `lpInterstitial`, `lpRewarded` and `levelPlayApi` right after
   the init promise resolves (after `ads.tsx:184`) and before any `loadAd()`. Call both first loads
   without `await`, with `.catch(scheduleReload)`. `scheduleReload` reuses the existing 15 s delay
   and keeps one pending-reload guard per ad, so a rejection and an `onAdLoadFailed` for the same
   request cannot schedule two reloads.
4. **Retryable init** (`src/ui/adInit.ts`, pure TS):
   - `createAdInitController({ attempt, delaysMs, setTimer, clearTimer })` holds a state of
     `'idle' | 'running' | 'ready' | 'failed'`.
   - `start()` is idempotent: it is a no-op while `running` or `ready`.
   - After a failure it schedules the next timed attempt from `delaysMs` and stops once the list is
     exhausted.
   - `onAppActive()` starts an attempt when the state is `failed`, whether or not timed attempts
     remain. Players make this trigger happen by switching back to the app; it needs no number.
   - `ads.tsx` owns one controller. `initAds()` calls `start()`. `App.tsx` subscribes
     `AppState.addEventListener('change', s => s === 'active' && controller.onAppActive())` and adds
     `.catch(() => {})` to the `initAds()` call.
   - `delaysMs` starts at `AD_INIT_RETRY_DELAYS_MS = [5000, 15000, 45000]`. This is an
     OWNER-PICKED STARTING VALUE with nothing measured behind it. Setting `[]` disables timed
     retries in a hotfix.
5. **UI.**
   - `HeaderButton` gains `disabled?: boolean`. It passes `disabled` to `Pressable`, sets
     `accessibilityState={{ disabled }}`, and renders the glyph in the same inactive colour
     `active=false` uses today. W0-06 retunes that colour; do not retune it here.
   - The hint button is `disabled` when `!rewardedReady || terminalPending || adBusy`.
   - "Continue +♥ (ad)" is `disabled` when `!rewardedReady || adBusy`.
   - When `!rewardedReady` on the lose panel, the `panelSub` text (`GameScreen.tsx:268-272`) reads
     `No ad available right now — Retry is free`.
   - When a show was attempted and resolved `false` (readiness changed between render and tap), the
     same line appears on the lose panel. During play, `Hint unavailable` appears in the existing
     header row beside `{remaining} left` (`GameScreen.tsx:218-220`), using `styles.diffLabel`.
     It stays until the next readiness change or the player's next board tap. There is no timer,
     it never overlays the board, and there is no new component.
6. A failed show grants nothing. No hint and no heart are given without `earned === true`.

### Non-goals

## W0-03 — Boot backstop: the app must always reach the menu

- **Status:** READY
- **Effort:** S
- **Depends on:** none
- **Flag:** none (defect fix)
- **Files:** `src/ui/SplashScreen.tsx`, `App.tsx`, `src/ui/splashBackstop.ts` (new),
  `src/ui/__tests__/splashBackstop.test.ts` (new)

### Context
- **(a) Splash.** Both `onDone` call sites are Reanimated completion callbacks: the scripted
  fade-out at `src/ui/SplashScreen.tsx:47-49` (`withDelay(2250, withTiming(..., 380))`, which ends
  at 2630 ms by the file's own timeline) and tap-to-skip at `:52-56`. There is no JS timer and no
  AppState fallback (`grep -rn AppState src/` = 0 hits). If the animation never completes, the
  player stays on the splash. Also, `onDone` can run twice if a skip tap and the scripted
  completion both finish.
- **(b) Fonts.** `App.tsx:23` destructures only `[fontsReady]` from `useFonts`, but expo-font
  returns `[loaded, error]` (`node_modules/expo-font/build/FontHooks.d.ts`). A font-load error
  leaves `fontsReady` false forever, and `App.tsx:54` renders a bare background `View`.
- **(c) Save init.** `App.tsx:30-34` has no `.catch` on `initSaveSystem()`. Reading
  `src/ui/storage.ts:18-30,73-77` shows `hydrate()` already swallows `multiGet` failures, and
  `storage.test.ts:70-78` asserts `initSaveSystem()` resolves when hydration fails. So a rejection
  is not reachable through the known path today, and this part is hardening, not a reproduced
  defect.

### Change
1. Add `src/ui/splashBackstop.ts`, pure TS with an injected clock and timers:
   `createSplashBackstop({ maxMs, now, setTimer, clearTimer, onDone })` returns
   `{ finish(), onAppStateChange(state), dispose() }`.
   - `finish()` calls `onDone` at most once for the lifetime of the object.
   - Construction starts a `maxMs` timer that calls `finish()`.
   - `onAppStateChange('active')` calls `finish()` if `now() - mountedAt >= maxMs`. A JS timer
     does not fire while Android has the app paused, so the timer alone is not a backstop.
2. `SplashScreen` creates one backstop per mount and subscribes to `AppState` in the same effect.
   It routes both `runOnJS(onDone)` sites through `backstop.finish` and disposes on unmount.
   `SPLASH_MAX_MS = 4000` is an OWNER-PICKED STARTING VALUE. The floor of 2630 ms comes from the
   file; the 1370 ms of headroom is picked. If the backstop fires early, the player simply skips
   the splash tail, which is harmless.
3. `const [fontsReady, fontError] = useFonts(...)`. Treat `fontsReady || fontError != null` as
   ready, so Fredoka falls back to the platform font instead of a blank screen.
4. `initSaveSystem().then(...).catch(() => setReady(true))`. SaveSystem keeps its in-memory store,
   which never writes to AsyncStorage, so existing saved progress cannot be overwritten. Do NOT add
   a timeout that sets `ready` before hydration finishes. A later `SaveSystem.useStore` swap could
   then write progress from a level-1 in-memory session over the player's real progress.

### Non-goals
- A timeout on font loading that never resolves or rejects. No path to that hang is known, and it
  would add another picked number.
- Any change to the splash's visible animation in the healthy path.
- Reduce-motion treatment of the splash (the W2 census).

### Acceptance criteria
1. `npx jest src/ui/__tests__/splashBackstop.test.ts` passes, covering:
   - the timer fires `onDone` once;
   - `finish()` from a skip plus a completion in the same tick calls `onDone` once;
   - `'active'` after `maxMs` finishes, and `'active'` before `maxMs` does not;
   - `dispose()` clears the timer, and nothing fires after dispose.
2. Measured before committing the constant: five (**OWNER-PICKED STARTING VALUE**) healthy cold
   starts of the release build on the emulator, with a temporary log of mount to `onDone` in ms.
   Before the first start, read back `adb shell settings get global transition_animation_scale`
   and require `1` (then force-stop and relaunch): at `0` Reanimated treats the device as reduced
   motion and `withDelay` skips its delay, so the splash ends almost at once and every value would
   trivially sit below the constant (the perf harness leaves all three scales at `0`,
   `benchmark.mjs:350-357`). The verification record lists the read-back and all five values next to
   `SPLASH_MAX_MS`, and every value is below it.
3. Injection 1, a temporary edit removing both `runOnJS(onDone)` lines: a fresh launch reaches the
   menu. Screen recording, with the time from splash mount to menu printed from the log. "Reaches
   the menu" means the menu is **visibly rendered**, not only mounted: a screencap taken after the
   log line shows the Play pill and the "Level N" label. The menu sits inside an entering
   `FadeIn.duration(180)` wrapper that starts at opacity 0 (`App.tsx:63`), so a mounted-but-invisible
   menu would otherwise pass.
4. Injection 1 plus HOME pressed about 1 s into the splash, with a wait longer than
   `SPLASH_MAX_MS` before returning: the menu is visibly rendered (screencap as in criterion 3) when
   the app returns. Screen recording. Add a temporary log inside `finish()` naming its caller
   (`timer` or `appstate`). A JS timer can also catch up on resume, so if the log shows `timer`

5. Injection 2, a temporary edit making `useFonts` return `[false, new Error('injected')]`: the

6. Injection 3, a temporary edit making `initSaveSystem` reject: the menu renders, Play starts a

## W0-04 — Reduce-motion players must still see which arrow blocked them

- **Files:** `src/ui/feedbackCurves.ts`, `src/ui/StaticBoardSurface.native.tsx`,
  `src/ui/BoardView.tsx`, `src/ui/__tests__/feedbackCurves.test.ts`

### Context
There are six feedback `withTiming` drivers, all using Reanimated's default
`ReduceMotion.System`:

| Renderer | Blocker flash | Blocked bump | Hint pulse |
|---|---|---|---|
| Native Skia (`StaticBoardSurface.native.tsx`) | `:264` | `:308` | `:348` |
| Web SVG (`WebDynamicBoardLayer`, `BoardView.tsx:732`) | `BoardView.tsx:842` | `:887` | `:934` |

With the OS reduce motion setting on, `getReduceMotionFromConfig`
(`node_modules/react-native-reanimated/src/animation/util.ts:150-155`) makes `withTiming` assign
the final value at once, so every reader sees k = 1:

- `blockerOpacityAt(1) = 0` (`feedbackCurves.ts:25-31`), so the blocking arrow is drawn invisible.
- The blocked-arrow colour mix `1-(1-k)^2 = 1` (`StaticBoardSurface.native.tsx:315-318`,
  `BoardView.tsx:894-902`) returns pure `ink`, so the tapped arrow never turns magenta. Its bump is
  already zeroed by the existing `reducedMotion` guard (`:312`, `:891`).
- The player loses a heart and the board shows nothing. The mount frame renders at k = 0 before
  the jump, so one or two frames of magenta may still appear. Expect that in the pre-fix capture.
- The hint does NOT disappear: its accent colour is a static prop (`StaticBoardSurface.native.tsx:360,366`,
  `BoardView.tsx:947,952`). Only the stroke pulse flattens to 1.0×.

The reduce-motion value comes from Android `Settings.Global.TRANSITION_ANIMATION_SCALE`
(`node_modules/react-native-reanimated/android/src/main/java/com/swmansion/reanimated/NativeProxy.kt:329`).
It is read once at JS module init (`node_modules/react-native-reanimated/src/ReducedMotion.ts:15-20`),
and that one constant seeds both the JS value and the UI-thread value. So the two cannot disagree,
and changing the setting on a running process changes nothing: a force-stop and relaunch is
required. `useReducedMotion()` is read in `BoardView.tsx:191`. Today only `ShakingArrow` receives
`reducedMotion`; `BlockerArrow` and `HintArrow` do not, in either renderer.

**Mechanism.** Honour the user's setting. Do not pass `ReduceMotion.Never`, which would force the
animation on people who asked for less motion. The render code decides what degrades, because the
same curves drive both renderers. Information-carrying feedback gets a static equivalent.

### Change

   `feedbackCurves.ts`, and add two new functions extracted from the inline maths:
   - `blockerOpacityAt(k, reducedMotion)`: returns `1` when `reducedMotion`, otherwise the current
     curve.
   - `blockerStrokeSwellAt(k, reducedMotion)`: returns `blockerStrokeSwellAt(0, false)` (1.6, the
     current swell at flash onset) when `reducedMotion`.
   - `blockedFlashMixAt(k, reducedMotion)` (new): 0 = `heart`, 1 = `ink`. Returns `0` when
     `reducedMotion`, otherwise `1-(1-t)^2` with `t` clamped to [0, 1].
   - `hintStrokeSwellAt(k, reducedMotion)` (new): returns the current pulse's peak factor (1.45,
     from the existing `1 + 0.45 * pulse` at `:351-354` / `:938-941`) when `reducedMotion`,
     otherwise the current expression.
   - Export the 1.45 as a named constant instead of repeating the literal.
2. Pass `reducedMotion` into `BlockerArrow` and `HintArrow` in both renderers

   `StaticBoardSurface.native.tsx:267-270,315-318,351-354` and `BoardView.tsx:845-848,894-902,938-941`
   with the shared functions.
3. When `reducedMotion` is true, do not start the `withTiming` driver in these three components.
   The derived values are then constants, and no settle-triggered re-render happens.
4. The static result under reduce motion, with lifetimes set by the timers that already exist:
   - The blocking arrow is solid `heart` at 1.6× stroke and full opacity, until
     `blockerCleanupTimer` unmounts it (`BLOCKER_FLASH_MS + 40`, `BoardView.tsx:456`).
   - The tapped arrow is solid `heart` at resting stroke with no translation, until

5. Do not touch `excludedArrows` (`BoardView.tsx:646-650`) or the visibility-mask memo (`:664`).
   The blocked tap must trigger exactly the mask rebuilds it triggers today.
