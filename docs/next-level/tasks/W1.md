# W1 — The first 90 seconds (FTUE)

A first-time player learns two things by doing them: "a tap fires the arrow" and "a blocked lane is why a tap failed". They learn them on two small hand-authored boards (T1, T2) that never call the generator. They then reach the real level 1 with one forgiveness rule switched on. Every returning player's launch stays exactly as it is today. Nothing in this workstream adds a rule or an ordering mechanic, and nothing claims puzzle depth. Arrows is a calm visual-search game. The tutorial teaches the players to read the board and how the blocked-lane feedback works, and nothing more. Every player-visible piece ships behind a build-time flag that defaults to OFF. A flag turns on only after the owner accepts screenshots or recordings in W1-11.

**Merged from:** W1-draft1 steps W1-01 … W1-09 (this workstream has only one draft). Red-team findings applied: brand-13 on W1-08 (the assist count was an invented number), on W1-06 (its reduce-motion check passed without testing anything unless W0-04 came first), and on missing work (nobody counted the words or the chrome); skeptical-14 on W1-07 (the playtest must not gate W1), on W1-02 (44/48 are published guideline values, not measurements), on W1-03 (several steps added keys to the same key list), and on W5-07 (it should consume W1-01's measured viewport); evidence-15 on W1-07 (a p75 over n=5 is meaningless), on W1-01 (the logged value must be the one used), and on W1-vs-W3 (the level-1 fixes could overshoot into too easy).

## W1-01 — Measure the board viewport, then derive the tutorial grid ceiling

- **Status:** READY (emulator geometries only; physical-phone insets are UNVERIFIED-DEVICE)
- **Effort:** S
- **Depends on:** none. W1-01 is the single owner of the viewport measurement (W3 draft 1's own viewport logging is CUT in `W3.md`; W3-08, W5-06, W5-15 and W5-16 consume `docs/board-viewport-measured.md`).
- **Flag:** none. This is a build-time diagnostic switch that no player build sets.
- **Files:** `src/ui/BoardView.tsx` (existing), `scripts/analysis/ftue-board-metrics.ts` (new; `scripts/analysis/` does not exist yet), `docs/board-viewport-measured.md` (new)

### Context
Screen points per cell at fit-to-view are set by `fitToViewport` (`src/ui/BoardView.tsx:237-248`): `fit = Math.min(vw / boardW, vh / boardH) * FIT_MARGIN`. `FIT_MARGIN = 0.94` is at `:59` and `CELL = 40` at `:52`. `boardW = cols*CELL`, so CELL cancels out and `cellPt = 0.94 × min(vw/cols, vh/rows)`. `vw`/`vh` come from `onLayout` (`:285-292`) after the header band and safe-area insets. No config file holds them, which is why W5-07 got the viewport wrong when it modelled it from an assumed header height. Every tutorial board size in W1-02 needs this number. W5 and W3 need it too, so it is measured once here.

The tap-target floor is a published guideline value, not a measurement of this game: Apple HIG 44 pt and Material 48 dp. The shipped `TAP_RADIUS_PT = 22` (`src/ui/hitTest.ts:11`) is already half of 44. Android is the only platform that ships, so W1 authors against **48 dp**. Label that as a SOURCED CONSTANT, not a measurement of Arrows players' tap accuracy.

### Change
1. (Integrator 2026-09-16: W1-01 is the only task that builds this measurement; there is no "whichever lands first" case.)
2. In `BoardView.tsx`'s `onLayout`, add a log line guarded by a build-time switch `process.env.EXPO_PUBLIC_LOG_BOARD_VIEWPORT === '1'`. Metro inlines it the same way as the `EXPO_PUBLIC_*` switches in `src/perfMode.ts`. It logs `[board-viewport] w=<vw> h=<vh>`. Player builds never set the variable.
3. Build one release APK with the switch set, install it on `fleet_floor_api31`, and record the logged `{w,h}` for three geometries:
   - native 1440×3120 @560 (514×1114 dp);
   - `adb shell wm size 1080x2340 && adb shell wm density 480` (360×780 dp, the W5-07 worst case);
   - `adb shell wm size 1080x1920 && adb shell wm density 480` (360×640 dp).

   Reset afterwards with `wm size reset; wm density reset`. For each geometry, cross-check the logged value against `adb shell uiautomator dump` bounds of the board view (px ÷ density/160). Write both values, the geometry, and the API level into the doc.
4. Add `scripts/analysis/ftue-board-metrics.ts` (run with `npx tsx`). It imports only `src/core`. Given `--level N` or `--tutorial T1|T2`, it prints rows, cols, arrow count, arrows clearable at deal (count and %), and legal-move count per state across a greedy solve. Given `--viewport WxH`, it also prints `cellPt` using the formula above.
5. In the doc, for each geometry, record the largest `rows` and `cols` with `cellPt ≥ 48`, with the formula and the logged `vw`/`vh` next to each number. Do the same for ≥ 44 as a reference row.

### Non-goals
Choosing tutorial board sizes (W1-02). Measuring the minimum legible cell for dense generated boards (W3). Any change a player can see.

### Acceptance criteria

- The doc states the maximum rows and cols for `cellPt ≥ 48` and `≥ 44` for each geometry, computed from the **logged** values. The printed formula must match the one used.
- `npx tsx scripts/analysis/ftue-board-metrics.ts --level 0` prints `rows 20 cols 20 arrows 60 clearable 19 (31.7%)`. That is the independently measured baseline above, which proves the script measures what it claims. It also equals W3-01's `npm run analysis:probe -- --version 1 --levels 1-1` row (W3-01 lands first, in Phase 2).
- A release bundle built without the variable does not emit `[board-viewport]` to logcat: install it, open a level, and `adb logcat -d -s ReactNativeJS:V | grep board-viewport` returns nothing.
- The doc says plainly that all three geometries are one emulator with `wm` overrides, and that notches, cutouts and gesture-nav insets on physical phones are UNVERIFIED-DEVICE.

## W1-03 — Add FTUE stage accessors and a pure first-run route that keeps returning players out

- **Status:** READY (after P-01 lands)
- **Effort:** S
- **Depends on:** P-01 (registers `arrows_ftue_stage`, creates `src/core/__tests__/saveSystem.test.ts`), W1-02
- **Flag:** introduces `FTUE_ENABLED` and `FTUE_ASSIST_ENABLED` (both default **OFF**) in the new `src/ui/ftueConfig.ts`
- **Files:** `src/core/saveSystem.ts` (existing; accessors only), `src/core/__tests__/saveSystem.test.ts` (created by P-01), `src/ui/ftueConfig.ts` (new), `src/ui/ftueRoute.ts` (new), `src/ui/__tests__/ftueRoute.test.ts` (new)

### Context
`SaveSystem` is an int-only store (`src/core/saveSystem.ts:12-16`). It is hydrated by a single `AsyncStorage.multiGet(SaveSystem.persistenceKeys)` (`src/ui/storage.ts:20`) over the frozen `PersistenceKeys` array (`saveSystem.ts:41-50`), and `src/ui/__tests__/storage.test.ts:36-45` asserts that array's exact contents. A key that is missing from the array silently never hydrates, which would replay the tutorial on every cold start. P-01 is the single owner of that array, the schema version and the migration. **This task must not edit `PersistenceKeys`, `storage.ts` or `storage.test.ts`.**

The store has no "has key" call, and a default of 0 cannot tell "new player" apart from "existing player on a build that predates the key". Existing players must never see the tutorial. The classification is derived from keys that already exist, and it is computed at route time on every launch rather than in a one-off migration. That also covers three cases a one-off migration would miss:
- a player who progressed while `FTUE_ENABLED` was OFF, before the flag was ever turned on;
- an Android Auto Backup restore of an old save that has progress but no stage key (`allowBackup` is on and unconfigured);
- a hydrate failure, such as private browsing on web.

### Change
- Add accessors to `SaveSystem`, using the constant P-01 defines for `arrows_ftue_stage`: `get ftueStage(): number` (raw int, default 0) and `setFtueStage(n: number)`. Stage meaning: 0 = not started, 1 = T1 cleared, 2 = T2 cleared (the assist phase), 3 = done.
- Add `src/ui/ftueConfig.ts` with `export const FTUE_ENABLED = process.env.EXPO_PUBLIC_FTUE === '1'` and `export const FTUE_ASSIST_ENABLED = process.env.EXPO_PUBLIC_FTUE_ASSIST === '1'`. Both are OFF in every build that doesn't set them. The owner's flip in W1-11 replaces each with `true` in a reviewed commit.
- Add `src/ui/ftueRoute.ts`:
  - `ftueRoute({ enabled, perfMode, stage, currentLevel, totalSolved }): 'T1' | 'T2' | 'real'`
    - `!enabled || perfMode` → `'real'`
    - `stage` not an integer in 0..3 → `'real'` (fail safe)
    - `stage >= 2` → `'real'`
    - `currentLevel > 0 || totalSolved > 0` → `'real'` (an existing player; nothing is written)
    - `stage === 1` → `'T2'`
    - otherwise → `'T1'`
  - `assistActive({ enabled, assistEnabled, stage }): boolean` returns `enabled && assistEnabled && stage === 2`.
- Do **not** change `resetProgress()` (`saveSystem.ts:146-153`). No UI reaches it (only `storage.test.ts` calls it). Whether a reset should replay the tutorial is an owner question listed in W1-11.

### Non-goals
Registering keys, migrations or `storage.test.ts` edits (P-01). Writing any stage value on first launch; the route never writes. Wiring into `App.tsx`/`GameScreen.tsx` (W1-04).

### Acceptance criteria
- `ftueRoute.test.ts` has one named test per row:
  - flags OFF, stage 0, no progress → `real`
  - `perfMode`, stage 0 → `real`
  - stage 0, no progress → `T1`
  - stage 1, no progress → `T2`
  - stage 2 → `real`; stage 3 → `real`
  - stage 0 with `currentLevel 5` → `real`
  - stage 0 with `totalSolved 17` → `real`
  - stage 1 with `totalSolved 1` → `real`
  - stages −1, 4 and `NaN` → `real`
- `assistActive` tests: true only for (enabled, assistEnabled, stage 2). False when either flag is off, and false for stages 0, 1 and 3.
- `saveSystem.test.ts` gains: `ftueStage` defaults to 0 on an empty store; a `setFtueStage(2)` round-trips through a `MemoryStore`; the accessor diff adds lines and does not modify `PersistenceKeys` (`git diff` of `saveSystem.ts` touches no line in `:41-50`).
- `npx tsc --noEmit` is clean. `npx jest` is green, and `storage.test.ts` is byte-identical to its post-P-01 version.

### Verification
1. PRE-FIX REPRODUCTION: `grep -rn "ftue" src` returns 0 hits. No first-run branch exists, so nothing can be reproduced. The failure this task prevents (a returning player sent into the tutorial) is exercised on real on-disk state by W1-10 scenario C.
