# W3 — Content and progression

**Goal.** Arrows is a visual-search game: a board gets harder only by being harder to *read*. That means more arrows to scan, a lower share of them clearable at any moment, smaller cells, and less familiar silhouettes. Today none of those levers moves with progress. `Difficulties.config(d)` (`src/core/difficulty.ts:51-67`) switches on the tier and never reads the level index. Level 1 is a 60-arrow board with 31.7% of arrows clearable. A third of the first 200 levels are a plain filled grid, and no new silhouette appears after level 168. This workstream builds the instrument first: a difficulty probe that plays every board to empty and reports search cost and clearable fraction. Everything it builds is a second generator version ("v2") that stays dark behind `GEN_V2_ENABLED`. v2 adds a capacity-aware shape bag, a clearable-fraction knob, and a level-indexed curve whose numbers come from probe runs and owner picks, not from taste. A per-install switch level means a player already at level N is dealt exactly the board they had, and the five golden checksums never change. Human playtests, naming tests and every taste call are owner tasks. The scripts and measurements behind them are agent tasks.

**Merged from:** draft 1 W3-01…W3-11 and draft 2 W3-01…W3-10. Red-team findings applied:
- **evidence-15:** the W3-04 first-level gate was unreachable, and the curve saturates flat.
- **skeptical-14:** W3-01's module fork was reworked; the W3-04 gate and τ were invented; the catalogue-stability and `shapeNameFor` collisions with W4 are resolved here.
- **brand-13:** the W3-08 pool size of ≈40 was invented.
- **performance-16:** W3-09's mask-rebuild measurement moves early; exit numbers from runs at animator scale 0 measure the reduced-motion variant.
- **Cross-workstream items:** the joint W1+W3 level-1 re-measurement; draft 1's viewport logging is merged into W1-01.

Because `BoardLogic.tryRemove` (`src/core/boardLogic.ts:112`) only empties cells, `canExit` is monotone and no tap order can brick a board. So the only cost a player pays is *search*. If a player samples uniformly without replacement, the expected number of arrows examined before finding a clearable one is `(n+1)/(k+1)`, where n is arrows left and k is arrows clearable now. The expected number of wrong looks is `(n−k)/(k+1)`.

### Context
In a search game there are few difficulty levers. Board size carries arrow count and clearable fraction together. Cell size is capped by legibility (W3-09). Hearts are fixed at 3 (DESIGN.md:133).

- Bolt (level 12) is 55.6% clearable, scan 79.

- A carved head's lane never contains unfilled cells, because `rayClearOfNeed` requires that.

- Scaling the candidate weight of such heads by `clearableBias` moves the t=0 clearable fraction. It changes only the weights, never the candidate set, so the peel proof (`:29-39`) and fill completeness hold for any bias > 0.
