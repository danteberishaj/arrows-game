# W4 — The retention meta

A player who has cleared a level gets reasons to come back tomorrow that survive closing the app,
without the calm, no-pressure register getting worse. There is one date-seeded board per day, the
same for everyone on that day. The day streak the game already keeps no longer breaks for good
after one missed day: free automatic freezes cover it, and the streak stays in the quiet `inkDim`
stats line. A gallery shows the silhouettes the player has actually solved. The store-review
prompt fires only at a perfect clear and follows both stores' rules. All of this stays int-only on
the keys P-01 registers. The shape catalogue order becomes a save-format contract. Every
player-visible piece ships behind a flag that is OFF by default. The share card is kept, but the
owner has not ruled on it, so only its preparation is READY. W4 adds no notification, no ad
placement and no motion.

**Merged from:** draft 1 W4-01…W4-10 and draft 2 W4-01…W4-10. Red-team findings applied:
brand-13 on W4-01, W4-06, W4-09 and W4-10, plus its notes that nobody owns the menu composition
and nobody counts the words. skeptical-14 on W4-01, W4-04 and W4-08, plus the catalogue-stability
contract, the version-aware backfill and the missing `saveSystem.test.ts`. evidence-15 on W4-01
and W4-04, plus the uncommitted analysis scripts and the W4-03 headroom widths.

**Measured while writing this file (2026-09-16, base `da93dcd`, Node via `npx tsx`, Mac, not
device).**
- The union of `SimplePool`, `MediumPool` and `ComplexPool` is exactly 26 distinct names.
- `SaveSystem`'s local day number for 2026-09-16 is **2450**.
- On the base commit, a save with `arrows_day_streak=14` and `arrows_last_play_day=today-2` reads
  `dayStreak = 0`. After `registerSolve`, the stored streak is **1**.
- `ShapeLibrary.pick(Difficulties.forLevel(i), new DotNetRandom(seed(i))).name` matches
  `LevelGenerator.generate(i).shapeName` for all of i = 0..299: **0 mismatches**.
- That cheap lookup takes 15.7 ms for 5000 levels.

The draft-2 figures for the daily board (median 82 arrows, 0 seed collisions, 135–146 appearances
per shape) came from scratchpad scripts that **no longer exist**. They count as unreproduced until
W4-03 re-runs a committed script.

## W4-01 — Freeze the shape catalogue as an append-only save-format contract

- **Status:** READY
- **Effort:** S
- **Depends on:** none
- **Flag:** none (no player-visible change; this adds a pure core module)
- **Files:** `src/core/shapeCatalogue.ts` (new), `src/core/levelGenerator.ts`, `src/core/index.ts`,
  `src/core/__tests__/shapeCatalogue.test.ts` (new),
  `scripts/analysis/shape-lookup-equivalence.ts` (new)

### Context
Draft sources: draft 2 W4-02 and the catalogue-pin half of draft 1 W4-03. Red-team findings:
skeptical-14 on sequencing (nobody owns catalogue stability, and backfill must be version-aware)
and the plan's list of missing work ("a shape-catalogue stability contract").

W4-07 stores a player's collection as bit positions. That makes the order of shapes part of the
save format. Today no array lists the 26 shapes:
- The tier pools overlap. `Circle` and `Diamond` are in both `SimplePool` and `MediumPool`
  (`src/core/shapeLibrary.ts:282-290`).
- The only complete enumeration is the object literal returned at `shapeLibrary.ts:292-298`.

W3 (`W3.md`, as consolidated) changes shape *selection*, not the catalogue:
- v1 stays the default path inside `levelGenerator.ts`; there is no module fork (W3-05);
- v2 adds a capacity-aware bag that can leave a shape out of a window but never removes it from the
  catalogue (W3-10);
- Bolt thickening is optional and keeps the id `Bolt`;
- new silhouettes are appended with an owner stop rule and no count target (W3-18).

If the collection keyed its bits to pool membership, or to any generator version's pool, a reorder or
removal would silently relabel every player's collection. The catalogue therefore has to live on its own,
outside any generator version.

The collection's backfill also needs "which shape was level i" for thousands of levels. Full
generation is far too slow for that. It is also unnecessary. In `generate()`
(`levelGenerator.ts:44-49`), the RNG is created and `ShapeLibrary.pick` is its **first** draw, so
the shape is fixed before any expensive work. Checked on 2026-09-16: 0 mismatches over 0..299.

### Change
1. Create `src/core/shapeCatalogue.ts`:
   - `SHAPE_CATALOGUE: readonly string[]` is frozen and lists stable shape ids. Today each id
     equals its `ShapeDef.name`. The order is the declaration order in `shapeLibrary.ts:115-274`:
     `Square, Rectangle, Circle, Diamond, Triangle, Plus, Hexagon, Star, Heart, Trophy, Crescent,
     Flower, Bolt, Arrow, Crown, Hourglass, Pentagon, Octagon, Ring, X, Butterfly, Rocket, Pine,
     Cat, Mushroom, Fish`.
   - `catalogueIndexOf(id: string): number` returns -1 for an unknown id.
   - `shapeDefFor(id: string): ShapeDef | null` resolves an id to the drawing definition. It uses
     the newest generator's definition, falling back to v1's.
   - `RETIRED_SHAPE_IDS: ReadonlySet<string>` starts empty.
   - `MAX_CATALOGUE_BITS = 60`, which is two 30-bit keys.
2. In `levelGenerator.ts`, export
   `shapeNameForLevel(levelIndex: number): string =
   ShapeLibrary.pick(Difficulties.forLevel(i), new DotNetRandom(seed(i))).name`.
   - Do not change `seed()` (lines 382-384).
   - Do not change the order of RNG draws in `generate()`.
3. Put the **stability contract** verbatim in a comment at the top of `shapeCatalogue.ts`:
   - **Append-only.** An index is permanent. Never reorder, delete or reuse an index. New shapes go
     at the end.
   - **Independent of pools and generator versions.** Removing a shape from a pool, or retiring
     it in a later generator version, does not remove it from the catalogue. Add it to
     `RETIRED_SHAPE_IDS` instead. The gallery shows a retired shape only if the player collected it.
   - **A silhouette edit keeps its id** if it is still the same object, such as a thickened Bolt;
     the gallery draws the newest definition. If the object changes, append a new id.
   - **Display names are not ids.** A rename changes a display-name map, never the id.
   - **Capacity.** At most 60 ids. Past 60, add a third additive key through the P-01 migration
     pattern. Never repack existing bits.
   - **Obligation on W3.** Any new generator version must provide an equivalent
     `shapeNameForLevel(index, version)`. It must extend this task's equivalence test to that
     version, and it must register every new shape id here before the shape can appear in a level.
     (Owners: W3-05 adds the `version` parameter and routes W4-07's fold through it, W3-10 adds the
     v2 branch, W3-18 appends ids.)
4. Export the new symbols from `src/core/index.ts`.
5. Commit `scripts/analysis/shape-lookup-equivalence.ts`. It prints the mismatch count and the
   timing of lookup against full generation over a level range given as an argument.

### Non-goals
- No change to any pool, any silhouette, `pick`, or any generated board.
- No persistence. W4-07 owns the bits.
- No UI.

### Acceptance criteria
- `SHAPE_CATALOGUE` has 26 entries, all distinct, and `Object.isFrozen` is true.
- An **order-lock test** asserts the exact 26-id array above, with a comment naming the
  save-format dependency. Inserting or reordering fails the test. Appending changes only the
  length assertion.
- Every member of `SimplePool`, `MediumPool` and `ComplexPool` resolves to an index ≥ 0.
- `SHAPE_CATALOGUE.length <= MAX_CATALOGUE_BITS`.
- `shapeNameForLevel(i) === LevelGenerator.generate(i).shapeName` for every i in 0..599, plus the
  golden indices 239, 917, 935, 3827 and 5363. Expected: 0 mismatches.
- The five golden checksums in `src/core/__tests__/levelGenerator.test.ts:150-160` pass
  **unchanged**. No constant in that file is edited.

### Verification
1. **Pre-fix reproduction.** On `da93dcd`:
   - `grep -rn "SHAPE_CATALOGUE\|shapeNameForLevel" src` returns nothing.
   - A `tsx` one-liner builds the union of the three pools and prints 26 names, with `Circle` and
     `Diamond` in two pools each. This shows no ordered catalogue exists and that pool order cannot
     be one.
2. **Closing commands.**
   - `npx jest src/core/__tests__/shapeCatalogue.test.ts src/core/__tests__/levelGenerator.test.ts`.
     The equivalence loop compares the cheap lookup against the **real** generator, which is the
     hazard: a lookup that drifts from `generate()` sets the wrong bit.
   - The unchanged golden checksums prove the export did not alter RNG draw order.
   - `npx tsx scripts/analysis/shape-lookup-equivalence.ts 0 999` prints 0 mismatches. Paste its
     output into the commit message so the figure is reproducible.
3. **TDD.** Write the order-lock test and the equivalence test first. They fail to compile until
   `shapeCatalogue.ts` and `shapeNameForLevel` exist.
4. **UNVERIFIED-DEVICE:** none. This is pure core logic.

### Risk and rollback
Low. The sharp edge is that someone later adds an RNG draw before `pick` in `generate()`, or
edits the catalogue order. Both tests catch those. Rollback is a clean revert: nothing calls the
new code until W4-07.

## W4-02 — Make the day streak forgiving with free automatic freezes, keeping it in the quiet stats line

- **Status:** READY
- **Effort:** M
- **Depends on:** P-01 (`arrows_streak_freezes`, `arrows_streak_saved_day`; creates
  `src/core/__tests__/saveSystem.test.ts`)
- **Flag:** `META_STREAK_FREEZE`, default `false`
- **Files:** `src/core/streak.ts` (new), `src/core/__tests__/streak.test.ts` (new),
  `src/core/saveSystem.ts`, `src/core/__tests__/saveSystem.test.ts`, `src/ui/HomeScreen.tsx`,
  `src/featureFlags.ts`

### Context
Draft sources: draft 1 W4-05 and draft 2 W4-06. Red-team finding: brand-13 REWORK on W4-06. Ship
the freezes; keep the streak in the existing stats line from 2 up; no standing "· 1 saved" token;
show forgiveness only when a freeze is actually spent.

Today the streak punishes and is silent about it:
- `SaveSystem.dayStreak` (`src/core/saveSystem.ts:104-109`) returns 0 as soon as
  `today - last > 1`.
- `registerSolve` (`:119-126`) then overwrites the stored streak with 1.
- One missed day destroys a 14-day chain, and nothing tells the player. Reproduced on 2026-09-16:
  a seeded 14-day chain with a one-day gap read 0, and after a solve it was stored as 1.
- The streak appears only in `buildStatsLine()` (`src/ui/HomeScreen.tsx:102-112`), from 2 days up,
  in one 13 pt `inkDim` line. DESIGN.md:91-92 specifies exactly that. It stays that way.

`dayNumber()` (`saveSystem.ts:56-60`) calls `new Date()` directly, so no day-boundary rule can be
tested without faking global timers.

### Change
1. **Injectable clock.** Add `SaveSystem.useClock(fn: () => Date)`, defaulting to `() => new Date()`.
   Add `SaveSystem.today(): number`, which applies the existing local-day formula to the injected
   clock. Route `dayStreak` and `registerSolve` through it. W4-06 and W4-11 reuse `today()`.
2. **Pure rules.** In `src/core/streak.ts`, export
   `advanceStreak(state: { today, lastPlayDay, streak, freezes }, opts: { freezesEnabled, earnEveryDays, cap })`.
   It returns `{ streak, lastPlayDay, freezes, savedToday: boolean }`. Also export
   `readStreak(state, opts): number` for the getter.

   Rules when `freezesEnabled`:
   - **First-ever solve** (`lastPlayDay === 0`): streak becomes 1.
   - **Gap 0** (same day): nothing changes.
   - **Gap 1:** the streak goes up by 1.
   - **Gap g ≥ 2** (g − 1 missed days):
     - If `freezes >= g - 1`: spend `g - 1` freezes, add 1 to the streak, and set `savedToday`.
     - Otherwise: restart at 1 and keep the banked freezes.
   - **Negative gap** (the clock moved back, or a restored backup is ahead of this device's clock):
     keep the streak, set `lastPlayDay = today`, and spend no freeze.
   - **Earning:** when the streak reaches a positive multiple of `earnEveryDays`, set
     `freezes = min(cap, freezes + 1)`. A streak carried by a freeze earns exactly like any other.

   When `freezesEnabled` is false, the function reproduces today's arithmetic exactly, including
   the getter reading 0 for a broken chain.
3. **Starting values:**
   - `STREAK_FREEZE_EARN_EVERY_DAYS = 7` — **OWNER-PICKED STARTING VALUE**, a legibility choice
     ("a week banks a miss"). It is not measured.
   - `STREAK_FREEZE_CAP = 2` — **OWNER-PICKED STARTING VALUE**. Duolingo's reported result supports
     a cap of 2–3 over 1, but not this exact number.

   Both carry an inline comment saying exactly that.
4. **SaveSystem wiring.** `registerSolve` delegates the day-chain half to `advanceStreak`. When
   `savedToday` is set, it writes `arrows_streak_saved_day = today`.

   `dayStreak` returns `readStreak`: the stored streak while the chain can still be rescued
   (`today - last <= 1`, or the freezes cover the missed days), and 0 otherwise. The menu therefore
   never shows a 0 that the next solve would undo.
5. **Menu, with the flag on.** `buildStatsLine()` keeps its format and keeps showing the streak
   from 2 up.

   If `arrows_streak_saved_day !== 0` when HomeScreen mounts, append `   ·   streak saved` to the
   line for that one mount (the copy is **OWNER-PICKED STARTING VALUE**). Then write 0 to the key.
   - Capture the text in `useState` initialisation so a theme toggle during the same visit does
     not make it disappear.
   - No new element, no icon, no colour role, no animation.

### Non-goals
- No separate daily streak.
- No streak element of its own, and no streak before day 2.
- No standing freeze count on screen.
- No count-up animation.
- No paid or advertised freezes.
- No retroactive freezes for existing chains.
- No copy that mentions deadlines, risk or time remaining.
- No change to the perfect streak.

### Acceptance criteria
- `streak.test.ts` table, with freezes enabled:
  - gap 0: nothing changes;
  - gap 1: +1;
  - gap 2 with 1 freeze: +1, freezes −1, `savedToday`;
  - gap 2 with 0 freezes: restart at 1;
  - gap 3 with 2 freezes: +1, freezes −2;
  - gap 3 with 1 freeze: restart at 1, freezes stay 1;
  - first-ever solve: 1;
  - negative gap: streak unchanged, no freeze spent, `lastPlayDay = today`;
  - reaching 7 and 14 earns one freeze each;
  - freezes never exceed the cap and never go below 0.
- **Flag-off parity.** The same table with `freezesEnabled: false` matches the base commit's
  `registerSolve` / `dayStreak` output for every row. Compute the expected values by running the

  freeze keys. The chain reads 14 and becomes 15 after a solve. Freezes read 0.
- With the flag ON, on a menu captured at 360×640 dp:
  - A fresh install with one solve shows no streak text.
  - After a seeded gap-2 solve with 1 freeze, the stats line contains `streak saved` exactly once.
  - The next menu mount does not show it.
  - No other element is added. Compare the element count with the flag-OFF capture.
- `grep -rniE "lose|expire|hurry|left to|before midnight" src/core/streak.ts src/ui/HomeScreen.tsx`

## W4-03 — Build a date-seeded daily board in its own seed namespace, with a versioned shape pool

- **Status:** READY
- **Effort:** M
- **Depends on:** W4-01
- **Flag:** none at this layer (pure core; nothing calls it until W4-06, which is flagged)
- **Files:** `src/core/dailyBoard.ts` (new), `src/core/levelGenerator.ts`, `src/core/index.ts`,
  `src/core/__tests__/dailyBoard.test.ts` (new), `src/core/__tests__/levelGenerator.test.ts`,
  `scripts/analysis/daily-band.ts` (new), `docs/next-level/measurements/daily-band-2026-09.md` (new)

### Context
Draft sources: draft 1 W4-03, draft 2 W4-03, and the script half of draft 1 W4-02. Red-team
findings: evidence-15 (commit the analysis scripts; the W4-03 headroom widths are invented) and
skeptical-14 on W4-04 (ship on the measured band; do not gate on a human playtest).

Arrows has no daily board. The generator is a pure function of the level index, but a daily cannot
reuse it naively, for three reasons:
- **Seed collision.** `seed(i) = Math.imul((2166136261 ^ i)|0, 16777619)|0` (`levelGenerator.ts:382-384`).
  Today's day number is 2450, and level 2451 (index 2450) is reachable. Seeding the daily with the
  day number would hand some player a board they already have in the campaign.
- **Pool.** `ShapeLibrary.pick` gives Normal only `Square/Rectangle/Circle/Diamond`
  (`shapeLibrary.ts:282,301-307`). The daily is the one board every player sees, and under
  Track A, silhouette novelty is part of the core loop.
- **Shape override.** `generate()` chooses the shape inside itself (`:49`), so a daily cannot supply
  its own shape without extracting the rest of the pipeline.

Two independent draft replicas both reported a median of 82 arrows at Normal config over a
full-catalogue draw. Draft 2 also reported p90 100, max 145 and near-uniform shape counts. The
scripts behind those numbers are gone, so they are **not evidence** until re-run.

### Change
1. In `levelGenerator.ts`, extract `generate()`'s body after the shape pick (lines 51-86) into
   `buildFromShape(shape, difficulty, cfg, rng): GeneratedLevel`. `generate()` calls `pick` and then
   `buildFromShape` with the same `rng`. No RNG draw may move.
2. In `src/core/dailyBoard.ts`:
   - `dailySeed(day)` is a namespaced two-round FNV:
     `let h = 2166136261; h = Math.imul(h ^ 0x64, 16777619); h = Math.imul(h ^ day, 16777619); return h|0;`.
   - `DAILY_VERSIONS: readonly { fromDay: number; pool: readonly string[] }[]` is frozen. It holds
     one entry: `{ fromDay: 0, pool: DAILY_POOL_V1 }`.
   - `DAILY_POOL_V1` lists catalogue ids in catalogue order and excludes the two no-picture fills
     (`Square`, `Rectangle`), listed explicitly by id. Do not read `ShapeDef.fillsGrid`: W3-03
     deletes that field. That leaves 24 shapes. **OWNER-PICKED STARTING
     VALUE** (recommendation). The script in step 4 reports both the 24- and 26-shape pools so the
     owner can confirm at flag acceptance.
   - `generateDaily(day)`: create `rng = new DotNetRandom(dailySeed(day))`, set
     `shape = shapeDefFor(pool[rng.next(pool.length)])`, and return
     `buildFromShape(shape, Difficulty.Normal, Difficulties.config(Difficulty.Normal), rng)`.
   - **Versioning rule.** Adding shapes to the daily (for example, after W3 authors new ones) means
     appending a new `DAILY_VERSIONS` entry whose `fromDay` is a **future** day. Past days never
     change. If W3's v2 pipeline should apply to dailies, it arrives the same way.
3. `generateDaily` reads and writes no `SaveSystem` key.
4. **Measure first, then assert.**
   - Commit `scripts/analysis/daily-band.ts`, which calls the real `generateDaily`. Over days
     0..3649 it prints, for both candidate pools: arrowCount min/p10/p25/p50/p75/p90/p95/max, max
     grid dimension, per-shape counts, consecutive-day repeats, and the seed-collision count
     against `seed(i)` for i in 0..199999.
   - Run it twice and diff the two outputs to prove determinism.
   - Record the output with its date and commit in `docs/next-level/measurements/daily-band-2026-09.md`.
   - **Only then** write the distribution assertions in step 5 from the recorded figures.

### Non-goals
- No UI and no persistence.
- No leaderboard or anti-tamper. A changed device clock gives a different daily, and that is
  accepted.
- No change to any campaign board or pool.
- No size tuning beyond Normal config. Size changes belong to W3.

### Acceptance criteria
- **The campaign is unchanged.** The five golden checksums in `levelGenerator.test.ts:150-160` pass
  with no edits. Editing one is the sign that `buildFromShape` diverged from `generate()`.
- **Determinism.** `generateDaily(d)` called twice serializes identically for d = 0, 2450 and 9999.
  Golden checksums are recorded for those three days.
- **Namespace.** `dailySeed(d) !== seed(i)` for all d in 0..19999 and i in 0..199999. The test
  derives both from the live functions.
- **Solvability.** For 365 consecutive days, a `findHint` loop clears each board in exactly
  `arrowCount` removals, the same loop as `scripts/perf/android/soak-plan.ts:58-68`. Every mask cell
  holds exactly one arrow.
- **Independence.** `SaveSystem.currentLevel` and `totalSolved` are unchanged after generating a
  daily.
- **Distribution** over days 0..3649 with the shipped pool:
  - Every pool shape appears.
  - Median and p90 arrow counts sit within bounds written as *measured value ± headroom*. Both
    numbers come from the committed measurement note, and the headroom is labelled **OWNER-PICKED
    STARTING VALUE**.
  - Consecutive-day repeats are ≤ the measured count plus labelled headroom.
- `docs/next-level/measurements/daily-band-2026-09.md` exists, contains both runs' identical
  output, and names the commit.

### Verification
1. **Pre-fix reproduction.** On `da93dcd`, `grep -rn generateDaily src` returns nothing. A `tsx`
   one-liner prints `seed(2450)` next to the seed `generate(2450)` uses, and they are identical.
   That is the collision a naive daily would ship. `ShapeLibrary.SimplePool.map(s => s.name)`
   prints the four Normal shapes.
2. **Closing commands.**
   - `npx jest src/core` (the whole core suite). The pre-existing golden checksums were computed
     against today's `generate()`, so any RNG reordering during the extraction fails them.
   - `npx tsx scripts/analysis/daily-band.ts > a.txt && npx tsx scripts/analysis/daily-band.ts > b.txt && diff a.txt b.txt`
     shows the distribution is a pure function of the code. The assertions are derived from that
     output.
3. **TDD.** Write the namespace test and the golden-checksum-unchanged run first. Write the
   distribution test after the measurement, never before.
4. **UNVERIFIED-DEVICE:** none for this logic. Whether an 82-arrow daily is *completable in a new
   player's first session* stays UNVERIFIED (see W4-05).

### Risk and rollback
The extraction is the risk: one moved `rng.next()` regenerates every campaign level for every
player. The unchanged golden checksums are the safety net; if they break, revert rather than
re-baseline. Thin shapes (the Bolt) inherit the 46-row clamp problem W3 is fixing. The daily picks
up W3's fix only through a future `DAILY_VERSIONS` entry. Rollback is a clean delete, since nothing
calls this until W4-06.

## W4-07 — Record solved silhouettes into the collection, with an incremental version-aware fold

  `src/featureFlags.ts`

### Context
Draft sources: draft 1 W4-06, and the persistence and backfill half of draft 2 W4-07. Red-team

- `saveSystem.test.ts` did not exist (P-01 now creates it).

A solved level's shape reaches the player only as a token in a 12 pt subline
(`GameScreen.tsx:270`), and nothing remembers it.

`setCurrentLevel(levelIndex + 1)` runs only on a clear (`GameScreen.tsx:122`). So every level below
`currentLevel` was solved, and existing players' collections can be reconstructed truthfully rather
than guessed.

Draft 2 ran the reconstruction inside the schema migration. That puts derived-data work on the path
that owns every player's progress (P-01's), and a one-shot backfill loses bits for levels solved
while recording was off. An incremental fold avoids both problems.

### Change
1. `src/core/collection.ts`. These are pure functions over two ints.
   - `markSeen({lo, hi}, index)` sets bit `index` in `lo` for 0–29, or bit `index−30` in `hi` for
     30–59. Use `(x | (1 << b)) >>> 0` and stay within 30 bits.
   - `hasSeen({lo, hi}, index)`.
   - `countSeen({lo, hi})`.
   - `foldLevels({lo, hi}, fromLevel, toLevel, shapeNameForLevel, maxSteps)` returns
     `{ lo, hi, through }`.
2. **Version-aware lookup.**
   - Until W3 lands, `shapeNameForLevel` is W4-01's v1 lookup for every index.
   - Once W3's generator-version seam exists, the lookup routes exactly as the game does: index
     below the player's `arrows_gen_switch_level` goes to v1, otherwise to the current version.
     W3-05 wires that routing into this fold (W4-01 contract).
3. `SaveSystem.syncCollection(maxSteps)`:
   - folds campaign levels `[arrows_shapes_through_level, currentLevel)` and writes both masks and
     the new `through`;
   - `maxSteps` = 5000 per call (**OWNER-PICKED STARTING VALUE**). The fold is incremental, so a cap
     delays bits but never drops them.
4. **Call sites.**
   - `HomeScreen` mount, where the board is unmounted and there is no gameplay frame budget.
   - Campaign clear: in `onRemoved`, after `setCurrentLevel`, only when `through === levelIndex`
     (the O(1) fast path). Otherwise defer to the next menu mount.
   - Daily clear: `registerDailyClear` also calls `markSeen` for the daily's shape.
   - A W1 tutorial board never calls any of these.
5. Expose `newlyDiscovered: boolean` on the clear path (true when the bit was 0 before this clear).
   This is data only; W5's silhouette-celebration task decides whether and how to show it.

### Non-goals
- No UI and no win-panel line.
- No bits for a loss.
- Tutorial boards never set bits.
- No change to `resetProgress()`. P-01 decides the reset set.
- No IntStore widening.

### Acceptance criteria

  - setting each of the 60 indices alone and reading every index back gives exactly one true;

  - both survive `String(v)` then `parseInt(v, 10)`, the serialization at `src/ui/storage.ts:23,39`.
