# W6 — Instrumentation and verification

W6 changes nothing a player can see. It makes the claims other workstreams make checkable. It
measures the most expensive cost on the blocked-tap path before anyone else changes that path. It
adds a remote kill switch, so a bad ad or telemetry decision can be turned off without a Play
review cycle. It defines a small, typed, on-device event stream, aggregated per level so a
250-arrow board costs nothing per tap. It records JS fatals and checks that native crash stacks
can be symbolicated. It makes `.tsx` components testable once a spike shows the toolchain
resolves. It writes down the decision rules before any data exists. The event stream stays on the
device. The network transport can be written, but it ships behind a flag that is OFF. No byte of
telemetry leaves the device until consent exists and the privacy policy and Play Data safety form
say so. The endpoint, the hosting and the legal review belong to the owner. The capture instrument
(boot into splash or menu, set and read back the motion scale, the pixel-difference floor,
phase recording and the effect-rendered gate) is **P-02**. W6 does not build it again.

**Merged from:** W6-draft1 W6-01, W6-02, W6-03 (install id and crash persistence only; the
schema-version half went to P-01), W6-04, W6-05 (drafting half), W6-07, W6-08 (kill-switch half),
W6-09, W6-14, and the draft's open verification gaps and escalations. W6-06 is moved to W7-01, and
W6-10…W6-13 are moved to P-02 (see the CUT list at the end). Red-team findings applied:
evidence-15 (W6-02's sample floor and minimum detectable effect, the W6-06/W7-01 collision, the
W6-03/W4-01 schema-key collision, the missing retrospective read, and the rule that telemetry must
not be sequenced behind the work it measures). skeptical-14 (W6-06 cut, W6-03's parallel
persistence namespace, W6-09 demoted to a spike, W6-08 pulled forward, the W6-02 vs W2 `onRemoved`
handler collision). performance-16 (the unmeasured O(n) `visibleMask` rebuild on the blocked-tap
path, the `board.arrows()` identity invariant, and the W6-11/W6-13 findings that now travel with
P-02).

**Base commit for every pre-fix observation:** the `next-level` tip before the task's first commit
(at the time of writing `da93dcd`: `npx jest` 11 suites / 61 tests, `npx tsc --noEmit` clean).
Before any native build, run `df -h /`. Only one native build may run at a time, and an arm64
release build needs about 4 GB of the roughly 10 GB free.

**Facts every W6 task relies on (read from the repo at `da93dcd`):**
- Jest runs one ts-jest project in a node environment, and only files matching
  `**/src/**/__tests__/**/*.test.ts` (`jest.config.js`). A node test cannot import `ads.tsx`,
  `GameScreen.tsx` or `App.tsx`, because they pull in `react-native`. Logic that needs a test goes
  into a pure `.ts` module that the `.tsx` calls.
- `__DEV__` is not defined under ts-jest/node. Any module under test that branches on it must take
  that branch as an injected option.
- `SaveSystem` is int-only (`src/core/saveSystem.ts:12-16`). It is hydrated by one
  `AsyncStorage.multiGet(SaveSystem.persistenceKeys)` (`src/ui/storage.ts:20`), and a key missing
  from that list silently never hydrates. Writes are cached synchronously and flushed to
  AsyncStorage on a microtask (`storage.ts:37-69`).
- On Android, AsyncStorage keeps every key in one SQLite database named `RKStorage`
  (`node_modules/@react-native-async-storage/async-storage/android/src/main/java/com/reactnativecommunity/asyncstorage/ReactDatabaseSupplier.java:25`).
  `android/` and `ios/` are generated and gitignored (`.gitignore:40-41`), so a manifest can only
  change through a config plugin in `plugins/`.
- `board.arrows()` returns the live internal array (`src/core/boardLogic.ts:60-62`), which is
  spliced in place, so its reference never changes. The mask and static-art memos in
  `src/ui/BoardView.tsx:653-666` are invalidated by `arrowCount` and `excludedArrows`, not by
  `arrows`. A task that adds a memo in `BoardView` must key it on `arrowCount`. A task that makes
  `arrows()` return a copy turns the mask rebuild into a per-render cost.

**Int keys W6 needs from P-01.** Every key is an int with default 0, and P-01 registers all of
them. No W6 task edits `PersistenceKeys`, `storage.ts`'s hydrate path or the exact-array assertion
in `storage.test.ts`. If P-01 picks different names, use P-01's names. The recommendation to P-01
is that none of these keys join `resetProgress()`.

| Key | Meaning | Used by |
|---|---|---|
| `arrows_rc_kill_bits` | last good remote kill bits (bit 0 all ads, bit 1 interstitials, bit 2 rewarded, bit 3 telemetry transport) | W6-02 |
| `arrows_rc_version` | `configVersion` of the last accepted remote config; 0 = never fetched | W6-02 |
| `arrows_tel_install_hi` | high 31 bits of the app-generated install id; 0 = not generated | W6-05 |
| `arrows_tel_install_lo` | low 31 bits of the app-generated install id | W6-05 |
| `arrows_tel_session_count` | cold starts since install | W6-05 |
| `arrows_tel_fatal_pending` | JS fatals recorded and not yet emitted | W6-07 |
| `arrows_tel_fatal_hash` | 32-bit FNV-1a hash of the last fatal's `name + message` | W6-07 |
| `arrows_tel_fatal_screen` | screen at the last fatal (1 splash, 2 menu, 3 game) | W6-07 |

**Flags.** Flags are build-time constants in `src/featureFlags.ts`. Create the file if no earlier
task has; otherwise add entries. W6 adds `REMOTE_KILL_SWITCH = false` and
`TELEMETRY_TRANSPORT = false`. Neither changes anything a player sees. They are OFF because turning
them on sends network requests, and that needs owner hosting and, for telemetry, consent.

## W6-01 — Measure the O(n) visibleMask rebuild on the blocked-tap path before anyone changes that path

- **Status:** READY
- **Effort:** M
- **Depends on:** none. It must land before W6-06 (telemetry call sites on the blocked-tap path). It
  does **not** gate W0-04: W0-04 step 5 leaves `excludedArrows` and the mask memo untouched, so the
  rebuild count it measures is unchanged, and W0-04's own criterion 7 A/B covers the blocked phase
  (integrator ruling 2026-09-16). W3-07 was merged into this task.
- **Flag:** none (measurement only; the timing hooks are build-time env gated and absent from normal builds)
- **Files:** `scripts/perf/mask-rebuild-benchmark.ts` (new), `src/ui/BoardView.tsx` (env-gated timing only),
  `modules/arrows-board/android/src/main/java/com/danteb/arrows/board/ArrowsBoardView.kt` (trace section only),
  `scripts/perf/android/benchmark.mjs` (pass one env var through the existing block at `:380-397`),
  `docs/perf-mask-rebuild-<YYYY-MM-DD>.md` (new)

### Context
A blocked tap puts the tapped arrow into `shaking` (`src/ui/BoardView.tsx:426-429`). About
`BLOCKED_BUMP_MS + 40` ms later (`src/ui/feedbackCurves.ts:8`, `BoardView.tsx:433-440`) it clears
`shaking`. Each change produces a new `excludedArrows` set (`BoardView.tsx:646-651`), which
invalidates `nativeVisibilityMask` (`:663-666`). That runs `BoardArrowArtCache.visibilityMask`
(`src/ui/arrowGeometry.ts:183-191`): a `new Set` over every visible arrow, then `map(...).join('')`
over every arrow, allocating a string per arrow. The resulting string crosses to native as the
`visibleMask` prop (`ArrowsBoardModule.kt:15-16`). There `setVisibleMask` takes a lock and calls
`rebuildCompoundPathsLocked` (`ArrowsBoardView.kt:111-115`, `:303-322`), which re-adds up to n paths
into two compound paths.

So a blocked tap costs two full JS mask builds and two full native compound-path rebuilds. At the
harness level (`FIXED_LEVEL = 3827`, 250 arrows, `benchmark.mjs:38`) n is 250. `blocked` is the
worst phase in `docs/perf-tap-forgiveness-ab-2026-09-08.md`, at 35.7–55.1 ms p95 across five
samples. No step in the plan isolates this cost. W0-04, W2-09/W2-10 and W6-06 all ship changes on
this path.

The performance reviewer's claim that the rebuild is *why* `blocked` is the worst phase is
INFERRED, not measured. This task confirms or refutes it.

### Change
1. `scripts/perf/mask-rebuild-benchmark.ts`, run with `npx tsx`. Follow the style of
   `scripts/perf/core-benchmark.ts`, which already builds boards with `node:perf_hooks`.
   - For levels 0, 168 and 3827, build the `BoardArrowArtCache` exactly as `BoardView` does.
   - Time one blocked-tap cycle: excluded set with the arrow, mask, excluded set without it, mask.
   - Use a warmup and at least 1000 measured cycles per level.
   - Print n, min, median, p95, max, arrow count and the host `uptime` load average.
2. On-device JS timing, only when `process.env.EXPO_PUBLIC_PERF_MASK_TIMING === '1'`, which Expo
   inlines at build time:
   - wrap the `nativeVisibilityMask` memo body in `performance.now()`;
   - accumulate count and durations in a module-level array;
   - `console.log` one summary line (`[mask] n=… median=… p95=… max=…`) when the board unmounts or
     every 50 rebuilds.
   - When the variable is unset, the memo body must be byte-identical to today's.
3. Native: wrap the body of `setVisibleMask` in `android.os.Trace.beginSection("ArrowsBoard.setVisibleMask")`
   / `endSection()`. Capture it with Perfetto app tracing for `com.danteb.arrows`. The perf build is
   already `profileable` through `plugins/withPerfProfileable.js`.
   - If app trace sections cannot be captured on the API 31 emulator, say so in the doc.
   - Instead, measure with a `System.nanoTime()` logcat timer on a throwaway local patch that is
     never committed, and remove the `Trace` lines.
4. `benchmark.mjs`: forward `EXPO_PUBLIC_PERF_MASK_TIMING` from the caller's environment in the
   env block, and record its value in the result JSON configuration. Do not touch
   `DEFAULT_PHASES` (`:72`).
5. Run the existing `blocked` phase:
   `EXPO_PUBLIC_PERF_MASK_TIMING=1 npm run perf:android -- --feedback --phases blocked --label mask-timing --output docs/tmp-mask-timing.json`.
   - Use AVD `fleet_floor_api31` on `-port 5556 -gpu host`.
   - Capture Perfetto during the phase.
   - Record P-02's motion-scale read-back. The harness default sets all three scales to 0
     (`benchmark.mjs:351-353`; Reanimated reads `transition_animation_scale`), so this measures the
     reduced-motion variant of the dynamic layer.
     The mask rebuild itself does not branch on reduce motion, because `shaking` is set
     unconditionally at `BoardView.tsx:426-429`.
   - From W3-07 (merged): also record 20 manual blocked taps at level index 11 (54 arrows) as a second
     on-device point, and a same-arrow null run with no mask change that sets the timer floor.
6. Write `docs/perf-mask-rebuild-<date>.md`. It must contain:
   - the node distributions and the on-device JS and native distributions;
   - per-blocked-tap totals;
   - the reconciliation;
   - the blocked-phase frame p95 from the same session, placed beside them, with the ratio labelled
     INFERRED (frame time is not additive with this cost);
   - host load average, APK sha256 and scale read-back.

### Non-goals
- Optimising the rebuild, such as an incremental mask or a bitset. That is a separate decision
  taken on this data.
- iOS. `ArrowsBoardView.swift` has not compiled since 2026-09-01.
- Changing any existing phase or its numbers.

- The doc states the smallest non-zero duration each timer reported. No difference smaller than that
  is quoted as a finding.
- With `EXPO_PUBLIC_PERF_MASK_TIMING` unset, a production `npx expo export --platform android`
  bundle does not contain the string `[mask]`.
- `DEFAULT_PHASES` in `benchmark.mjs` is byte-identical to the parent commit.

1. **PRE-FIX REPRODUCTION:** not a defect. Before quoting any number, prove the state transition

   the reconciliation. A timer that never fired means the build was not the instrumented one.
2. Commands:
   - `npx tsx scripts/perf/mask-rebuild-benchmark.ts` isolates the pure JS cost from the emulator's
     noise.
   - The `perf:android --phases blocked` run with `EXPO_PUBLIC_PERF_MASK_TIMING=1` plus a Perfetto

3. TDD: not applicable. This is a measurement. `npx jest` and `npx tsc --noEmit` stay green.
4. UNVERIFIED-DEVICE: every number is emulator (software GPU) or Mac node. A physical device may
   rank the cost differently.

### Risk and rollback
An env-gated timer left in the memo could ship. The bundle-grep acceptance guards against that.
`Trace.beginSection` is cheap when tracing is disabled (stable platform knowledge, not measured
here). If the owner wants zero native diff, use the throwaway-patch fallback. Rollback: revert the
commit. Nothing is persisted.

## W6-02 — Add a remote kill switch for ads and telemetry (client side)

- **Status:** READY (client code). Hosting the config file is W6-03, BLOCKED-ON-OWNER.
- **Effort:** M
- **Depends on:** P-01 (`arrows_rc_kill_bits`, `arrows_rc_version`), W0-01, W0-02, W0-05 (these
  are sequential edits to `src/ui/ads.tsx`, and W0-02 owns the honest "no ad available" state that a
  killed rewarded ad must use)
- **Flag:** `REMOTE_KILL_SWITCH` (default `false`). While it is false, or while the URL constant is
  empty, no request is made and every getter returns the compiled default.
- **Files:** `src/config/remoteConfig.ts` (new), `src/config/__tests__/remoteConfig.test.ts` (new),
  `src/ui/adGate.ts` (new, pure), `src/ui/__tests__/adGate.test.ts` (new), `src/ui/ads.tsx`,
  `App.tsx`, `src/core/saveSystem.ts` (getter and setter only), `src/featureFlags.ts`,
  `docs/remote-config.md` (new)

### Context
Nothing about ads can change without a new build:
- `initAds()` always contacts LevelPlay (`src/ui/ads.tsx:154-237`);
- `showInterstitialIfDue()` (`:268-290`) and `showRewarded()` (`:296-312`) have no off switch.

The only rollback for a bad mediation configuration, or a bad telemetry decision, is a new release
and a Play review cycle. The W0 release task says this outright ("No remote kill switch exists
yet"). The plan pulls this forward into Phase 1 because it is the only rollback that does not cost
a review cycle.

Per owner ruling the pacing stays as shipped (W0-05 persists the counter, and nothing else about
pacing changes). So this switch can only turn things **off**. It cannot tune `GAMES_PER_INTERSTITIAL`
(`ads.tsx:38`), and it cannot make ads more frequent.

### Change
1. `src/config/remoteConfig.ts`:
   - A pure `parseRemoteConfig(raw: unknown)` returns `{ version: number, killBits: number } | null`.
   - The accepted payload is `{ "configVersion": <safe integer ≥ 1>, "adsEnabled": bool,
     "interstitialsEnabled": bool, "rewardedEnabled": bool, "telemetryEnabled": bool }`.
   - Only a literal `false` sets a kill bit. A missing key, a wrong type or `true` leaves that
     feature enabled.
   - A payload whose `configVersion` is not a safe integer ≥ 1 returns `null`.
   - Unknown keys are ignored.
   - A body over a size cap is rejected before `JSON.parse`. The cap is an OWNER-PICKED STARTING
     VALUE; propose 4096 bytes.
2. `applyFetched(parsed, cached)`:
   - Accept a result only when `parsed.version > cached.version`. That makes the change monotone,
     so a stale CDN copy cannot undo a newer kill. To re-enable, the owner publishes a higher
     version.
   - Persist through `SaveSystem` accessors on P-01's two keys.
3. `initRemoteConfig({ url, fetchImpl, timeoutMs })`:
   - `url` comes from `REMOTE_CONFIG_URL`, a constant in `remoteConfig.ts` defined as
     `process.env.EXPO_PUBLIC_REMOTE_CONFIG_URL ?? ''` (Expo inlines it at build time). The committed
     value is empty; W6-03 compiles in the real URL.
   - Called once from `App.tsx` after `initSaveSystem()` resolves.
   - **Boot order.** Today `App.tsx:35` calls `initAds()` synchronously in the same effect as
     `initSaveSystem()`, before hydration finishes, while `SaveSystem` still points at its in-memory
     store. A cached kill read at that moment is always 0, so `LevelPlay.init` would run even with a
     kill persisted. Move the `initAds()` call so it runs only after `initSaveSystem()` settles
     (in both the `.then` and the `.catch` that W0-03 added), after the persisted kill bits have
     seeded the getters. `initRemoteConfig` may start in the same place; it never blocks `initAds`.
   - Fire-and-forget. It never blocks the first render and never throws.
   - Uses `AbortController` with `timeoutMs`, an OWNER-PICKED STARTING VALUE (propose 3000 ms).
   - Returns immediately when `REMOTE_KILL_SWITCH` is false, when `url` is empty, or when
     `PERF_MODE` is on (`src/perfMode.ts:13`).
4. Getters `RemoteConfig.adsKilled()`, `interstitialsKilled()`, `rewardedKilled()` and
   `telemetryKilled()` read the in-memory value, which is seeded from the persisted bits at boot.
   A kill fetched mid-session applies to the next ad decision. A kill that is already cached applies
   from the first decision of the next cold start, even offline.
5. `src/ui/adGate.ts` (pure): `adDecision(format, killBits)` returns `'allowed' | 'killed'`.
6. `ads.tsx`, reading at call time and never capturing at module load:
   - `initAds()` does not call `LevelPlay.init` when the cached `adsKilled()` is true. W0-02's retry
     path checks the same gate.
   - `showInterstitialIfDue()` returns early when killed, **without** changing W0-05's counter.
   - `showRewarded()` resolves `false` when killed, and W0-02's readiness reports not-ready, so the
     player sees W0-02's "no ad available" state. It grants no hint and no heart.
7. `docs/remote-config.md` covers:
   - every key, its default and what happens when it is wrong;
   - the monotone version rule;
   - "config values only; downloading code through this channel violates Play's Device and Network
     Abuse policy";
   - the fact that the request exposes the device IP to the host (input for W6-13 and W7-05).

### Non-goals
- Tuning `gamesPerInterstitial`, cooldowns, caps or grace periods remotely (rejected by owner
  ruling on pacing).
- Sample rates, A/B assignment or any "enable" direction.
- Hosting (W6-03).
- The consent state (W7-01).

### Acceptance criteria
- `remoteConfig.test.ts` feeds `null`, `[]`, `"x"`, `42`, `NaN`, `{}`,
  `{configVersion: 0}`, `{configVersion: 1.5}`, `{configVersion: "2"}`, `{configVersion: 2,
  adsEnabled: "false"}`, a body over the cap, and an unknown extra key. Every case returns either
  `null` or a result with only literal-`false` bits set, and nothing throws.
- A fetch that rejects, times out (fake timers) or returns non-2xx leaves the cached bits
  unchanged. With nothing cached, every getter reports "not killed".
- A payload with a version less than or equal to the cached version is ignored. A higher version
  replaces the cache and is written through the `SaveSystem` setters, which are asserted against a
  `MemoryStore`.
- `adGate.test.ts` covers all 4 bits × both formats. Killing interstitials does not kill rewarded,
  and killing ads kills both.
- With `REMOTE_KILL_SWITCH=false`, a mocked `fetchImpl` is called 0 times.
- On the emulator (dev build, `adb reverse tcp:8787 tcp:8787` to a local static server serving the
  file; the URL comes from `EXPO_PUBLIC_REMOTE_CONFIG_URL`), with `REMOTE_KILL_SWITCH` set to `true`
  **locally and uncommitted** (the committed `false` makes no request, so the flip cannot be
  observed without it), in both directions:
  - Publish `adsEnabled:false` with version 2, cold start twice, and finish enough games that an
    interstitial is due. Zero interstitials are shown (neither a real one nor the `__DEV__` simulated
    host), the rewarded button shows W0-02's unavailable state, and logcat shows the accepted version.
  - **Cached kill at boot:** on the second cold start of that direction, with a temporary log line
    immediately before `LevelPlay.init`, logcat shows no init line. This fails if `initAds()` still
    runs before hydration (Change step 3, boot order).
  - Then publish `adsEnabled:true` with version 3, cold start, and the ads return. Observe the return
    without displaying a live ad (W0-02's rule): logcat shows the init line and a rewarded
    `onAdLoaded`, and the rewarded button renders enabled (screencap). Do not tap an enabled ad
    button or reach a due interstitial with the network on unless the owner has registered the
    emulator as a test device.
  - A record showing only one direction does not pass. Revert the local flag and log lines before
    commit; the committed diff shows `REMOTE_KILL_SWITCH = false`.

### Verification
1. **PRE-FIX REPRODUCTION:** on the base APK, block the device from the ad network through the
   emulator's airplane mode. No control exists: the only way to stop LevelPlay contact is a new
   build. Record `grep -n "LevelPlay.init" src/ui/ads.tsx`, which shows an unconditional call. This
   is the missing capability, not a defect replay.
2. Commands:
   - `npx jest src/config src/ui/__tests__/adGate.test.ts` covers every path through the parser and
     the gate, because both are pure.
   - The two-direction emulator flip exercises the real fetch → parse → persist → gate → `ads.tsx`
     chain. Only it proves the `ads.tsx` wiring, which node jest cannot import.
3. TDD: write `remoteConfig.test.ts`'s hostile-payload case and `adGate.test.ts` first. Both fail
   because the modules do not exist.
4. UNVERIFIED-DEVICE: a release build over HTTPS against the real host is W6-03. Cleartext
   `http://localhost` is expected to work only on a dev build (INFERRED, not checked).

### Risk and rollback
- A stuck kill (for example the host deleted after a kill was published) keeps ads off, which costs
  revenue. It fails safe for players, and `docs/remote-config.md` names the recovery (publish a
  higher version with `true`).
- A parser bug cannot enable anything, because only literal `false` acts.
- Rollback: set `REMOTE_KILL_SWITCH=false`. The persisted bits are then ignored because the getters
  return defaults when the flag is off. State this in the getter and test it.

## W6-03 — Host the kill-switch config file and prove its caching by observation

- **Status:** BLOCKED-ON-OWNER. The owner must choose the origin (for example the domain that hosts
  the privacy policy), give access to the hosting account, and confirm with legal review
  (W7-07) that a config request exposing the device IP to that host is covered by the
  published privacy policy.
- **Effort:** S
- **Depends on:** W6-02
- **Flag:** flips `REMOTE_KILL_SWITCH` to `true` and compiles in the URL, in a release the owner
  approves
- **Files:** the hosted `arrows-config.json` (outside this repo, or in the hosting repo the owner
  names), `docs/remote-config.md`, `src/config/remoteConfig.ts` (URL constant), `src/featureFlags.ts`

### Context
W6-02 ships with an empty URL. The file must be static, not a function, because a function bills an
invocation and its duration on every cold start. The kill must reach devices quickly after a
publish, but every cold start still costs one edge request.

### Change
Once the owner unblocks it:
1. Deploy `arrows-config.json` with `configVersion: 1` and every feature `true`.
2. Headers, if the host is Vercel:
   - `Cache-Control: public, max-age=0, must-revalidate` for the client;
   - `Vercel-CDN-Cache-Control: max-age=31536000` so the edge answers, and a deploy purges it.
   - This is the house pattern for a file that must change the moment it is redeployed. Record the
     equivalent headers if the host is different.
3. Compile in the URL, flip the flag, and add the release to the owner's release checklist.

### Non-goals
- A dynamic endpoint, per-user targeting or authentication.

### Acceptance criteria
- `curl -sI <exact URL the app fetches>` shows 200 and the headers above. A second request shows
  `x-vercel-cache: HIT` (or the host's equivalent). The check runs against the real URL, not against
  a `headers` pattern in a config file.
- The release build does both directions of W6-02's flip against the real URL over HTTPS, using the
  two-cold-start protocol.
- The measured time from redeploy to the first device fetch that sees the new version is written in
  `docs/remote-config.md`.

### Verification
1. **PRE-FIX:** `curl -sI` on the URL before deploy returns 404, which proves the check can fail.
2. `curl -sI` twice, then the release-build flip. The flip is the only check that exercises the
   real TLS, CDN and cache path the kill will travel.
3. TDD: not applicable.
4. UNVERIFIED-DEVICE: behaviour on real carrier networks.

### Risk and rollback
A header block whose pattern never matches the real path is the common silent failure, so the
headers are asserted on the real URL. Rollback: redeploy `configVersion` n+1 with everything
`true`.

## W6-04 — Define a typed event schema and a pluggable sink that does nothing by default

- **Status:** READY
- **Effort:** S
- **Depends on:** none
- **Flag:** none (no runtime behaviour: the default sink is a no-op and nothing is persisted or sent)
- **Files:** `src/telemetry/events.ts` (new), `src/telemetry/telemetry.ts` (new),
  `src/telemetry/hash.ts` (new), `src/telemetry/__tests__/telemetry.test.ts` (new)

### Context
The app has no analytics of any kind (NEXT-LEVEL-PLAN §1.4). So none of W1 (does the tutorial
teach), W3 (is the curve right) or W4 (does the daily bring players back) can be shown true or
false on Arrows' own players. The product is an attention game where the only failure is a misread
(owner ruling, Track A). The signals are therefore:
- taps;
- blocked taps;
- hearts left on a clear;
- where players stop.

"Puzzle depth" is not one of them. W1-08 (a dev-only session log) and W4-04 (a dev-only
time-to-clear instrument) both say they must reuse W6's aggregation rather than build a second one.

## W6-14 — Write the batched HTTP transport client, shipped with the flag OFF and no endpoint

- **Status:** READY
- **Effort:** M
- **Depends on:** W6-04, W6-05, W6-06, W6-02 (telemetry kill bit)

- events not sent before the process dies are lost;

Android stops JS timers while the app is paused, so a flush must start synchronously inside the

### Change
1. `createHttpSink({ url, fetchImpl, appState, consentGranted, killed, installId, cap })`, with
   every platform dependency injected so node jest can test it.

   - `flush()` builds one POST body: `{ installId: "<hi>-<lo>", events: [...] }`.

   - an AppState change to `background`, called synchronously from the listener;
   - `session_end`;
   - the first `flush()` after the next `app_open`.

   - one immediate retry;
   - after that the batch stays in memory for the next trigger;
   - a flush never throws into React and never blocks a screen change.
4. Gate: `flush()` and `send()` are no-ops unless all four hold: `TELEMETRY_TRANSPORT`,

5. `App.tsx` installs this sink only when the flag is true. Otherwise it keeps `noopSink`.

### Non-goals

- Persisting the queue.
- Consent UI.

### Acceptance criteria

- A rejected fetch triggers exactly one retry. Both failing leaves all events queued, and the next
  trigger sends them in one call.
- The flush runs synchronously inside the AppState callback. The test asserts `fetchImpl` was called
  before the callback returns, with fake timers never advanced.
- With any one of the four gate inputs false, `fetchImpl` is called 0 times over 1000 events and 3
  triggers.
- The serialized body contains no key `advertisingId`, `gaid`, `idfa`, `ip`, `deviceId`, and no
  property outside `EventSchema` plus `installId`.
- The cap holds: 10,000 sends leave at most `cap` events queued, the newest ones.
- In a release bundle built with the default flags, `grep` for the literal `sink.http` or the
  transport's log tag finds only dead-code-eliminated references, or finds none. Record which.
