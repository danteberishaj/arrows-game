## What changed

- `src/ui/adReadiness.ts` (new, pure TS): `createReadiness(initial=false)` returns `{ get, set, subscribe }`. It notifies only on a real change, and a subscriber can safely unsubscribe itself while being notified.
- `src/ui/adInit.ts` (new, pure TS): `createAdInitController({ attempt, delaysMs, setTimer, clearTimer })` with the states `idle | running | ready | failed`.
  - `start()` does nothing while `running` or `ready`, and never rejects.
  - After a failure it schedules `delaysMs[firedCount]`. A timer that gets cancelled does not count, so at most `delaysMs.length` timed attempts ever fire.
  - `onAppActive()` starts an attempt only in `failed`, and cancels any pending timer first.
  - `AD_INIT_RETRY_DELAYS_MS = [5000, 15000, 45000]` is an OWNER-PICKED STARTING VALUE.
- `src/ui/ads.tsx`
  - Readiness: `syncRewardedReady()` uses the native `rewardedLoaded` once handles exist, otherwise `__DEV__ && fakeAdListener !== null`.
    - `onAdLoaded` sets it true.
    - `onAdLoadFailed`, `onAdDisplayed`, `onAdDisplayFailed` and `onAdClosed` set it false.
    - `AdHost` mount and unmount re-sync it.
  - The store is exposed as `Ads.rewardedReady` (a getter) and `Ads.subscribeRewardedReady(cb)`. There is no polling.
  - `initLevelPlayOnce()` keeps the order init, then assign `lpInterstitial`/`lpRewarded`/`levelPlayApi`, then un-awaited `loadAd().catch(reload)`.
  - `createReloader()` keeps one pending reload per ad and reuses the existing 15 s delay, now named `RELOAD_DELAY_MS`.
  - `initAds()` requires the module once. If that fails there is nothing to retry. Otherwise it calls `adInitController.start()`.
  - Dev logs now go through `adLog()` (`if (__DEV__)`).
- `App.tsx`: `initAds().catch(() => {})`, plus `AppState.addEventListener('change', s => s === 'active' && adInitController.onAppActive())`, removed on unmount.
- `src/ui/HeaderButton.tsx`: new `disabled?: boolean`. It is passed to `Pressable` and to `accessibilityState={{ disabled }}`. A disabled glyph uses the `active=false` colour, **plus opacity 0.35** (deviation 1).
- `src/ui/GameScreen.tsx`
  - `useSyncExternalStore(Ads.subscribeRewardedReady, …)`.
  - The hint is disabled when `!rewardedReady || terminalPending || adBusy`.
  - Continue is disabled when `!rewardedReady || adBusy`, and while not ready it is drawn with a `heartLost` background and `inkDim` text.
  - Lose-panel subtitle: `No ad available right now — Retry is free` when `!rewardedReady || adShowFailed`.
  - `adShowFailed` is set when a show resolves `false`. It is cleared by a readiness change (direct subscription), a board tap (`onRemoved`/`onBlocked`), a new show attempt (deviation 3) or `loadLevel`.
  - During play, `Hint unavailable ·` replaces the mission label (deviation 2).
  - Nothing is granted unless `earned === true`, which is unchanged.

### Deviations from the brief's letter (each found by a capture, each needs owner acceptance)
1. **Disabled hint dimmed with opacity 0.35 (OWNER-PICKED STARTING VALUE).** On the first build (A0), the disabled 💡 was pixel-identical to the enabled one: its crop bbox diff against the pre-fix capture was `None`, even though uiautomator read `enabled="false"`. Android draws the emoji in full colour whatever Text `color` says, so "same inactive colour" alone would still have shipped a button that looks available and does nothing (`post/A0-superseded/`). W0-06 still owns colour.
2. **`Hint unavailable` takes the mission label's place.** On build B0, appending ` · Hint unavailable` after `60 left` pushed the hint button off the right edge at 1440x3120 / 560 dpi (411 dp) (`post/B0-superseded/c6-06-after-hint-tap-hint-unavailable.png`). The row now reads `Hint unavailable · 60 left`: the same row, one line, no new component, and the board is not overlaid.
3. **The label clears when a new show starts.** The web dev preview showed `Hint unavailable` next to a hint that had just been granted (skip, then claim). No readiness change or board tap happens between the two on the simulated path (`web/run1-found-stale-label/web-02-hint-claimed.png`).
4. **`loadLevel` (Retry / Next) also clears the label.** Otherwise a failed Continue would show `Hint unavailable` on the fresh board after Retry.

## Concerns
1. **Criterion 3 cannot close on this emulator.** LevelPlay answered `Mediation No fill` (509) to every rewarded and interstitial load: 4 online probes in the premise build and 14 reloads in the criterion 3 run. Re-init after app-active and init success are proven. `onAdLoaded` and the enabled Continue are proven only through forced readiness. Closing it needs a physical device with Play Services, or an owner-registered test device.
2. **Defect (b) does not happen as worded.** `loadAd()` resolves offline and on no-fill (premise Q2), so a first load never rejected in practice and never nulled the handles. The handle-assignment fix and the reload guard are hardening. Criterion 5 proves them with an injected throw.
3. **"Criteria 2-5 on one release build" is impossible as written.** Criterion 5 needs an injected throw, and criteria 3 and 4 need temporary logs, so every capture build differs from the shipped code. The split was: A (temp logs) for criteria 2-4; C (`382dd9f`, no temp code) repeating criterion 2 plus log-free init counts for 3 and 4; B2 (final commit + injections) for criteria 5 and 6. The code differences are recorded as patches. A0 and B0 are kept as superseded evidence for deviations 1 and 2.
4. **Picked values and looks the brief did not specify:** `DISABLED_GLYPH_OPACITY = 0.35`; Continue's not-ready look (`heartLost` background, `inkDim` text, text contrast not measured, W0-06 owns contrast); the `Hint unavailable ·` placement. The lose panel's width also changes with the subtitle length, because the panel sizes to its text (`final/c6-lose-panels-montage.png`).
5. **No init timeout.** If LevelPlay never calls either init callback, the controller stays `running` and app-active does nothing. The brief sets no timeout, and I did not add a number. This was not observed: every attempt got a callback within 0.02-2.3 s.
6. **A stale "ready" is possible.** If `isAdReady()` returns false while the last callback said loaded (for example an ad expiring without a callback), the tap shows the honest label but the button stays enabled until the next callback. Readiness changes only on SDK callbacks, as the brief requires. Not observed.
7. **"Board tap" means a tap on an arrow** (`onRemoved`/`onBlocked`). A tap on empty board space does not clear the label, because `BoardView.tsx` is outside this task's Files list.
8. **The hint now also dims during `terminalPending`/`adBusy`**, because `disabled` includes them as the brief specifies. Before, that state was colour-only and invisible on the emoji.
9. **Host conditions.** Load average reached about 25, and the concurrent geoguesser session ran its own emulators. One pre-fix run was invalid, and one ANR happened on W0-01's APK while gradle ran. Free disk dipped to 3.1 GiB (swap) during the task, and building waited until it recovered to 7.5 GiB. It ended at 5.7 GiB. `android/app/build` (767 MB) was kept for W0-03+ incremental builds.
10. **Emulator state left behind.** emulator-5556 has APK C (`382dd9f`, no temp code) installed with cleared data, radios on, scales `1 1 1`, the app force-stopped and `./gradlew --stop` run. adbd is still root.
11. **Rewarded and interstitial reloads repeat every 15 s forever while there is no fill.** That is the shipped behaviour and unchanged, now with a single pending reload per ad.
