## Outcome

With `EXPO_PUBLIC_META_GALLERY=1` and at least one solve, the menu shows a quiet `Gallery` text control. It sits
in the same row as W4-06's daily line (inkDim, Fredoka SemiBold 15, no pill, a ≥ 44 × 44 dp box). It opens a
screen with:

- a fixed header: the `‹` HeaderButton and one count line, `N of M`;
- a vertical ScrollView of 40 dp tiles, one `react-native-svg` `Svg` + `Path` per tile, in catalogue order.
  - **Collected:** `silhouettePath(shapeDefFor(id).rasterize(14, round(14 × aspect)))` filled in `ink` with
    `fillRule="evenodd"`, with the display name under it in `inkDim` (Fredoka SemiBold 12).
  - **Not collected:** the same path, outlined in `pipSpent` (1.5 dp stroke, no fill), with no name.
  - **Retired and not collected:** no tile.

Nothing on the wall is pressable. There are no level numbers, stars, scores or tile motion. `‹` and Android's
hardware back (`BackHandler`, consumed) return to the menu. Opening the gallery runs W4-07's sliced collection
fold from the first frame, with no 2 s menu delay, and the wall fills as the bits arrive. With the flag OFF the
menu is BASE: a jest tree check against BASE-written snapshots, plus a masked pixel diff of 0 px.

## Performance

All numbers: EXECUTED on the API 31 emulator at 360×640 dp, scales 1/1/1, UI thread only (HWUI `gfxinfo
framestats`, Flags == 0). They belong to this emulator on this loaded host (loadavg 4–7); UNVERIFIED-DEVICE.
Windows are aligned with the app's own `[capture-diag] screen=…` logcat lines and `W409MARK` marks
(`logcat -v monotonic` = framestats IntendedVsync). Scripts: `scripts/perf-run.sh`, `perf-analyze.py`,

### Menu, ON against OFF (the gallery route must not add work to the menu)

**Design:** equal protocol, cold starts in menu-only mode, arms alternating in blocks (OFF, ON, OFF, ON …),
3 runs per block, each block = install + unmeasured warm-up. Two rounds (`perf/abab`, `perf/abab2`),
pooled in `perf/abab-pooled/summary.txt`: **24 OFF against 24 ON**. The null is |median(odd blocks) −
median(even blocks)| of the same APK. The p value is a permutation test (20 000 shuffles).

| metric (per-run statistic, ms) | OFF | ON | effect | null OFF / ON | p | verdict |
|---|---|---|---|---|---|---|
| mount window [0, 2 s): p50 | 22.11 | 21.59 | −0.52 | 8.32 / 0.32 | 0.020 | inside null (ON faster) |
| mount: p95 | 43.88 | 43.06 | −0.81 | 1.99 / 0.88 | 0.73 | inside null |
| mount: max | 78.63 | 75.81 | −2.83 | 1.22 / 1.37 | 0.40 | outside null, p ≥ 0.05 (ON faster) |
| mount: frames n | 113.5 | 113.5 | 0 | 1.0 / 1.0 | 1.00 | inside null |
| steady window [2.5, 5 s): p50 | 8.18 | 8.21 | +0.04 | 0.27 / 0.19 | 0.79 | inside null |
| steady: p95 | 11.64 | 11.69 | +0.04 | 1.08 / 0.33 | 0.91 | inside null |
| steady: max | 13.81 | 14.91 | **+1.10** | 0.25 / 0.98 | **0.037** | outside null (see below) |
| steady: deadline misses | 0 | 0 | 0 | 0 | 1.00 | inside null |

- **Sample reconciliation:**
  - mount window: 105–119 frames against 117–120 expected (2 s × 60 Hz = 120), window start covered in 48/48
    runs;
  - steady window: 147–148 frames against 149–150 expected (150).
- **Per-frame app work** (pooled frames, steady window, runs not in buffer-wait mode; 3403 OFF / 2960 ON frames
  against 3450 / 3000 expected; `perf/abab-pooled/steady-frames.txt`):

  | stage | OFF p50 / p95 / p99 (ms) | ON p50 / p95 / p99 (ms) |
  |---|---|---|
  | UI thread | 1.85 / 2.89 / 3.50 | 1.88 / 2.98 / 3.51 |
  | render issue | 3.07 / 6.37 / 7.73 | 3.02 / 6.04 / 7.71 |

- **Why steady.max moves:**
  - p = 0.037 is uncorrected across 12 metrics; the Bonferroni level is 0.004. Per round it was p 0.023, then
    0.381.
  - The difference sits in the emulator's **buffer-wait mode**: DequeueBufferDuration ~14 ms, frames complete
    one vsync late, and no vsync is skipped.
  - That mode occurred in 4/24 ON runs against 1/24 OFF runs. Fisher exact test p = 0.35.
  - My reading (INFERRED): display back-pressure on the emulator, not app work, since the app's own work per
    frame is the same.
- **Earlier unequal-protocol rounds, reported for honesty:**
  - Design: OFF×6 / ON×6 / OFF×6. In these rounds every ON run also opened the gallery, scrolled and took a
    screencap before the next force-stop.
  - Round 1 (`perf/aba1`): no metric different.
  - Round 2 (`perf/aba2`): menu mount max ON **+28.3 ms, p = 0.001**. It did **not** replicate in either
    equal-protocol round (−3.97 and +0.08).
  - I attribute it to the protocol asymmetry and host load, not the flag. INFERRED.

## Decisions

1. **Placement:** the Gallery control shares one row with the daily line, so the column does not grow. The
   upper-block 36 dp spacing (W4-06) applies when either control is shown. W4-10 owns final placement.
2. **Outline role:** `pipSpent`, the spent-heart-pip precedent: an outline with no fill meaning "not had".
   3.02:1 in both themes. Stroke 1.5 dp, round joins (OWNER-PICKED STARTING VALUE). The louder alternative is
   `border` (3.47 / 3.42).
3. **Count:** N counts collected non-retired shapes, so the line never reads above M. A collected retired shape
   is still shown.
4. **Display name:** `shapeDefFor(id).name`, the same string as the win panel's subline.
5. **Layout:**
   - fixed header, scrolling grid;
   - cell minimum 68 dp and column gap 8 dp (OWNER-PICKED STARTING VALUES), giving 3/4/5 columns at
     320/360/412 dp;
   - whole-dp cells, with the leftover going to the gutters.
   - At 360×640 the 7th row sits under the nav bar until scrolled (about 78 dp of scroll).
6. **Screen transition:** the gallery uses App's standard 180 ms screen FadeIn, which honours reduced motion,
   like every other screen. Tiles have no motion of their own.
7. **Sync on open:** time-sliced, reusing W4-07's machinery with no delay, instead of a synchronous catch-up.
   The wall re-renders only when a slice changes the masks, and tiles are memoised.
8. **Code location:** `galleryTilePath` and `galleryWall` live in `galleryLayout.ts`, a pure module the node
   jest project can test. The path cache is module level.
9. **Capture builds:** they carry `EXPO_PUBLIC_CAPTURE_DIAG=1` (screen markers) on top of W5-04's flag set. The
   handback APK does not.
10. **Build method:** JS repack (GLOBAL.md recipe) over `artifacts/W5-04/apk/arrows-testads-W5-04.apk`, no
    gradle. Native is unchanged since 87ec519.
11. **Accessibility:** the `‹` button got `accessibilityRole="button"` and `accessibilityLabel="Back"`.
    Collected tiles are accessible with their name; outlined tiles are not focusable.

## Concerns

1. **Scroll on the emulator:**
   - In 8/12 runs the swipe-up window ran in buffer-wait mode: 20 ms frames, one vsync late, no skipped vsyncs,
     53–55 deadline misses.
   - In the same runs, swipe-down never did.
   - App work stays ≤ 3.9 ms p99.
   - The cause is not isolated. The API 31 stretch overscroll on the emulator's software GPU is a candidate
     (INFERRED, untested); `overScrollMode="never"` would test it.
   - UNVERIFIED-DEVICE.
2. **Gallery first frame:** a median of 79 ms (up to 179 ms under load) drops a few frames at the start of the
   fade. The cost is UI-thread recording of 26 per-tile `Svg` views, the brief's structure. UNVERIFIED-DEVICE.
3. **Menu steady.max +1.1 ms:** p 0.037 uncorrected (see above). Per-frame app work is equal; I read it as
   emulator back-pressure, INFERRED. The unequal-protocol +28 ms mount max did not replicate.
4. **Capture tree against final tree:**
   - The capture and perf APKs were built from tree `2ea174bd2a62`.
   - After them I reworded one 3-line comment in `HomeScreen.tsx` (above the upper block). No line counts or
     code changed.
   - The final tree is `8e95f5a262ab` (git-diff sha `f805b84d2691`). All gates and the handback APK come from
     the final tree.
5. **Ink Night nav bar:** the Android navigation bar stays light in Ink Night. This is pre-existing (W5-04's
   night captures show it too) and out of scope.
6. **Menu margin:** 7 dp between the entry row and the stats line at 360×640, inherited from W4-06. Name

### Change

`src/ui/GalleryScreen.tsx`:

- `TileWall` is one `react-native-svg` `Svg`: absolutely positioned under the grid, the grid's size, and
  `pointerEvents="none"`.
- Every tile is one `Path` in it, with the same `d`, collected fill and outlined stroke as before, placed with
  `transform="translate(x y)"`.
- The grid cells stay RN `View`s. They keep the tile testIDs, accessibility and the name `Text`; the name sits
  under a `paddingTop: tileSize` box.

**Why it was slow.** react-native-svg's Android `SvgView.onDraw` rasterises each Svg into its own ARGB bitmap
(`drawOutput`, SvgView.java:267-283). So each of the 26 per-tile Svgs was a separate bitmap allocation and a
separate software draw.

`src/ui/galleryLayout.ts`:

- adds `roundToPixelGrid` (Yoga's rule: half up, 1e-4 tolerance);
- adds `galleryTileOrigin(index, layout, rowPitch, pixelRatio)`.

The first one-Svg build placed each path at its unrounded flex position. That was pixel-identical at 3.0 px/dp,
but 14 246 px (0.33 %) differed at native 3.5 px/dp: silhouette edges moved by ¼ to ¾ px. Yoga used to round
each per-tile view to the pixel grid. The origins are now rounded the same way, so the pixels match at any
density.

**SvgText was not built or measured.** RN `Text` keeps the names pixel-identical. The measurements below show
names are not the cost: a whole mount frame is 25–30 ms in opens without the warning burst.
