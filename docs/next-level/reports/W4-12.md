## What the script does

For every id in `DAILY_POOL_V1` (24 shapes), the script scans `generateDaily(day)` forward from
day 0 and keeps the first 5 REAL occurrences of that shape (never a forced/synthetic shape — every
board is the genuine, unmodified daily draw). That gives 120 boards total. A day-0..167 survey
found every shape's 5th occurrence inside that window, so the script's own scan cap (2000 days) is
generous; it throws if a shape is somehow not found within the cap rather than silently truncating.

Each board's mask is cropped to its bounding box, then box-downsampled (>=50% coverage per output
cell) to each of the 4 candidate widths (8/10/12/16), rendered in each of the 3 candidate glyph
sets (`⬛/⬜`, `■/□`, `🟪/⬜`), with and without a placeholder URL line — 24 render variants per
board, 2,880 total. The header is `Arrows · <date>` / shape name / `Hearts left: H/3` / `Day streak:
N`; hearts and streak are NOT simulated play (nothing here plays a level) — they are script-picked
placeholders varied across the 5 occurrences (streak: 1, 7, 21, 100, 365 — chosen to exercise 1/2/3
digit widths, since digit count is what can move the character budget) and are called out as such
in the script's own header comment so nobody mistakes them for shipped numbers later.

The placeholder URL (`https://play.google.com/store/apps/details?id=com.danteb.arrows`) uses the
project's real, unpublished Android package id from `app.json` — it is not a claim the app is live,
just one concrete, correctly-shaped candidate for the owner's "which URL" ruling.

Output: a full dump (every shape's first occurrence printed as 24 full cards = 576 printed cards,
plus a 2,880-row metrics table covering all 120 boards so the summary maxima aren't from a single
lucky/unlucky day) and a curated owner sheet with side-by-side comparisons and the four ruling
questions spelled out.

## Candidates, in short

- **Glyph set** — `⬛/⬜`, `■/□`, `🟪/⬜` at a fixed width/board, shown side by side in owner sheet
  section A. `⬛⬜■□` are single BMP code points (1 UTF-16 unit each); `🟪` (U+1F7EA) is astral (a
  UTF-16 surrogate PAIR) paired with the BMP `⬜` — the one glyph set where UTF-16 length and
  code-point count diverge (confirmed in the metrics: Circle @ width=8, no URL is 130 UTF-16 units /
  130 code points for `⬛/⬜` and `■/□`, but 184 UTF-16 units / 130 code points for `🟪/⬜`).
- **Column width** — 8/10/12/16, same board, shown side by side in section B.
- **URL line on/off** — same board/width/glyph set, shown side by side in section D; adds a fixed
  65 UTF-16 units (the placeholder URL plus a blank line).
- **Worst cases across the whole pool** — section C, `Bolt` (native mask 15×42, aspect 0.36, the
  tallest in the pool) vs `Fish` (up to 32 wide, aspect ~1.9, the widest).

## The finding that matters for the ruling

Both ceilings the red-team flagged as "unmeasured" (brief context, brand-13) are not just
unmeasured — they are **violated** by the current design, at every tested width:

| width | max picture rows (all 120 boards) | shape/day |
|---|---:|---|
| 8 | 22 | Bolt @ day 37 |
| 10 | 28 | Bolt @ day 37 |
| 12 | 34 | Bolt @ day 37 |
| 16 | 45 | Bolt @ day 37 |

`Bolt`'s native aspect ratio (0.36, i.e. nearly 3x taller than wide) means downsampling it to ANY
of the 4 candidate widths blows the assumed 16-row ceiling — even at width=8 (22 rows). This
repeats for other tall shapes in the pool (e.g. `Trophy`, aspect ~0.54) though less severely; full
per-shape numbers are in the dump's metrics table.

The 240-character ceiling is blown even more broadly:

| width | glyph set | max UTF-16 (no URL) | max UTF-16 (with URL) |
|---|---|---:|---:|
| 8 | `⬛/⬜` / `■/□` | 256 | 321 |
| 8 | `🟪/⬜` | 319 | 384 |
| 16 | `⬛/⬜` / `■/□` | 823 | 888 |
| 16 | `🟪/⬜` | 1040 | 1105 |

Even the SMALLEST candidate width (8), with NO URL, already exceeds 240 UTF-16 units in the worst
case (`Bolt`, 256). The header alone (4 lines: `Arrows · <date>` / shape / hearts / streak) is
roughly 55-70 characters before a single grid glyph is printed, so a 240-character budget only
holds for the most compact shapes at the smallest width — it is not a safe general assumption for
the whole `DAILY_POOL_V1` catalogue as currently defined.

## Decisions

- Read "for 5 fixed days and for every shape in `DAILY_POOL_V1`" as: since the brief also says the
  card is "built from `generateDaily(day).mask`" (the real, unforced draw), and a single day can
  only ever produce one shape, full pool coverage from the real function requires scanning forward
  and taking each shape's first N natural hits. I used N=5 (matching "5 fixed days") rather than
  forcing shapes through `generateDailyFromPool` with a singleton pool, so every board here is
  provably a board that could actually ship on some real day, not a synthetic substitute.
- Printed full card text only for each shape's FIRST occurrence (576 cards) to keep the dump
  readable; occurrences 2-5 contribute measurements only (all 2,880 rows of the metrics table), so
  the summary maxima reflect real day-to-day variance in the generator's cell-count target instead
  of a single sample.
- Hearts-left and day-streak are explicit script-picked placeholders (documented in-file), not a
  simulated play result, since nothing in this task plays a level.
- Chose the Play Store URL shape (using the project's real package id) as the one placeholder URL
  candidate rather than inventing an unrelated domain, so the length estimate is grounded in a URL
  this app could actually use.
- Produced the owner sheet as `.txt`, per the task's own allowance ("or a `.txt` if the cards are
  text-only") — every candidate here is plain text, and a PNG render would have introduced exactly
  the emoji-font/advance-width risk that's already flagged UNVERIFIED-DEVICE, for no evidentiary
  gain.

## Concerns

- The row-ceiling and character-ceiling violations above are real findings, not edge cases: `Bolt`
  is a normal member of `DAILY_POOL_V1` and will appear on real days. If the share feature is built
  with a naive "crop + downsample to a fixed width" approach, either the row/character ceiling
  assumptions need to be dropped, or the pool needs a per-shape aspect-ratio cap (e.g. clamping
  height at render time, independent of `DAILY_POOL_V1` itself, which is shared with the daily board
  and out of scope here), or the width needs to vary per shape's aspect ratio instead of being fixed.
  This is a design question for W4-13, not something this task decides.
  This is exactly the kind of concern the brief's own red-team flag (brand-13) anticipated; I am
  surfacing it rather than silently choosing a mitigation.
- The `🟪/⬜` UTF-16/code-point divergence is mechanically confirmed, but whether it causes a visibly
  broken layout in any real client is still open (UNVERIFIED-DEVICE, unchanged from the brief).
