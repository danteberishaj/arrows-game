## Key findings

- **Script determinism (EXECUTED, the acceptance criterion):** `npx tsx scripts/analysis/dead-band.ts
  --from 0 --to 500`, run twice, byte-identical stdout.
- **The same level (109, a 13x20 "Rectangle") is the worst level at all three geometries** in 0-500.
  At the capture geometry (360x780dp, adjusted/on-screen numbers): min slack/side 87.58dp, median
  147.30dp, max (level 109) **206.52dp**. Even the *best* sampled level never comes close to filling the
  viewport vertically, at any of the three geometries.
- **Camera-flag finding (the important one, found while capturing):** every test APK available to this
  task has `EXPO_PUBLIC_META_ZOOMED_CAMERA=1` baked in, a flag that defaults OFF in `src/featureFlags.ts`.
  `dead-band.ts` correctly models the **shipped default** (`!zoomed` branch); the real captures below can
  only show the **zoomed** branch, which fills more of the screen. Both numbers are reconciled in the doc
  against the same capture (206.52dp computed/default vs 149.7-150.0dp measured/zoomed-test-build) — I did
  not let the smaller, easier-to-photograph number stand in for the one that matters (what ships).
- **Real capture** (`emulator-5556`, level 109 seeded via `su sqlite3` `arrows_current_level`, 360x780dp,
  both themes): a large, visually obvious empty band above and below the arrows in both screenshots. I
  looked at both before building the mocks.
- **8 mock images** (4 options x 2 themes), each stamped "MOCK -- not rendered by the app", composited
  over the real captures with pixel boxes measured by a per-row colour-distance scan (not guessed).
  **One placement bug was found and fixed**: option C's first render put the new bottom band 18px below
  the *top* dead zone by mistake, overlapping the board's first arrow row; corrected to anchor off the
  bottom dead zone and re-rendered before finishing.

## Emulator collision with W2-09 (full writeup in the doc)

Another agent (W2-09) was independently driving `emulator-5556` from 16:02:03-16:02:04 (uninstalled
`arrows-testads-W4-11.apk`, installed its own `w209-off.apk`) — a dispatch error the controller has since
confirmed and corrected ("you have it exclusively until you report"). Both real captures for this task
were taken under `w209-off.apk`, not W4-11. I checked, rather than assumed, that this substitution could
not have changed what they show: `w209-off.apk`'s build record shows it is a JS-only repack hosted on
W4-11's own native build with an identical feature-flag set, and `git diff` between the two builds' commit
hashes for `src/ui/GameScreen.tsx` (read in full) touches only the W4-11 review-prompt logic and W3-05's
session-version parameter — no header JSX, no `<BoardView>` props. `src/ui/BoardView.tsx` and
`src/ui/boardCamera.ts` have zero diff between the two commits. The captures did not need to be redone.
**Installed APK as of this report: `w209-off.apk` (sha256 `3c454801…a22`).** `wm size`/`density` are reset
(native `1440x3120@560`, no override) and the three motion scales read back `1 1 1`, unchanged throughout.

One minor, disclosed emulator-state side effect: seeding `arrows_current_level=109` triggered the app's
own collection-folding logic, writing `arrows_shapes_seen_lo` / `arrows_shapes_through_level=109`; a
follow-up cleanup `DELETE` for those two keys was blocked by the harness's own auto-mode permission
classifier ("Irreversible Local Destruction") and not retried, per its own instruction to disclose instead
of finding a workaround. `arrows_current_level` and `arrows_dark_mode` (the two keys this task actually
needed) were removed.
