## Decisions

1. A shared singleton bridges per-level tallies in `GameScreen` to App's background
   `session_end`; the aggregator itself remains independently constructible and pure-testable.
2. The schema has no `simulated` field and F08 forbids a schema-version bump. Development fake-ad
   events therefore use an adjacent `[ads][simulated]` log tag instead of adding an event field.
3. `telemetryScreen` accepts future `daily`/`gallery` values now and maps them per F08 without
   widening the current App screen state ahead of those workstreams.
4. The PERF memory sink is bounded to one event and the direct-timer quiet window is 750 ms; both
   code values are marked `OWNER-PICKED STARTING VALUE`. PERF suppression keeps the sink empty.
5. Activity-background attempts did not unmount the React root. The deterministic PERF proof
   therefore logs from the game-subtree unmount reached through Home. Superseded root-unmount logs
   remain in the artifact directory and are not cited as proof.
6. The W0-04b blocked-tap cleanup path was not refactored. Telemetry emits immediately before the
   existing blocked visualization logic, leaving its staged cleanup timing intact.
7. `continuesUsed()` is called only after an earned reward exactly as required. Because the same
   brief also requires `end('out_of_hearts')` immediately on the accepted lost branch and makes an
   ended aggregator inert, the current out-of-hearts event is already final before a later
   continue can be earned. No second end/start or schema behavior was invented to resolve that
   upstream lifecycle tension.

## Fix round 1

### Outcome

- **DONE:** the controller's continued-level lifecycle now emits the original
  `level_end{outcome:'out_of_hearts'}` immediately, reactivates the same aggregation only after an
  earned continue, and emits a second terminal event for a later clear, loss, or abandonment.
- **DONE:** the requested level-0 blocked / miss / ghost classification and the full lose → earned
  continue → clear lifecycle were both observed through the real dev-build call sites on
  `emulator-5556`.
- This section supersedes Decision 7 and the continue-lifecycle concern above. The controller has
  now ruled that one continued level intentionally emits two `level_end` events.

### What changed

1. `src/telemetry/levelAggregator.ts` now models `idle`, `active`, and `resumable` explicitly.
   `end('out_of_hearts')` leaves the same level resumable after emitting its loss event. `resume()`
   accepts only that state, keeps the original start time and all counters, increments
   `continuesUsed`, and reactivates aggregation. A clear then increments `levelsCleared` normally.
   Calling `resume()` before a start or after a clear/abandon remains inert.
2. `src/ui/GameScreen.tsx` calls `resume()` only after `Ads.showRewarded('continue')` returns
   `earned === true`. The existing early return still leaves failed or unearned attempts on the lose
   panel without resuming aggregation.
3. `src/telemetry/__tests__/levelAggregator.test.ts` adds the required real-`BoardLogic`
   loss → resume → clear test and an invalid-resume invariant test.
4. `docs/telemetry-decision-rules.md` documents the lifecycle: a continued level emits two
   `level_end` events, its later terminal retains the earlier counters with `continuesUsed >= 1`,
   and consumers dedupe on `levelIndex + continuesUsed` within install/session instead of assuming
   one `level_end` per `level_start`.
