## What changed

`src/ui/adPacing.ts` (new, pure)
- `isInterstitialDue(finished, perInterstitial)` returns `finished >= perInterstitial`.
- `sanitizeCounter(raw: unknown)` returns 0 for anything that is not a finite number. Otherwise it truncates and clamps the value to at least 0.
- `afterDisplayed()` returns `0`.

`src/core/saveSystem.ts` (accessors only; `Keys` / `PersistenceKeys` untouched)
- `get finishedGames()` reads `Keys.finishedGames` (`arrows_finished_games`, P-01 row 10) with default `0`, as a non-negative integer.
- `setFinishedGames(n)` writes `n` as a non-negative integer.
- A private `nonNegativeInt` helper does the clamping. Core has no imports from `src/ui`, so the helper copies the numeric half of `sanitizeCounter` (concern 3).
- `resetProgress()` is unchanged. It does not delete the counter.

`src/ui/ads.tsx`
- The module variable `let finishedGames = 0` is gone. `finishedGames()` returns `sanitizeCounter(SaveSystem.finishedGames)`, and `markInterstitialDisplayed()` writes `afterDisplayed()`.
- `registerGameFinished()` now calls `SaveSystem.setFinishedGames(finishedGames() + 1)`.
- `showInterstitialIfDue()` checks `isInterstitialDue(finishedGames(), GAMES_PER_INTERSTITIAL)`.
- The native path no longer resets before `showAd()`. The interstitial listener's `onAdDisplayed` now calls `markInterstitialDisplayed()`. That is the only native reset.
- The release path with no native ad is unchanged: it returns and does not reset.
- `__DEV__` simulated path: `showFakeAd('interstitial', markInterstitialDisplayed)`. `FakeAdRequest` gains an optional `onDisplayed`. `AdHost` calls it in the `[req]` effect, after the modal has committed. If no host is mounted, `showFakeAd` resolves `false` and nothing resets.
- `GAMES_PER_INTERSTITIAL = 2` is unchanged. Its comment now says the value is inherited and was never measured. No new numbers were added.

Tests
- `src/ui/__tests__/adPacing.test.ts` (new, 23 tests):
  - The pure rules: due at exactly N and not at N-1; malformed, negative and non-integer raw values all sanitise to a non-negative integer.
  - `ads.tsx` as a release build over a fake LevelPlay SDK, with two fresh module loads (`jest.isolateModules`) over one backing map:
    - lose, then process death, then win makes `showAd` run (the original failure);
    - the counter is not reset before `showAd`, only by `onAdDisplayed`;
    - `onAdDisplayFailed`, a rejected `showAd` and "not ready" all keep the count, and the next attempt shows;
    - with no native SDK (init failed), nothing shows and the count is kept;
    - a corrupt negative stored value counts up from 0.
- `src/core/__tests__/saveSystem.test.ts`: six W0-05 cases were added, including "a counter written through one store is read back by a fresh store instance over the same backing map (process death)", corrupt-value reads, and "resetProgress does not touch the counter".
- `src/ui/__tests__/storage.test.ts`: one hydration case was added (a stored `'1'` reads back as `1` after `initSaveSystem()`). The exact-array assertion was not touched.

Not changed: `PersistenceKeys`, the exact-array test, `GameScreen.tsx` (which outcomes count), and `GAMES_PER_INTERSTITIAL`. The rejected items were not added: no loss interstitial, no cooldown, cap or grace, and no free hint.

## Concerns
1. **No gradle build: both capture APKs are JS repacks.** This is the same pipeline as W0-03 and W0-04: a release Hermes bundle over the gradle-built `da93dcd` base APK, debug-signed. W0-05 is JS-only and the native code has not changed since `da93dcd`, so the repack exercises the release JS path. The brief's "Release build" and "base APK with the same log patch" were not run literally, because patching the base APK without rebuilding it is impossible. The repack is the smallest change that makes that possible. W0-07's gradle artifact should repeat criterion 3 with its log-free substitute (an RKStorage dump after force-stop).
2. **The retry-on-every-Next-level trade-off the brief anticipated.** A display failure or rejected show now keeps the count, so every later "Next level" tries again until an ad displays. That is intended. Repeated `onAdDisplayFailed` would show up only in logcat, and nothing counts it. With real fill this has not been observed (UNVERIFIED-DEVICE).
3. **Small duplication.** `SaveSystem` clamps with its own `nonNegativeInt`, because `src/core` does not import `src/ui`. `ads.tsx` also passes the value through `adPacing.sanitizeCounter`. Both are tested. If a later task wants one definition, `sanitizeCounter` could move to core. I did not do that because the brief names `src/ui/adPacing.ts`.
4. **Brief line numbers have drifted** (for example `ads.tsx:255`, `GameScreen.tsx:123/148/160`). W0-01 to W0-04 changed these files. The described code matched, so nothing diverged.
5. **Release coupling (ruling I-23):** the W7-11 LevelPlay baseline export should come before any release that contains this change. That is the owner step inside W0-08. This task releases nothing.
6. **Test-strength note:** the first red run showed two wiring tests passing on the unfixed code (they checked only that the stored value was not reset, and the unfixed code never writes it). They were strengthened before implementation. Reviewers should re-run the red check: revert `src/ui/ads.tsx` to `80959cb` and expect 9 failing wiring tests.
