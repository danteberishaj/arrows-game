## Parity table (in the doc; 18 rows, file:line on both sides, each tagged READ or INFERRED, all "observe in W8-05")

Same on both sides (READ): header 10 tokens; duration 160..1000 ms; trail points 2..4098;
accepted token counts 10+2n / 12+2n / 13+2n; 2 concurrent slots; `tokens[3] == "1"`;
duplicate-id / bad-index ignored; motion-token ranges (`fadeStart` [0, 1), `launch` [0, 2]);
reduced motion (no travel, linear fade); motion-token travel curve (Swift's cubic Bezier is the
exact degree elevation of Kotlin's quadratic); ink change mid-exit.

Differences found:
1. **`endMs` (13+2n):** Kotlin validates it (1..durationMs, else the exit is dropped) and stops
   the exit early if the camera did not move; Swift ignores the value entirely.
2. **Start frame with motion tokens:** Kotlin starts one display frame back and draws in the
   mounting frame (POLISH-T12); Swift does not (about one frame, INFERRED).
3. **Travel with the flag OFF (10+2n):** Kotlin exact `k²`; Swift the `(0.11, 0, 0.5, 0)`
   approximation, although the exact Bezier `(1/3, 0, 2/3, 1/3)` is already in the file.
4. **Fade:** smoothstep vs `easeInEaseOut` (INFERRED small).
5. **Alpha:** per-paint alpha vs group opacity (INFERRED overlap difference).
6. **Clipping (new):** Swift sets `clipsToBounds = true` and sizes the exit container to `bounds`,
   while `META_EXIT_TO_SCREEN_EDGE` (not gated off for iOS in JS) relies on painting past the board
   rect, so an edge-running trail would be clipped on iOS (INFERRED).
7. **Props:** Kotlin has 9 (adds grid, gridStyle, markMask, markColor); Swift 5. Grid and marks are
   gated off on iOS in JS.
8. Dash direction: congruent modulo one period (INFERRED); never observed.
