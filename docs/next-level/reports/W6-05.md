## What I implemented

   `bucketOf(hi, lo, buckets?)`, and the `IdentityStore` interface production code (`SaveSystem`)
   and tests (a plain in-memory double) both satisfy structurally.
   - `ensureIdentity` fills in whichever half of the install id (`telInstallHi`/`telInstallLo`) is
     still 0, as an integer in `1..2^31-1` from an injected `random` (default `Math.random`), and

     `random`.

   `telInstallLo`/`setTelInstallLo`, `telSessionCount`/`setTelSessionCount` — reading/writing the

## Decisions

- **`IdentityStore` is a narrow structural interface, not a direct `IntStore`/`SaveSystem`
  reference.** The brief's acceptance criteria test against "a `MemoryStore`" the same way P-01's
  own tests use a local double rather than `saveSystem.ts`'s unexported internal `MemoryStore`. I
  read this as: identity.ts takes anything shaped like `{telInstallHi, telInstallLo,
  setTelInstallHi, setTelInstallLo, telSessionCount, setTelSessionCount}`; production passes the
  real `SaveSystem` (which has all six members after this task's accessor addition), tests pass a
  five-line class. This keeps identity.ts decoupled from `SaveSystem`'s full surface and matches
  "writes both through SaveSystem setters" in the brief (the setters it writes through are exactly
  `SaveSystem.setTelInstallHi`/`setTelInstallLo` at the call site in `App.tsx`).
- **`randomHalf` formula:** `Math.floor(random() * (2**31 - 1)) + 1`, giving exactly the
  `1..2^31-1` range the brief specifies, and never 0 regardless of what `random()` returns (0 or
  anything just under 1).
- **Partial state (one half already non-zero, one still 0) fills in only the missing half** rather
  than treating any-zero as "regenerate both." Not in the acceptance criteria; added a test for it
  (`fills in only the missing half when one is already set`) since it is the natural reading of
  "each half... when the stored value is 0" applied per-half, and it is the safer choice if a
  future bug ever zeroes one half without the other.
- **`bucketOf`'s `buckets` parameter defaults to `DEFAULT_BUCKETS` (100)** rather than being
  required, since nothing calls it yet (W6-06+ will) and a default keeps today's test/acceptance
  surface exact without forcing a caller to import the constant.
- **Did not wire `bucketOf` or the returned `{hi, lo}` into `telemetry.ts`'s envelope
  (`sessionIndex`/`bucket` are still hardcoded 0 there).** That wiring is explicitly W6-06's job
  per `telemetry.ts`'s own comment ("session tracking lands with W6-06") and the brief's file list
  for this task does not include `telemetry.ts`. Doing it here would be scope creep into another
  task's brief.
- **Optional emulator backup/restore run: not run.** `df -h /` showed 4.8Gi free, under the 5 GB
  native-build gate (Phase 2 controller note), and this task's code change needs no native build to
  exercise (JS + doc only) — the emulator step is explicitly optional in the brief and exists only
  to move the restore-keeps-the-id claim from INFERRED to EXECUTED. It stays INFERRED here (see
  Verification below), which is the state the brief says to leave it in "until it runs."

### Finding 1 — "Verification 2 overstates coverage" (fixed)

**The finding, verbatim gist:** `identity.test.ts` used a hand-written `MemoryStore implements
IdentityStore` double, so P-01's six SaveSystem accessors
(`src/core/saveSystem.ts:272-296` — `telInstallHi`/`setTelInstallHi`,
`telInstallLo`/`setTelInstallLo`, `telSessionCount`/`setTelSessionCount`) were never actually
called by any test in this task. The original report's Verification §2 line — "exercises
generation and persistence through the exact same `SaveSystem`-shaped setters... the app calls" —
claimed more than the test suite did: "same-shaped" is true of the double's method names, but
"the same... setters" implied the real accessors ran, and they didn't. The reviewer's own read is
correct: this was a coverage gap, not a live defect, because P-01's `storage.test.ts:260-261`
already round-trips `2^31-1` through hydration for these three keys, and the accessors themselves
are one-line pass-throughs to `nonNegativeInt(store.getInt/setInt(Keys.tel*, ...))` — the same
pattern as `finishedGames`/`rcKillBits` two accessor blocks above them, which is exercised.

**Fix — accepted, closed by adding real coverage rather than by only softening the report's
wording.** Added a new `describe('ensureIdentity + nextSessionIndex against the real SaveSystem', …)`
block to `src/telemetry/__tests__/identity.test.ts` (3 new tests, 8 → 11 in this file) that:
- imports the real, exported `SaveSystem` singleton and `IntStore` from `../../core/saveSystem`
  (not a double);
- calls `SaveSystem.useStore(new RecordingIntStore())` in `beforeEach` with a fresh in-memory
  `IntStore` (mirrors the pattern `src/core/__tests__/saveSystem.test.ts` already uses);
- calls `ensureIdentity(SaveSystem, ...)` and `nextSessionIndex(SaveSystem)` — the exact call
  shape `App.tsx` uses in production — and asserts the result by reading back through
  `SaveSystem.telInstallHi`/`telInstallLo`/`telSessionCount` (the real getters at
  `saveSystem.ts:272-296`), not just the function's return value;
- covers the same three properties as the original suite once each against the real accessors:
  fresh-store generation, "second call doesn't regenerate / doesn't call random", and
  `nextSessionIndex` returning 1, 2, 3, with the running total additionally asserted via
  `SaveSystem.telSessionCount` after each call.

This closes the actual regression-protection gap the finding named: if a future edit broke the
wiring between `identity.ts` and `SaveSystem`'s accessors (wrong `Keys.*`, a typo in a getter
name, `nonNegativeInt` swallowing a value), these three tests — not just `storage.test.ts`'s
key-list assertion — would fail on the accessor-usage path itself.

Did not change the original `MemoryStore`-based suite: those 8 tests are still the right place for
exhaustive edge cases (seeded randomness, `random` returning 0, partial-half fill) without needing
`SaveSystem.useStore()` housekeeping in every test; duplicating all 8 against the real singleton
would be redundant, not more rigorous. Also corrected the original report's Verification §2
wording below the diff line in this section rather than editing history above — the original
"GREEN"/"Acceptance criteria" sections above are left as they were EXECUTED at the time; the
overstated claim they contain is superseded by this section.
