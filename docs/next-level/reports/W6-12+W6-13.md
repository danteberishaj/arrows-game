## Decisions (routine judgment calls made without stopping to ask)

1. **W6-12, F36's uncomputable W1 sub-metric: dropped, not schema-extended.**
   The brief's own acceptance criterion offers exactly two resolutions —
   add a field to `events.ts` in the same PR, or drop the row. I dropped it.
   Reasoning: this batch's Files list for W6-12 is a single new document;
   adding an ordering/timestamp-per-tap field to `EventSchema` is a schema
   change with emission-site and schema-version implications for other,
   already-shipped tasks (W6-04/W6-05), and is a bigger change than "write
   decision rules." The row's other named metric (fraction of first-`app_open`
   installs reaching `level_end{cleared}` on level 0) already answers "does
   the tutorial teach" without needing tap order, so nothing about the
   underlying decision goes unmeasured — only the specific "before" framing
   is gone. If a future task adds an ordered tap log for an unrelated
   reason, this row should be revisited to use it.
2. **W6-12, install id as a join key, not an `EventSchema` field.** Rows 1
   and 4 need to group events "by install" to compute a fraction or a
   before/after comparison. `TelemetryEnvelope` deliberately excludes the
   install id (`events.ts:148-149`). I listed the install id as a separate
   "join key" note per row, explicitly not counted against the "only fields
   present in `events.ts`" criterion, rather than either (a) silently
   assuming a field that doesn't exist, or (b) refusing to write rows that
   need cross-event grouping at all. Same reasoning applied to W6-13's Data
   safety table, where the brief itself names "Device or other IDs for the
   install id" as a required row — so there I added it as the one explicit
   exception the brief itself calls for.
3. **W6-12, bands/thresholds are not chosen.** The brief's non-goal
   "Choosing thresholds on the owner's behalf" reads as: pick a starting
   sample size and window (both marked OWNER-PICKED, per the acceptance
   criteria), but do not pick the pass/fail cutoff that turns a measured
   number into a verdict. Every row's "action" cell reports the measured
   value(s) to the owner rather than computing a go/no-go itself.
4. **W6-13, retention number.** The brief asks for "retention, as an
   OWNER-PICKED STARTING VALUE" without naming one. I picked 180 days for
   raw events, marked explicitly as needing an owner yes, listed again as
   open question 1.
5. **W6-13, "Optional" column is "No" on every row.** There is no analytics
   opt-out UI in the app (W7-03 is out of scope for this task). Rather than
   guess at a nuanced per-row answer, I set every row to "No" and raised it
   as open question 2 — whether shipping without an opt-out is acceptable
   for this release, or whether W7-03 needs to land alongside W6-14/W6-15.
6. **W6-13, purpose column is "Analytics" uniformly.** All 39 fields belong
   to one channel with one purpose; a per-field purpose distinction (e.g.
   treating `error.*` as "App functionality" instead of "Analytics") looked
   like manufactured precision the brief didn't ask for, so I kept one
   value and let the category column (App activity vs App info and
   performance) carry the real distinction.

### 1–2. Row 4 (`docs/telemetry-decision-rules.md`): "sessionIndex ≥ 2" misread, cohort B anchor undefined

Both findings point at the same computation cell, so they were fixed together.

- **What changed:** Row 4's Computation cell no longer computes a return as
  "`sessionIndex` at least 2 higher, on a later calendar date." It now defines,
  precisely: the anchor date for cohort A is the calendar date (from
  `TelemetryEnvelope.ts`) of the install's first qualifying
  `level_end{mode:'daily', outcome:'cleared'}`; the anchor date for cohort B
  (which has no such event by definition) is the date of the install's first
  `level_end` of any kind in the window — so both cohorts anchor on "a
  session where the install actually played a level," not on app-open alone.
  A return is any event of any kind whose `ts` falls on a later calendar
  date than the anchor, within the look-forward window. This removes the
  unlabelled `2` entirely (no `sessionIndex` offset is computed at all), and
  fixes the undercount the reviewer identified: an install that clears the
  daily in session k and reopens once, the next day, in session k+1, is a
  `sessionIndex` delta of exactly 1 and is now correctly counted as
  returning.
  A new note was added directly above Row 4's table explaining why the
  brief's literal "`sessionIndex` ≥ 2 on later days" wording is read as
  informal shorthand for "at least one more cold start on a later day," not
  as a literal offset-of-2 rule, and why the literal reading breaks both the
  "no unlabelled number" acceptance criterion and the return-fraction math.
  The "What it cannot tell" cell was rewritten to match: it no longer treats
  the calendar-date check as an addendum to a `sessionIndex`-offset rule: the
  `ts`-based check is now the whole rule, stated as such.
- **Covering check (this is a doc, not code — see brief's own Verification
  §2, "grep each field name," the doc-appropriate equivalent of a test):**
  EXECUTED — re-read the new Computation cell against the two failure cases
  named in the finding: (a) a player who returns once, the next calendar
  day → old rule: NOT counted (session delta 1 < 2, finding's exact bug);
  new rule: IS counted (later `ts` calendar date exists). (b) cohort B's
  anchor: old rule left it as prose ("a matching reference session"), not
  computable; new rule names an exact field-level definition (first
  `level_end` of any kind in the window) that a query can execute without
  further judgment calls.
- **File:** `docs/telemetry-decision-rules.md:108-130` (Row 4 note +
