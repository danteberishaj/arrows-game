Implementer report, 2026-09-26. BASE = `e9e9950` (branch `next-level`). Requirements:
`.superpowers/sdd/TASKS/task-W4-11-brief.md` (with its binding controller amendments F12, F23 and F33),

## Outcome

With `META_REVIEW_PROMPT` on, a perfect campaign or daily clear can ask the OS for a store review (Play In-App Review /
StoreKit, through `expo-store-review`). Nothing of the app's own is shown: no button, no question, no copy, no reward.

- **Decision** (`src/core/reviewPolicy.ts`, pure): `shouldRequestReview({ perfect, assisted, totalSolved, today,
  count, lastDay, askedThisSession })`. Yes only for a perfect, non-assisted clear with ≥ 25 solves, fewer than 3 asks
  ever, the last ask ≥ 90 days ago (or never) and not after today, and no ask yet in this app process. Corrupt stored
  values fail closed. `reviewDeclineReason` returns the first gate that says no (used for the diagnostic line).
- **When** (`src/ui/reviewPrompt.ts`, `GameScreen`): `REVIEW_DWELL_MS = 2000` ms after the won phase commits, i.e.
  after the 180 ms win entrance (and its 250 ms backstop) and after all three stars have started (590 ms). Next / Done,
  leaving, unmounting or the app going to the background before then cancels it: no ask, nothing recorded. It is also
  skipped when this campaign panel's Next would show an interstitial. See "When it fires" below.
- **Bookkeeping**: after `isAvailableAsync()` says yes and before `requestReview()`, `arrows_review_last_day = today`
  and `arrows_review_count + 1`, whatever the OS then shows. Not written while persistence is unhealthy (then no ask).
- **Fire and forget**: the panel never awaits the flow. Next / Done wait for an in-flight flow, at most
  `REVIEW_FLOW_WAIT_MAX_MS = 3000` ms, so the card can never land over the next board or an ad (Play's integration
  guide asks exactly this).
- **Flag OFF** (default): no timer, no AppState listener, `expo-store-review` is never loaded or called, the two keys
  are never touched; Next and Done run with no added `await` (identical to BASE; tests below).

## When it fires, relative to the win panel, and why

Timeline of a clear (constants in `gameSessionLifecycle.ts`, `overlayPresence.ts`, `GameScreen.tsx` Stars):

| t (ms after the won commit) | what happens |
|---|---|
| −450 | last arrow leaves; board locked (`terminalPending`) |
| 0 | won phase commits: panel mounts, scrim + panel enter over 180 ms (W2-05; backstop settle ≤ 250) |
| 250 / 420 / 590 | stars 1 / 2 / 3 start their springs |
| **2000** | **the ask fires** (only if the player is still on the panel and the app is in the foreground) |

Why this moment:

- **Never during the entrance**: 2000 ms is 1820 ms after the 180 ms entrance and 1750 ms after its latest backstop
  settle, and 1410 ms after the last star starts (`reviewPrompt.test.ts` pins both inequalities from the constants).
- **A natural break, not an interruption**: the board is already locked behind the panel, so no gameplay input can be
  blocked; Apple's HIG asks for a natural stopping point, and Apple's own sample waits about 2 s on its completed scene
  before asking. `REVIEW_DWELL_MS = 2000` is taken from that sample — an OWNER-PICKED STARTING VALUE.
- **A player who moves on is never asked**: Next / Done within 2 s cancels it, so the prompt only reaches players who
  pause on the panel, and nothing is spent.
- **Never before or over an ad**: a campaign panel whose Next would show an interstitial (`Ads.interstitialDue`) never
  asks; Next's interstitial and W2-04's scrim can never start under an in-flight flow because Next first waits for the
  flow (Play: finish the review flow before continuing, e.g. advancing to the next level); Next / Done cancel a pending
  ask; and the ask is skipped while `adBusy`. A daily has no interstitial.
- **Measured on the emulator** (`device/accept-on-level12-second/star-motion.txt`, EXECUTED): panel first frame
  14:33:13.119, ask 14:33:15.089 = mount + 1.97 s. The stars' spring (mass 4 by Reanimated 4 default, damping 11,
  stiffness 260) still wobbles then: frames with any star-row change are 30/30 in [+1.5, +2.0) s and 31/31 in
  [+2.0, +2.5) s, falling to 7/30 in [+3.5, +4.0) s; the last change is at +4.2 s. So the ask lands after the entrance
  and the pop-in but inside the stars' low-amplitude tail. On this emulator nothing appears (see below), so nothing
  covers it; on a device the OS card would arrive after Play's own IPC time (UNVERIFIED-DEVICE). If the owner wants
  the ask strictly after all panel motion, `REVIEW_DWELL_MS ≈ 4300` does that on this measurement (fewer players
  would still be on the panel).

## Store rules this relies on (read 2026-09-26; copies under `artifacts/W4-11/docs/`)

Paraphrased; the saved copies hold the exact text.

|---|---|---|
| Google Play, *In-App Reviews API* overview — https://developer.android.com/guide/playcore/in-app-review (updated 2026-01-30) | Ask only after the player has used the app enough to give useful feedback; do not prompt excessively. | `REVIEW_MIN_SOLVES = 25`, lifetime 3, 90-day gap, once per process |
| same | Ask no question before or while the card shows — neither opinion ("do you like…") nor predictive ("would you rate 5…"). | no pre-gate at all; `storePolicyGuard.test.ts` forbids the wording in `src/` |

| Google Play, *Integrate in-app reviews (Kotlin or Java)* — https://developer.android.com/guide/playcore/in-app-review/kotlin-java (updated 2026-09-16) | Wait until the review flow completes before continuing the normal flow (their example: advancing to the next level). The API does not say whether a card was shown or a review left; on error, do not tell the player or change the flow. | `waitForReviewFlow` (bounded 3 s) before Next / Done; `requestStoreReview` swallows and logs errors |
| Google Play, *Test in-app reviews* — https://developer.android.com/guide/playcore/in-app-review/test | The flow needs a Play-distributed install (internal test track / internal app sharing) and a signed-in account that has the app in its library; a sideloaded Play Store is a known cause of no dialog. | why the emulator shows no card (UNVERIFIED-DEVICE) |
| Google Play policy *Ratings, Reviews, and Installs* — https://support.google.com/googleplay/android-developer/answer/9898684 | No incentivised ratings, no rewards for ratings, no deceptive or forced rating pop-ups. | no reward, no copy, the OS card only |
| Apple HIG *Ratings and reviews* — https://developer.apple.com/design/human-interface-guidelines/ratings-and-reviews | Ask after demonstrated engagement (e.g. a completed level), never at first launch or during onboarding; do not interrupt play — use a natural break; do not pester. The system shows the prompt at most 3 times per app per 365 days. | perfect clear, 25 solves, not assisted (FTUE), win panel after a 2 s dwell |
| Apple *Requesting App Store reviews* — https://developer.apple.com/documentation/storekit/requesting-app-store-reviews | At most 3 prompts per 365 days; do not ask as the result of a user action; the sample waits on its completion scene for a couple of seconds before asking. | `REVIEW_DWELL_MS = 2000` (from the sample), no button |
| Apple *App Review Guidelines* 5.6.1 and the introduction — https://developer.apple.com/app-store/review/guidelines/ | Use the provided API; custom review prompts are disallowed; paid, incentivised, filtered or fake feedback is grounds for expulsion. | expo-store-review → StoreKit only; no filtering on sentiment |
| Expo SDK 57 StoreReview — https://docs.expo.dev/versions/v57.0.0/sdk/storereview/ | API: `isAvailableAsync(): Promise<boolean>`, `requestReview(): Promise<void>`; do not call it from a button; do not ask questions before or during the card. | exact names used; see the Android note below |

**Android note (read from the installed source, not the docs).** The v57 docs say `isAvailableAsync()` resolves true
on Android 5.0+. The installed `expo-store-review` 57.0.3 (`android/.../StoreReviewModule.kt`) actually returns whether
the `com.android.vending` package exists. Its `requestReview()` resolves only after Play's `launchReviewFlow`
completes, and rejects if either Play task fails. Behaviour here does not depend on the difference: a false answer
means no request and no bookkeeping.

## Persistence and wipe risk

- **Keys.** Only `arrows_review_count` and `arrows_review_last_day` (P-01 rows 18-19, already registered and hydrated
  by `storage.ts`) are written, both through new named accessors in `saveSystem.ts`. No key was added, renamed or
  removed. `PersistenceKeys`, the exact-array assertion in `storage.test.ts`, `SCHEMA_VERSION` and `migrate()` are
  untouched.
- **Migration.** None needed. An absent key reads 0, which means "never asked" (P-01 default). Existing saves keep
  every value.
- **Wipe risk: none.**
  - The new code never deletes or resets any key.
  - `recordReviewRequest` writes only these two keys, and only while `persistenceHealthy` is true, so a failed
    hydrate cannot overwrite a real count with one derived from defaults.
  - `resetProgress()` does not touch them (test), so a progress reset cannot re-open the three lifetime asks.
  - Corrupt values (negative, fractional, NaN) make the policy fail closed (no ask) and are never rewritten by a
    read.
  - An Auto Backup restore carries the count, and a restored `lastDay` in the future suppresses the ask (P-01 row 19).

## Decisions

1. **The dwell (`REVIEW_DWELL_MS = 2000`) and its cancel rules.** The brief says "when the phase commits to 'won'";
   the controller forbids the entrance and asked for an exact, justified moment. See "When it fires". A player who
   leaves the panel within 2 s is not asked, and nothing is recorded for that clear.
2. **`isAvailableAsync()` false → no bookkeeping, but the session is marked asked.** No OS call was made, so no quota
   was spent. The platform answer cannot change within a process.
3. **`Ads.interstitialDue` (new read-only getter in `ads.tsx`, outside the brief's file list).** It is the only way
   to keep the ask off a panel whose Next shows an interstitial ("never before an ad") without guessing the pacing in
   GameScreen. It has no side effect, and every existing Ads mock returns `undefined` for it, which reads as "not due".
4. **Next / Done wait for an in-flight flow, bounded by `REVIEW_FLOW_WAIT_MAX_MS = 3000`.** Play asks for this.
   Without a bound, a store service that never answers would strand the player on the panel. The trade-off: after
   3 s a late card could still land over the next board (it cannot land over an ad, because no ad is due). With the
   flag off, and whenever no flow is in flight, no `await` is added, so Next and Done run as in BASE.
5. **The session flag is per app process** (`reviewSession` in `reviewPrompt.ts`), so leaving to the menu and coming
   back is the same session (test).
6. **`expo-store-review` is `require`d lazily on first use.** Flag-OFF builds bundle it (Metro resolves it
   statically; 3 `ExpoStoreReview` refs in the OFF bundle) but never evaluate it.
7. **`reviewDeclineReason`** is added next to the brief's `shouldRequestReview`, so the diagnostic line can say which
   gate declined. `shouldRequestReview` is defined as "no reason".
8. **`persistence_unhealthy` and `interstitial_due`** are GameScreen guards, not policy inputs, because the brief
   fixes the policy's signature.
9. **Handback build = the controller's recipe** (`build-final.sh testads` plus the four extra flags, so
   `META_ZOOMED_CAMERA` is on and `CAPTURE_DIAG` is off). All captures and perf used JS repacks over that same gradle
   native with the fit camera and `CAPTURE_DIAG` on.
10. **`contrastAudit.ts`**: only the line numbers of its test-checked sites moved, re-pointed with a difflib map from
    BASE (the W4-07 precedent).

## Concerns

1. **The ask lands inside the stars' low-amplitude tail.** Measured on the emulator, the stars (Reanimated 4's
   default mass 4) still move at +2.0 s: 31/31 frames change in [+2.0, +2.5) s, and the last change is at +4.2 s. It
   lands after the entrance and all pop-ins, but not after all motion. Owner call: keep 2000 (Apple's sample value),
   or use ~4300 for "fully still", which fewer players will wait for.
2. **UNVERIFIED-DEVICE: whether Play's card appears, and its timing and cost.** This emulator's Play Store is a
   non-functional stub (versionName 1.8, no account, the review service is not found), and the app is sideloaded. A
   real check needs an internal-test-track or internal-app-sharing install on a physical device with a signed-in
   tester account. iOS is not verified (BLOCKED-ON-DISK).
3. **One perf run (on5-1) saw 3 arrows removed before any scripted board tap.** The cause is unknown; only
   emulator-5556 was attached and no other adb input client was visible. The driver's readiness guard aborted it and
   it is excluded. If an outside actor touched the emulator, other runs could have been disturbed without such a
   visible sign; every analysed run passed the per-batch "N left" checks.
4. **Every `REVIEW_*` number is an OWNER-PICKED STARTING VALUE**: 25 solves, 3 lifetime, 90 days, 2000 ms dwell,
   3000 ms wait. `REVIEW_MIN_SOLVES` is to be re-derived from W6 data.
5. **A capture-build mistake was caught before install.** The first ON repack was built with the flag set passed as
   one zsh word, so `EXPO_PUBLIC_ADMOB_TEST_ADS` was not `1`. Its bundle proof showed the owner's units present, so it
   was deleted and never installed (`apk/rejected/README.txt`). All later builds passed the flags as a bash array and
   were proven with owner units 0/0 (ASCII and UTF-16LE) and TestIds present.
6. **The gradle `--no-daemon` JVM did not exit** for ~24 min after `BUILD SUCCESSFUL`. Its three processes (the
   wrapper, GradleMain and the Kotlin compile daemon, all children of this build) were stopped with SIGTERM after the
   APK was written. Free disk is now 3.9 GiB (9.0 before the build, 6.0 after the repacks, 3.9 at the end with no
   build of mine running), so the next native build is under the 5 GB gate.
