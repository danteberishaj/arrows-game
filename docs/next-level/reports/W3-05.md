## Migration and wipe risk

- The key is one additive int, `arrows_gen_switch_level`, P-01 row 20. It was already registered and hydrated
  by P-01.
- No existing key is read differently, rewritten or removed. `SCHEMA_VERSION` is not bumped.
- With `GEN_V2_ENABLED = false` (as shipped), the key is never written: EXECUTED, "the shipped flag (OFF) writes
  nothing".
- When the flag is ON, the key is written once, only after a healthy hydrate, and never over a present value.
  That includes a corrupt one.
- If the key is lost while `arrows_current_level` survives, the next flag-ON boot reclassifies the install as
  existing at `current+1`. At worst one board (the current index) is re-dealt as v1 once. No progress is lost.
- INFERENCE, not tested: Android Auto Backup restores the AsyncStorage database as a whole, so the switch level
  and current level restore together. UNVERIFIED-DEVICE.
- The store stays int-only.
- `resetProgress()` keeps the key. Whether a reset should clear it is part of the owner's reset-set decision
  (W1-11 question 5).
- After a reset, replayed levels below the switch are still dealt, and folded, as v1, so the collection stays
  consistent with the boards. This answers the question the W4-07 report left for W3-05.

## Decisions

1. **Absent and corrupt values are told apart through P-01's sentinel.** The brief says to stamp "if
   `genSwitchLevel === null`", but also that a stored -5 "reads as null … and nothing rewrites it". Those two
   rules conflict.
   - I follow P-01 row 20 exactly. `getInt(key, -1)`, where -1 means "not stamped", is the only stampable state;
     that is `genSwitchLevelStamped === false`.
   - Every other negative or non-integer value reads as null (so the resolver yields v1) and is never rewritten.
   - A literal stored -1 is therefore indistinguishable from absent and would be stamped. That is P-01's defined
     encoding, and nothing can write -1, because `setGenSwitchLevel` refuses negatives.
   - M3 proves the brief's literal condition would rewrite -5.
2. **The health check is enforced twice.** Both `stampGenSwitchLevel` and `setGenSwitchLevel` (which returns
   false, like W4-11's `recordReviewRequest`) check it. M1a shows either gate alone holds.
3. **The classification is a pure core helper taking the save as a parameter** (ruling F37: `App.tsx` cannot be
   imported by node jest). `App.tsx` only calls it. An App source-order test guards the placement: after
   `.then(`, before `setReady(true)`, and never in `.catch`. That guard is a source check, not runtime.
4. **The fold-routing test is a new file**, `saveSystem.genVersion.test.ts`.
   - It uses module mocks: `GEN_V2_ENABLED` is forced ON, and a spy wraps the real `shapeNameForLevel`.
   - This is needed because v2 content equals v1, so only the version *argument* can be observed.
   - Keeping it in its own file stops the forced flag leaking into `saveSystem.test.ts`.
5. **`createSoakPlan` also gained an optional `version = 1`**, so `createLevelPlan`'s parameter is reachable. The
   soak JSON shape and the CLI are unchanged.
6. **`campaignShapeName` reads the switch level on every level.** It costs one Map lookup. Node timing of a
   12000-level `syncCollection` (EXECUTED, 7 reps × 2 alternating runs): BASE median 27.1 ms against W3-05
   27.1–27.2 ms, both 2.26 µs per level. Hermes is not measured.
