## Decisions

1. **Opacity by overlay builds, not an env parse**: the player code has one constant, like every other W5 value.
2. **The tile is one 256 px file (no @2x/@3x variants).** Measured on the emulator: it repeats every 256 DEVICE px
   (one grain pixel = one device pixel). A coarser grain would be a taste question for the owner.
3. **No test under `src` names the asset** (the grep gate).

## Concerns

1. The resource routing in `repack514.sh` is a capture-build workaround forced by the disk (no gradle build possible);
   a gradle build packages `drawable-mdpi/assets_images_grain.png` itself. The routed file sits in all five density
   folders, so its tile size may differ from a gradle build's mdpi-only file: UNVERIFIED until a gradle build (the
   measured 256-device-px period is this routing's).
3. **The first implementation was wrong on the device** (one tile in the corner) while its jest tests passed; fixed
   and re-captured (above). The jest test now pins the size, but only a capture proves the layer covers the screen.
2. UNVERIFIED-DEVICE: banding and visibility on an OLED phone at low brightness (the brief's stated use case).

## Device results (EXECUTED)

### A defect found on the emulator and fixed (runtime truth, not the test)

The first ON capture (0.08) showed the grain in ONE 896x896 device-px square in the top-left corner and plain paper
elsewhere (`cap/superseded-no-size/0.08-day-menu.png`): RN gives an `Image` its static source's size (256x256 dp) as a
default width/height, which wins over `absoluteFill`'s left/right/top/bottom. Fix: `width: '100%', height: '100%'`
(`PAPER_TEXTURE_FILL`); the test now pins them. After the fix the grain covers the whole menu, and its luminance
autocorrelation along x has exact peaks (1.000) at lags 256, 512, 768 device px: **the tile repeats every 256 DEVICE
px** (73 dp), not every 256 dp (Decision 2 resolved). The OFF / ON builds and captures were redone on the fixed code.

### Frame cost: the brief's A/B/A (EXECUTED; `perf/ana514.md`, `perf/ana514.json`, `perf/position-check.txt`)

- 10 rounds of OFF / ON (0.08) / OFF, each leg: install -r (sha logged, `perf/run-log.txt`), seeded Daylight composed
  menu, scales 1/1/1 read back, cold launch, 4 s, `gfxinfo reset`, 8 framestats dumps 1.5 s apart, de-duplicated.
  Host load 6.5–14.

  OFF2 7315 / 7464 (windows 12.3–12.9 s each, so ~740 expected per run; 97.7–98.0 % present; the rest are single

- **Verdict: no difference smaller than the A/A is reported, and the A/A is large.** The emulator's RenderThread flips
  between a fast (RT median < 8 ms) and a slow mode per run, and the flip depends on the LEG POSITION, not the build:
  fast in 2/10 first legs (OFF), 2/10 second legs (ON), 6/10 third legs (OFF again). Comparing ON with the adjacent
  OFF leg before it (same position disadvantage): RT median −0.52 ms, total median +0.44 ms, janky −3.7 /s (medians
  of 10 paired rounds; ranges ±6–17). So the menu frames with the grain are not measurably different from without it on
  this host; a cost smaller than ~10 ms RT median (the A/A) cannot be excluded here. INFERRED: one full-screen tinted
  bitmap-shader quad under a static tree; the pill's per-frame animation does not invalidate the Image's display list.
