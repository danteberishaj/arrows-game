## The brief's premise, updated for POLISH-T10 (read before the numbers)

The brief computes the empty-board time as 450 − `exitTrailDurationMs` (180..320 ms). Since POLISH-T10, with
`META_EXIT_TO_SCREEN_EDGE` on (every test build), an exit's CLOCK is not what the eye sees: the arrow launches, leaves
the screen by motion at `exitOnScreenMs` (88..185 ms), and the rest of the clock (up to 1000 ms) runs off screen until
`endMs`. Scheduling the panel at `exitDurationMs + hold` would have added up to ~800 ms of invisible clock to the
hold. So the time this task passes is the **visible** time: `planExit(...).visibleMs` = the clock at which the tail cap
and its anti-aliased edge cross the visible edge (board-edge exits, flag OFF or reduced motion: `durationMs`, where
the fade ends). Measured over every arrow of levels 0..39 as if it were the last (`scripts/visrange.ts`,
`visrange-L0-39.txt`): **90..187 ms at fit (median 139)**, so today's flat 450 ms leaves **263..360 ms** of empty board.

## Decisions

1. **`exitVisibleMs`, not the exit's clock** (the premise section): the brief's `exitDurationMs` parameter name is kept
   in the prop's doc comment; the value is `planExit(...).visibleMs`.
2. **The factor stretches the whole exit clock including `endMs`** (`finalExitPlan` in `exitToScreenEdge.ts`, not in the
   brief's Files): applying `finalExitDurationMs` to `durationMs` alone would stop a slowed exit at the old `endMs`, with
   the arrow still on screen.
3. **Both won branches use the new delay** (the campaign / daily panel and the tutorial hand-off): both schedule "the
   board is empty -> what comes next" with the same constant today.
4. **`onRemoved`'s second argument is required** (ruling F07): all 13 one-argument calls in 11 test suites were updated
   mechanically to `(x, 0)`; W6-11's telemetry suite runs OFF and ON.
5. **Capture builds use the fit camera** (`META_ZOOMED_CAMERA` unset) and the clears are driven from a registered camera;
   the short / long contrast comes from two solve orders of the same level at fit (both 6- and 1-cell arrows exist) rather
   than a zoomed dense board: the visible-time range at fit (90..187 ms) already spans the whole POLISH-T10 band.
6. **Candidates were built as release repacks with the constants edited** (not a `__DEV__` Metro reload, which would need
   a debug gradle build): each candidate is the real release timing.

## Concerns

1. **Acceptance 7 is not run** (BLOCKED above). It needs either a profileable gradle host (≥ 5 GB free) or the
   controller's own harness host.
2. **Emulator noise:** 7 of 30 hold runs were excluded for stalls or a missed exit start under host load 5–16 (listed in
   `gates/hold-table.txt`); the decision rests on medians of 2–5 valid runs per cell. The candidate rows are single runs.
3. The `visibleMs` of a screen-edge exit assumes the camera does not move during the exit (as POLISH-T10's `endMs` does);
   a pan during the last exit would show the arrow for longer than the timer assumed (the panel would then appear with
   the arrow still leaving). INFERRED; not captured.
4. **UNVERIFIED-DEVICE:** whether the hold reads as a beat on a phone (brief item); iOS: the Swift parser's band is read,
   not run.
