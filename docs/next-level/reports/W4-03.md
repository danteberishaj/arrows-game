Implementer report. Raw command output: `artifacts/W4-03/verification.md` (gitignored).

## Outcome

`generateDaily(day)` exists as pure core: its own seed namespace, its own versioned 24-shape pool,
Normal config, no persistence, no UI, nothing calling it. The campaign generator is byte-for-byte
unchanged — proven against the pre-extraction commit over 1000 levels, not just by the committed
300-level fingerprint.

### Disproof attempt on my own verdict

The verdict at risk is "the extraction is output-inert". The specific way it could be wrong: the
committed fingerprint only covers levels 0..299, and the five golden checksums sample five indices —
a divergence that only appears on, say, a rarely-drawn SuperHard shape past level 300 would pass
every committed test. I attacked it by recomputing the whole-board fingerprint over levels 0..999
against the archived pre-extraction generator in a separate process (evidence 3). Both sides print
`916c6a47`. What survives: the claim is verified over the first 1000 campaign levels, and the
mechanism (a pure code move that hands the same `rng` object on, with `ShapeLibrary.pick` still the
first draw) makes a divergence past level 1000 implausible rather than impossible — since the seed,
not the index, is the only input downstream of the pick, and seeds beyond 1000 are drawn from the
same 32-bit image.

## Decisions

1. **`seed()` is now exported** from `levelGenerator.ts` (and `src/core/index.ts`). The brief
   requires the namespace test to derive both sides "from the live functions"; it was module-local.
   Additive, no behavior change.
2. **`generateDailyFromPool(day, pool)` was added** and `generateDaily` delegates to it. The brief
   wants the analysis script to report *both* candidate pools through real code; without this the
   script would have had to copy the pipeline, which is exactly the kind of copy that drifts.
   Production code and `DAILY_VERSIONS` are the only way a pool reaches a player.
3. **`buildFromShape` lives on the `LevelGenerator` object** rather than as a free function, matching
   `fillMask` next to it, and `generate` calls it as `LevelGenerator.buildFromShape` so the existing
   `LevelGenerator.fillMask` self-reference style is preserved.
4. **No feature flag.** The brief says none at this layer and the owner ruling binds *player-visible*
   features; nothing calls `generateDaily`, so there is no player-visible surface. W4-06 is the
   flagged consumer. `npx tsc --noEmit` and a `grep` over `src/ui` confirm no import outside tests.
5. **The daily serialization used for the golden checksums** includes `shapeName`, rows, cols,
   `arrowCount`, `hearts`, `difficulty` and every arrow line — wider than the campaign goldens
   (arrow lines only), because a daily's config is part of what a player gets on that day.
6. **Headroom values** (median ±6, p90 ±8, repeats +4) are drift tolerance, not measurements, and are
   labelled `// OWNER-PICKED STARTING VALUE` in the test next to the measured value each brackets.
7. **`levelGenerator.test.ts` was deliberately left unedited** (see "Changed files").
8. **No emulator was used.** This task is pure core logic and the brief asks for no device evidence;
   `emulator-5556` was left booted and untouched; the only `adb` command run was the read-only
   `adb -s emulator-5556 get-state` → `device`. No build, no install, no `df -h /` needed.

## Concerns

1. **The pool choice is taste, and the numbers cannot settle it.** The 24- and 26-shape pools are
   statistically indistinguishable (evidence 11), so excluding `Square` and `Rectangle` is purely a
   "the one shared board should be a picture" judgment. It ships as the owner-picked recommendation
   and needs an eyeball at W4-06's flag acceptance, not a re-measurement.
2. **Thin silhouettes inherit W3's 46-row clamp problem.** The measured max grid dimension is 46 for
   both pools, i.e. some dailies (Bolt in particular) hit the clamp exactly as campaign levels do.
   The daily can only pick up W3's fix through a future `DAILY_VERSIONS` entry, by design — past
   days must not change. Whoever lands W3's fix must decide, deliberately, whether to append an
   entry.
3. **Day numbering is not pinned by this task.** `generateDaily` takes a day number and nothing
   more; which day number "today" is comes from `SaveSystem.today()` at the W4-06 call site. A
   consumer that passes a different day unit (UTC vs local) silently deals a different board. That
   is W4-06's contract to get right.
4. **The distribution test costs ~14 s** of the core suite's runtime (3650 generated boards). It is
   the only way to assert the shipped band from live code rather than a copied constant, but it is
   the slowest test in the repo; if suite time becomes a problem, the honest fix is to narrow the
   window in both the test and the measurement note together, never to delete the assertion.
