## A. "Follow phone" theme

### The "brand-new player" rule (`src/ui/themeFollow.ts` `isBrandNewPlayer`)

Brand new = `currentLevel === 0` AND `totalSolved === 0` (counts daily clears too) AND `ftueStage === 0` AND
`arrows_dark_mode` absent (never written; the theme toggle is its only writer). Every number must be exactly 0; a
negative, fractional or non-finite value is an unknown save and keeps its stored theme. Brand new -> stamp 1 (follow
the phone); anything else -> stamp 0 (keep `arrows_dark_mode`).

Stamp rules (`stampThemeFollowsSystem`): only with the flag on, only while `SaveSystem.persistenceHealthy`, only when
the key holds no value at all (`getInt(key, -1) === -1`); a stamp is permanent. It runs in App's hydration `.then`
right after `stampGenSwitchLevel` and before `setReady(true)`, so the first themed frame after hydration already has
the right theme (the pre-ready blank frame is light, exactly as today).

### Behaviour with the flag on
- Following: `dark = Appearance.getColorScheme() === 'dark'` (null / unknown = light). Live updates through
  `Appearance.addChangeListener`; on AppState `active` it re-reads, covering a change made while backgrounded. These
  swaps call `setDark` directly: no scrim (the OS animated its own change).
- Menu sun/moon toggle: still flips to the opposite of what is shown (W2-08 scrim and reduced motion unchanged:
  `useThemeToggle` is untouched), writes `arrows_dark_mode`, and writes follow = 0 at the tap.
- Settings "Match phone theme" switch (state = the key): ON writes 1 and the effect applies the phone's scheme at
  once; OFF writes the currently shown theme to `arrows_dark_mode`, then 0, so nothing flips.
- StatusBar: App's `<StatusBar style>` follows `dark` as before; the sheet re-applies `StatusBar.setBarStyle` when
  `dark` changes while it is open (flag ON only; first render left to `onShow` as before).

### Migration / wipe note (required)
- Additive int key, P-01 row 30, appended to `Keys` (so it is hydrated by the one `multiGet`). No existing key is
  read differently, rewritten or deleted; `SCHEMA_VERSION` stays 1; `migrate()` untouched. `resetProgress()` does
  not delete it (a preference; reset lock test extended).
- Flag OFF (shipped default): the key is never written. It IS in the hydrate key list (one more key name in the boot
  `multiGet`; an absent key returns null and nothing is cached), and no getter of it is called. See Concerns 1.
- Downgrade to a build without the key: the key is not in that build's registry, so it is not hydrated and nothing
  reads it; the theme there is `arrows_dark_mode`. If the player was following the phone, `arrows_dark_mode` holds
  whatever it last held (absent = light), so the downgraded build may show a different theme from the one the phone
  had. No progress effect.
- Android Auto Backup restore onto another phone: the key travels with `arrows_dark_mode`. 1 -> the app keeps
  following, now the NEW phone's scheme; 0 -> the stored theme. The stamp is never re-run (key present). No progress
  effect. (INFERRED, not tested on device: Auto Backup restores the AsyncStorage database as a whole, as noted for
  row 20.)
- A failed hydrate (unhealthy persistence): no stamp, the theme is the in-memory default (light), exactly as today.

## Decisions
1. The key lives in `Keys` (P-01 amendment, as the brief says), so it is in the boot `multiGet` even with the flag
   off; it is never written and never read through a getter there (Concerns 1).
2. Stored value semantics: getter is `=== 1`; absent / 0 / corrupt = not following; "stamped" = any stored value.
3. Brand-new rule as above, with the exact-zero requirement for unknown saves.

## Lessons for the controller (not written to docs/engineering-lessons.md, per the brief)
- GLOBAL.md tells implementers to clear Metro with `npx expo export:embed --clear`; in this Expo version that fails
  with `CommandError: Unknown arguments: --clear`. The flag is `--reset-cache` (EXECUTED, 2026-10-13).
- The repo can be without `node_modules` (2026-10-13: absent; `npx tsc` then fetched the unrelated `tsc@2.0.4`
  package and printed "This is not the tsc command you are looking for"). Check `ls node_modules/.bin/tsc` before
  trusting a gate's exit code; `npm ci --prefer-offline` restored it in ~1 min.
- Under host load 25-50 the HEAD suite has ~10 timeout failures (and `loadGate.test.ts` fails by design). A gate run
  needs its failures classified against a same-load HEAD baseline, not read as regressions.

- `src/ui/contrastAudit.ts` pins `file:line` sites for HomeScreen, GameScreen and SettingsSheet, so any edit above
  those lines fails `contrast.test.ts` (56 rows here). Briefs touching those files should say "re-point the audit
  sites"; a difflib old->new line map (`artifacts/TF-01/remap_contrast_sites.py`) does it mechanically and flags lines
  whose text moved.

- A plan solver calibrated on one board does not transfer to another: the daily board's centre is 17 px higher
  than the campaign board's, and a blind tap batch then hit the lose panel's rewarded-ad button. Calibrate each
  board from its ink bounding box against its arrow-cell extents, and check "N left" after every batch before the
  next (`artifacts/TF-01/scripts/tapplan.py`, `CY=`). In zsh, a `for` loop over "a b" pairs passes each pair as
  one argument, never as two.
- The emulator's `com.android.bluetooth` crash-loops (SIGABRT every ~8 s). A `logcat -b crash` line count without a
  process filter is a false "crash" alarm; grep for the app package or `>>> <process> <<<`.
