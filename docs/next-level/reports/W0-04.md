## What changed

`src/ui/feedbackCurves.ts`
- `blockerOpacityAt(k, reducedMotion)` returns `1` when `reducedMotion` is true.
- `blockerStrokeSwellAt(k, reducedMotion)` returns `1.6` (the value at onset) when `reducedMotion` is true.
- New `blockedFlashMixAt(k, reducedMotion)`: 0 is heart and 1 is ink. It returns `0` when `reducedMotion` is true. Otherwise it returns `1-(1-t)^2`, with `t` clamped.
- New `hintStrokeSwellAt(k, reducedMotion)`: when `reducedMotion` is true it returns the exported `HINT_STROKE_PEAK_SWELL` (`1 + 0.45` = 1.45). Otherwise it returns the old pulse expression unchanged.
- With `reducedMotion=false`, every function returns exactly what it returned before.

`src/ui/StaticBoardSurface.native.tsx` and `src/ui/BoardView.tsx` (web `WebDynamicBoardLayer`)
- `BlockerArrow` and `HintArrow` now receive `reducedMotion`.
- The inline maths (blocker opacity and swell, the blocked colour mix, the hint pulse) now call the shared functions.
- When `reducedMotion` is true, none of the three components starts its `withTiming`.
- Lifetimes still come from the existing cleanup timers.
- `excludedArrows`, the visibility-mask memo, durations, amplitudes and colours were not touched. The diff hunks touch only the three feedback components, their props and the imports.

`src/ui/__tests__/feedbackCurves.test.ts`
- The existing assertions are kept with the same values, now called with `false`. `blockerOpacityAt(1, false) ≈ 0` is kept as the regression anchor.
- New cases, 36 tests in total:
  - reduced-motion statics for k in {0, .25, .5, .75, 1, -1, 2};
  - `blockedFlashMixAt(k,false)` against the old inline `1-(1-k)^2`;
  - `hintStrokeSwellAt(k,false)` against the old inline pulse;
  - clamping of out-of-range k;
  - a check that the hint still pulses with motion on.

## Evidence

Display frame period **P = 16.667 ms**. EXECUTED: `dumpsys display` gives `fps=60.000004` (`artifacts/W0-04/display-fps.txt`).

Method notes for all native recordings:
- `screenrecord --size 720x1560`. At 1440x3120 the encoder refused and fell back to 720x1280, which is not the display's aspect ratio.
- The recorder emits variable-rate frames: a static screen produces one frame. A colour holds until the next frame's `pts_time`, so D = pts(first frame without heart) − pts(first frame with heart). The resolution is one frame period on each side.
- Regions are each arrow's **own cells** from `LevelGenerator.generate(0)`, so a neighbour can never be counted. Tapped arrow = arrow 6, tap at (1160,1869). Blocker = arrow 2, from `board.blockerOf`. The two are adjacent.
- Each pixel is classified to the nearest of {bg, ink, heart, accent} (theme Daylight).
- **Noise floor:** "heart present" means the region's heart count is above the maximum seen in feedback-free frames (every pre-tap frame, plus every frame at tap + ≥2 s). The blocker region shows 4-56 heart-classified pixels at rest (compression chroma on ink edges). A real heart stroke shows about 1600. Anti-aliased grey edges classify as accent in every frame, including pre-tap frames, so accent is not judged.
- Before each launch, all three scales were set and read back in `*-scales.txt`, then the app was force-stopped and relaunched. Level 1 was confirmed as `LEVEL 1 · 60 left` via uiautomator.

## Concerns
1. **Disk gate: I deleted the in-repo `android/` directory (2.4 GB, generated and gitignored) before the perf build.** `df -h /` showed 3.9 GiB before that and 5.9 GiB after, against the 5 GB gate. The harness's own `prebuild --clean` deletes that directory as its first build step, so the build's peak need was unchanged. Nothing outside the repo was deleted. `~/.gradle` was 4.5 GB, so it had been repopulated since the Phase 1 note. Free space after the whole task: 6.1 GiB.
2. **Pre-existing native defect, observed and not fixed (step 5 forbids touching the mask).**
   - The tapped arrow is missing from the screen for one frame (12-15 ms) when its overlay mounts, and again when it unmounts. The native board's visibility mask and the Skia overlay present on different frames.
   - It is visible in the fixed build (`post/w004-post-rm-strip.png`, frames at t=2.0223 and 2.3206: the region is all background).
   - It is also visible in the **base** APK (`pre/w004-pre-analysis.txt`, frame at t=2.3109).
   - This is W6-01's area (mask rebuild), not a W0-04 regression.
3. **Pre-existing web defect: the blocked arrow's colour never animates on web.**
   - The animated `stroke`/`fill` stays `rgba(228, 50, 125, 1)` for the whole bump, with motion on and off, both before and after the fix (`web/prefix/web-motion-blocked-summary.txt`).
   - So on web the tapped arrow was never blacked out; only the blocker was. The motion-on web bump never settles to ink before it unmounts.
   - Out of scope (colour, motion-on). It likely belongs to W2's census.
4. **The captures ran on JS-only repacks, not gradle builds.** They use W0-03's pipeline: the base APK's native code with a debug signature. The perf APKs are repacks into a gradle perf host. The pipeline control above shows only the HBC hashes differ. The native code of `da93dcd` equals HEAD's (W0-03 showed no package or native diff, and this task changes TS only).
5. **Blocker stroke ratio reads 1.82× on the 720 px recording**, not 1.6×: 8.0 against 4.4 px, which is integer-pixel rounding at half resolution. The web DOM gives the exact value, 9.216/5.76 = 1.600.
6. **The hint's static stroke is slightly thicker than any motion-on frame.** The shipped pulse's real peak is 1 + 0.45 × 0.925 ≈ **1.417×** (at k ≈ 0.121), because `|sin|` peaks where the decay factor is already 0.925. Ruling W0-4 and the brief fix the static value at 1.45×, so the reduce-motion hint is about 2% thicker than the thickest motion frame. The owner may want to know this when accepting the look.
7. **D₁ in the reduce-motion recordings rests on one held frame.** The recorder emits no frames while the screen is static. D is bounded by ±1 frame period at each end, which the window's ±2P already allows for. Two independent runs agree (286.1 and 302.7 ms).
8. The captures needed temporary code: a log line and, for the hint, an injection. Both are saved as patches under `artifacts/W0-04/patches/`, and neither is in any commit. For W0-07's log-free re-run, `analyse.mjs` works on any recording of the same level and tap. `useReducedMotion` would then have to be shown by the settings read-back plus the static-versus-fading contrast.
9. `blockedFlashMixAt` clamps `t`, and the old inline expressions did not. The result is identical for k in [0, 1], and `withTiming(0→1)` never leaves that range.
