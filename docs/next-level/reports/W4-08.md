# W4-08 — Measure silhouette legibility at gallery sizes before choosing tile size and raster rows

Implementer report, 2026-09-25. BASE = `05ac4c5` on `next-level`. Requirements: `task-W4-08-brief.md`
(no binding controller amendments — "No pre-flight scan finding names W4-08") and `codex/GLOBAL.md`.
Raw evidence is under `artifacts/W4-08/` (gitignored). Nothing was committed; the controller owns git.

## Outcome

Dev script only, no app code and no shape-art changes (non-goal, respected). It rasterizes all 26
`ShapeLibrary` shapes at rows ∈ {8, 10, 12, 14, 20} (cols = round(rows × aspect)) through the same
`ShapeDef.rasterize` → `silhouettePath` (even-odd fill) path W4-09's gallery tiles will use, at 2/3/4
px per raster cell, and writes the evidence for the owner to pick a raster row count and minimum tile
size from.

**Zero empty rasters** across all 26 shapes × 5 row counts (130 rasters; confirmed both by the printed
`RESULT` line and by scanning `filled-cell-table.txt` for `0/`). No raster is empty at any row count
tested — the numeric floor the acceptance criteria asks for is clean. That does not mean every shape
is *legible* at every row count: several go from a fully-filled mask to a mask that reads as a blob or
a bar rather than the intended shape well before it goes empty. See "Legibility verdict" below.

## Legibility verdict (plain language, for the owner — not a row/tile-size pick)

None of the 26 shapes ever renders as a fully empty raster. But "not empty" and "nameable" are
different bars, and several shapes cross from "clearly the intended shape" to "a blob or a bar" well
above 0 filled cells. Below, "collapses" means: at that row count, across the 2/3/4 px/cell range
tested, the silhouette reads as a generic blob/bar rather than the specific shape, even at the largest
(4 px/cell) tile in that sheet.

- **rows=8** (`gallery-rows8.png`, `owner-legibility.png` column 1): the worst of the five. Collapses:
  - **Bolt** — 4/48 filled. Four isolated dots, not a zigzag. The clearest collapse in the set.
  - **Trophy** — 12/56 filled. Reads as a plain vertical bar/hourglass; no bowl or base visible.
  - **Rocket** — 14/48 filled. Same: a plain bar, no fins or nose cone.
  - **Arrow** — 11/56 filled. Reads as a small barbell/exclamation mark, not an arrowhead.
  - **Pine** — 17/56 filled. A round blob with a stem dot; the two canopy tiers don't resolve.
  - **Star** — 20/64 filled. A rounded blob/asterisk; the five points don't resolve.
  - Borderline (recognizable but thin): **Crescent** (22/64 — reads as a comma more than a moon at
    2 px/cell, moon-like only at 4 px/cell) and **Butterfly** (42/72 — reads as a blocky domino, wings
    not distinct until 4 px/cell).
- **rows=10** (`gallery-rows10.png`): improves but the same shapes are still weak, especially at
  2 px/cell (the smallest tile in that sheet):
  - **Bolt** — 10/80. Only becomes a recognizable zigzag at 4 px/cell; still a squiggle at 2-3 px/cell.
  - **Trophy** — 24/90. Still mostly a bar; cup/base not distinguishable.
  - **Rocket** — 32/80. A nose+body silhouette starts to appear at 4 px/cell but no fin.
  - **Pine** — 25/90. Still a blob with a stem dot at 2-3 px/cell.
  - **Star** and **Arrow** cross into "nameable" here (Star's points and Arrow's arrowhead both
    resolve, at least at 3-4 px/cell).
- **rows=12** (`gallery-rows12.png`): **Bolt**, **Trophy**, **Rocket**, **Pine** all become
  identifiable at 3-4 px/cell (Bolt is a clean zigzag; Trophy shows a cup narrowing to a stem; Rocket
  shows a fin; Pine shows two tiers). All four are still weak at 2 px/cell (the smallest tile in this
  sheet, ~24-30 px).
- **rows=14** (`gallery-rows14.png`): every shape reads as its intended silhouette at every px/cell
  tested, including Bolt, Trophy, Rocket, Pine, Arrow, Star. One caveat that is NOT a raster-resolution
  problem and persists at rows=20 too: **Trophy** reads more like a goblet/wine glass/hourglass than
  specifically "trophy" — that's the shape's own design (a symmetric cup-on-a-stem-on-a-base outline,
  W3's art, out of this task's scope), not something more raster rows fixes.
- **rows=20** (`gallery-rows20.png`): every shape is clean, including the four weakest ones (Bolt,
  Trophy, Rocket, Pine). Best fidelity of the five, at the highest per-tile cell cost (e.g. Fish is
  20×24 = 480 cells, Rectangle is 20×30 = 600).

**Side-by-side, same on-screen size** (`owner-legibility.png`, all 5 row counts rendered at one fixed
40 px tile so only raster resolution varies, not display size): this is the clearest single artifact
for the owner — for a shape like Bolt or Trophy, scanning left to right across the row shows the exact
point where the silhouette resolves from "abstract blob" into "identifiable shape," at the size the
gallery would actually show it. The numeric caption under each tile is `rows×cols · filled` so a weak
tile's low fill count is visible right next to the picture.

## Decisions

1. **`shapeCatalogue()` reads `ShapeLibrary`'s own values by `instanceof ShapeDef`, not a literal
   `SHAPE_CATALOGUE` name.** The brief says "for every id in `SHAPE_CATALOGUE`"; no such export exists
   in `src/core/shapeLibrary.ts`. `ShapeLibrary` (the returned object) is the catalogue: its 26 named
   shape properties plus `SimplePool`/`MediumPool`/`ComplexPool` (arrays) and `pick()` (a function).
   Filtering by `instanceof ShapeDef` gets exactly the 26 shapes and stays correct if a shape is added
   later, instead of hardcoding a 26-name list that would silently go stale. Cross-checked against the
   brief's own arithmetic: "24 non-fill shapes" = 26 total − Square/Rectangle (the only two with
   `fillsGrid === true`), which matches.
2. **The owner-comparison sheet is additive, not in the original brief text.** The brief's acceptance
   criteria only ask for the per-row-count sheets and the filled-cell table. The dispatch instruction
   for this task additionally asked for one combined sheet, candidate row counts side by side, "at the
   tile size closest to ~40 dp." I read "the tile size" (singular) as one fixed rendering size used
   uniformly across all 5 columns — not each row count's nearest 2/3/4 px/cell variant (which would
   give 5 different pixel sizes: 32/40/36/42/40 for rows 8/10/12/14/20, undermining an apples-to-apples
   comparison). I used `silhouettePath(mask, 40)` directly, i.e. exactly 40, for every cell in that
   sheet. This sheet does not reuse the 2/3/4 px/cell sweep; it's a separate, focused rendering at one
   size so only raster resolution (not tile size) varies across the row.
3. **Per-row-count sheet tile size = `pxPerCell × max(rows, cols)`** (a square canvas the shape is
   centered in, same convention `scripts/art/silhouette-sheet.ts` already uses for `silhouettePath`'s
   `size` argument). Column width and row height in each contact-sheet SVG are the max tile size across
   shapes for that column/row respectively, since wide/tall shapes (Rectangle at aspect 1.5, Bolt at
   0.8, etc.) get different `cols` at the same `rows`.
4. Did not attempt the W4-09 "≥22/24 named unprompted" pass bar — that's W4-09's acceptance criterion
   (owner naming shapes from a real gallery, recorded in W4-09's PR), not this task's. This task's job
   was only to make legibility visible and measurable before that choice is made.
