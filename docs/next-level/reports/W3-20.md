## What changed

- **`src/core/displayTier.ts` (new).**
  - `displayTierForArrowCount(n, thresholds?)` and `displayTier(level)` are pure functions. They read only the
    arrow count.
  - `DISPLAY_TIER_THRESHOLDS = { hard: 88, superHard: 133 }` is marked `OWNER-PICKED STARTING VALUE`.
  - Normal is below 88, Hard is 88 to 132, and Super Hard is 133 and up. Each edge is one cut on one number, so
    **two displayed tiers can never share an arrow count, by construction**. A unit test checks that the tier
    never goes down as the count rises (0 to 600).
- **`TIER_LABEL_V2_ENABLED`** is in `src/featureFlags.ts`, as `process.env.EXPO_PUBLIC_TIER_LABEL_V2 === '1'`, and
  defaults to OFF. RULING 1 explains the placement.
- **`src/ui/tierLabel.ts` (new).**
  - `headerTier(level)`: with the flag ON it returns `displayTier(level)`; OFF it returns `level.difficulty`.
  - `menuTier(resumeIndex)`: with the flag ON it returns the displayed tier of the exact board Play deals. OFF it
    returns `Difficulties.forLevel` and generates nothing.
  - Each count is cached per `(index, version, switchLevel)`, up to 8 entries.
- **`src/ui/gameSessionLifecycle.ts`.** The generate call moved out of `createLevelSession` into
  `generateCampaignLevel(index, version)`. The menu and the session now share one call. The behaviour is
  unchanged, and the existing V2-WIRE spy tests pass.
- **`GameScreen.tsx`.** The tier word, its colour, "Hint unavailable ·" and the "N left" counter now use
  `labelTier = headerTier(level)`. All four already shared the tier colour. **`HomeScreen.tsx`** uses
  `useMemo(() => menuTier(resumeIndex), [resumeIndex])`.
- **`contrastAudit.ts`.** The 70 `${HS}`/`${GS}` file:line pins that moved were re-pointed with a difflib line map
  from HEAD's copies. Two comment pointers were also updated (`HomeScreen.tsx:269-300`, `:328`). The tier colours
  themselves are unchanged, and `contrast.test.ts` passes.
- **`DESIGN.md`.**
  - New **Displayed tier** entry. It names the flag and states what OFF and ON show.
  - The header and menu tier lines point to it.
  - The colour-table tier pointers were re-pointed.
- **`scripts/analysis/display-tier-report.ts` (new).** This is the measurement (below).

## Menu path and its cost

- **There is no cheap source for the arrow count.** `shapeNameForLevel` gives only the shape. `menuTier`
  therefore runs `generateCampaignLevel(resumeIndex, levelGenVersion(resumeIndex))`. That is the same version
  resolver and the same generate call, switch-level knob included, that `createLevelSession` uses.
- **When it runs.**
  - Once per mount, inside `useMemo` keyed on `resumeIndex`, on the first render.
  - A module cache keyed `(index, version, switchLevel)` then skips it on later mounts at the same level. For
    example, returning to the menu after a loss does not generate again.
  - It never runs per render.
  - With the flag OFF it never runs at all. A test proves 0 `generate` calls.
- **Node timings.** These were taken on Node v20.19.4 with `artifacts/W3-20/scripts/menu-cost.ts`. Output is in
  `artifacts/W3-20/menu-cost/node-timing.txt`. The host load average was 28–36 during the runs, so the numbers are
  upper-biased.

  | Board | Arrows | Cold | Warm median | Warm p90 |
  |---|---|---|---|---|
  | Heaviest fresh v2 (index 9479, Rectangle) | 197 | 32.1 ms | 10.1 ms | 25.8 ms |
  | Heaviest existing v2 (index 1733, Umbrella) | 196 | 37.3 ms | 11.2 ms | 29.4 ms |
  | v1 worst (3827, Flower) | 250 | 54.0 ms | 16.3 ms | — |
  | Level 12 v1 (Bolt) | 54 | 11.5 ms | 4.3 ms | — |

- **W3-15's "worst v2 board" is stale.** It cited index 80507 (194 arrows), which now deals Hexagon with 164
  arrows. The current heaviest boards come from W3-21 step 1.
- **On device: UNVERIFIED, inferred.** W3-15 measured cold Hermes deals on the emulator at about 85–93 ms for the
  v1 worst board and about 57–62 ms for a v2 worst. The flag-ON menu therefore pays up to roughly that much once
  per new resume level, on the menu's first render. Play then deals the board again (a duplicate generation). No
  device timing of the menu path itself was taken.
- **Possible follow-up, not built.** Hand the menu's board to the first `createLevelSession` once, as a single-use
  hand-off, so the generation is not repeated.

## RULINGs

1. **Flag placement.** `TIER_LABEL_V2_ENABLED` is an `EXPO_PUBLIC_TIER_LABEL_V2` env flag in `src/featureFlags.ts`,
   not a literal in `generatorVersion.ts` like `GEN_V2_ENABLED`. The header of `featureFlags.ts` says
   player-visible gates use `EXPO_PUBLIC_*` (ruling I-29). The name is the brief's, not `META_*`, so it gets its
   own flag test. The env var also meant the build needed no source edit.
2. **The brief's share premise is wrong.** The brief says "1/2 Normal, 1/3 Hard, 1/6 Super Hard … matching today's
   3/2/1 cycle share". The shipped cycle N, N, H, N, N, SH is **4/6, 1/6, 1/6**.
   - I kept the brief's explicit numbers, 1/2, 1/3 and 1/6, which give **88/133**.
   - The report also prints the real-cycle alternative, **95/133**. Super Hard is 133 either way.
   - The owner should pick.
3. **The daily header is derived too.** It renders through the same `MissionLabel` and colour. Its config stays the
   fixed Normal config. Flag OFF, the daily header is unchanged (identity test).
4. **Tutorial route.** The tutorial header has no tier word, so it is untouched. When Play would route to the
   tutorial, the menu still names the campaign board at `currentLevel`, as it does today.
5. **Capture build flags.** The flag-ON build reuses the installed build's flag set, so the before and after
   differ only by this code (plus the HEAD delta since `8a5a56d`), the tier flag and the `[ftue]` log.
