## Decisions (routine judgment calls, recorded per the unattended-run instruction)

1. **`ad_reward.earned` kind.** The brief names the key but not its value kind. I chose `boolean`
   (reward granted or not) and marked it `// OWNER-PICKED STARTING VALUE` in `events.ts`. An
   alternative (a numeric reward amount) seemed less likely given ad SDKs report reward grants as
   a boolean callback, but this is a guess, not a measured value.
2. **Envelope `sessionIndex`/`bucket` are hardcoded to 0 for now.** The brief specifies the
   envelope's shape but this task's Files list is only `events.ts`, `telemetry.ts`, `hash.ts` and
   the test — no session-tracking module. Real session/bucket values need a place to be set from
   (likely W6-06, which emits from the game). I did not invent an untested `Telemetry.configure`
   extension beyond the brief's exact `{ validate, disabled }` signature to avoid overbuilding;
   instead the envelope carries `sessionIndex: 0, bucket: 0` with a comment flagging this as a
   placeholder. None of the acceptance criteria constrain these values, so this doesn't affect
   verification, but a future task must wire real values before the envelope is meaningful for
   session-scoped metrics.
3. **`App.tsx` wiring for `Telemetry.configure({ disabled: PERF_MODE })` was not added.** The
   brief's sentence "`disabled` is set by `App.tsx` when `PERF_MODE`" describes the *capability*
   `configure` must expose, not a change to this task's Files list (only `src/telemetry/*` files
   are listed, and the rollback note says "delete `src/telemetry/`, since nothing imports it
   yet" — confirming no other file should import it in this task). `configure({ disabled })`
   exists and is tested; wiring it into `App.tsx` is left to whichever task actually starts
   emitting (W6-06), consistent with the Non-goals section ("Emitting from the game (W6-06)").
4. **No standalone "build an error event from a JS `Error`" export.** See acceptance criterion 5
   above — the brief doesn't name this function in the API list, and it would be one line at the
   call site (`fnv1a32(\`${err.name}:${err.message}\`)`), so I left it to the future caller
   (likely an error boundary, out of scope here) rather than adding unrequested surface area.
5. **`checkEvent`'s "outside the schema" covers 4 failure modes** (unknown event name, unknown
   property, missing property, wrong value kind), all treated the same way by `validate`
   (throw/drop). The brief's wording ("an unknown name or a property outside the schema throws")
   is slightly narrower in the literal text, but the Change section's field-spec design ("allowed
   value kinds") only has teeth if a wrong-kind value is also rejected, so I read "outside the
   schema" broadly. If the owner wants wrong-kind values to pass silently even under `validate:
   true`, that's a one-line change to `checkEvent`.

## Fix round 1 (task review, 2026-09-17)

**Finding (important, both entries the same defect):** `Telemetry.emit()`'s fast path was
`if (config.disabled || currentSink === noopSink) return;` — this ran *before* `checkEvent()`.
Since `noopSink` is the default sink until something calls `Telemetry.useSink()`, any call made
with `validate: true` and no sink installed yet (e.g. at app boot, or any dev/test code that sets
`validate: true` before wiring a sink) silently dropped an unknown event name or a malformed
property object instead of throwing — contradicting the brief's unconditional acceptance criterion
("With `validate: true`, both throw"). None of the 6 original validation tests caught this because
every one of them calls `Telemetry.useSink(jest.fn())` before asserting throw/no-throw, so the
`noopSink` branch of the fast path was never exercised under `validate: true`.

**Pre-fix reproduction (EXECUTED):** confirmed live before touching the fix — reverted `emit` to
the original fast path (`config.disabled || currentSink === noopSink`) and ran
`npx jest src/telemetry`. Two new tests that call `Telemetry.emit` with `validate: true` and no
prior `useSink` call both failed with "Received function did not throw" (see command output
below), reproducing the exact scenario in both finding entries. Then restored the fix and reran —
all 28 pass. This proves the new tests exercise the originally-broken path, not just the edited
unit.

**Fix:** reordered the fast path in `Telemetry.emit()` (`src/telemetry/telemetry.ts:121-152`) so
`disabled` still short-circuits everything (telemetry fully off, no validation either — this was
never in question), but the `noopSink` shortcut now only applies when `!config.validate`:

- `disabled` → return immediately (unchanged).
- `noopSink` **and** `!validate` → return immediately, no allocation (the common case: prod
  builds, or dev builds before `validate` defaults true, still pay zero cost).
- otherwise → run `checkEvent()`. A bad event throws under `validate: true` (now true regardless
  of whether a sink is installed) or drops silently under `validate: false` (unchanged).
- a **well-formed** event with `noopSink` still installed returns after the check, before
  building the envelope — so the "never allocates for noopSink" property from the brief still
  holds for the envelope-construction step; only the (cheap) `checkEvent()` call now also runs
  when `validate: true` and no sink is installed yet, which is the entire point of `validate: true`
  as a dev-time safety net.

This does not change behaviour for any call site that installs a sink before emitting (i.e. every
call site this codebase has today — nothing imports `src/telemetry/` yet), and does not change the
`disabled: true` behaviour or the `validate: false` "drop silently" behaviour in any configuration.

**Covering tests (new, in `src/telemetry/__tests__/telemetry.test.ts`, describe block
`"Telemetry.emit validation with the default sink still installed (fix round 1)"`):**
- `validate: true throws on an unknown event name even before any sink is installed`
- `validate: true throws on a malformed property object even before any sink is installed`
- `validate: false still drops silently (no sink installed, no throw)` — guards the fix didn't
  flip `validate: false` behaviour
- `disabled: true still wins over validate: true (no throw, no sink call)` — guards `disabled`
  still short-circuits first
- `a well-formed event with no sink installed does not throw and does not allocate a call` —
  guards a valid event still doesn't throw or need a sink

All five deliberately skip the `Telemetry.useSink(...)` call that every pre-existing validation
test makes first, since that call was exactly what masked the bug.
