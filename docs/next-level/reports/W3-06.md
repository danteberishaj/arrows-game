### Bundle grep (EXECUTED, no native build, no emulator)

`npx expo export --platform android` was run twice, output under `$TMPDIR`'s scratchpad, deleted
immediately after (disk was 3.3–3.4 GB free throughout, checked with `df -h /` before each export).
Both produced a Hermes bytecode bundle (`file` reports `Hermes JavaScript bytecode, version 98`,
confirming the "Hermes bytecode" case GLOBAL.md flags).

- A first check established the grep methodology actually finds text in `.hbc` output: `grep -a -c
  "Bolt"` found 1 occurrence directly (no UTF-16 decoding needed for this ASCII string), and a
  Python byte-scan for the same string's UTF-16LE/BE encodings found 0 — so for this bundle, ASCII
  `grep -a` alone is sufficient; a UTF-16LE/BE byte-scan was still run as a control on every check
  below.
- Sanity check: `EXPO_PUBLIC_DEV_LEVEL`/`EXPO_PUBLIC_DEV_GEN_VERSION` (the raw env var **names**) are
  compiled out (0) in the OFF export, as expected — Babel replaces `process.env.EXPO_PUBLIC_X` with
  its literal value, not the name. The **identifiers** `DEV_LEVEL_INDEX`/`DEV_GEN_VERSION` (the JS
  export names) still appear once each in both bundles — expected and harmless, matching precedent
  (`PERF_LEVEL_INDEX` is present in every bundle too): the code is always compiled in and inert; only
  the *value* is env-gated, which is what the risk note and the following check are actually about.
- **The proof:** `EXPO_PUBLIC_DEV_LEVEL=847293` (an arbitrary 6-digit value chosen only for this
  check, well outside any real level index / arrow count / hearts value in the game) with
  `EXPO_PUBLIC_DEV_GEN_VERSION=2`.
  - OFF bundle (no dev env set): `grep -a -c "847293"` → **0**. Python byte-scan (ASCII + UTF-16LE +
    UTF-16BE) → **0** on all three encodings.
  - ON bundle (positive control, env set as above): `grep -a -c "847293"` → **1**. Same Python
    byte-scan: ASCII **1**, UTF-16LE/BE **0** (Hermes stored this literal in its Latin1/ASCII string
    table, not its UTF-16 table).
  - Both `.hbc` files and their export directories were deleted immediately after
    (`rm -rf`), per the controller's disk-tight instruction.

## Migration and wipe risk

None. No persisted key is added, read, or removed. `EXPO_PUBLIC_DEV_LEVEL`/`EXPO_PUBLIC_DEV_GEN_VERSION`
are build-time-only switches read once at module load (same shape as `EXPO_PUBLIC_PERF_LEVEL`); no
player build sets them, and doing so does not touch `SaveSystem`, `AsyncStorage`, or the campaign
pointer — the game plays a level under whichever version was forced without ever writing that
version anywhere.

## Decisions

1. **`board_mount`'s new fields append *after* the existing `<board> <t>` pair**, not before it
   (unlike `blocked`/`clear`, which put their fields before `t`). This exactly reproduces the
   brief's own acceptance string (`board_mount 11 … gen=1 arrows=54 shape=Bolt`, where `…` is the
   elapsed-ms placeholder, always `0` for `board_mount`) rather than reordering it.
2. **Tutorial and daily sessions report `genVersion: 1`.** Neither is dealt through
   `LevelGenerator.generate(index, version)`: tutorial boards are authored (`buildTutorialLevel`),
   and `generateDaily` calls `LevelGenerator.buildFromShape` directly with no version parameter.
   There is no v2 tutorial or v2 daily content (non-goal), so tagging both `1` is accurate today and
   costs nothing to keep accurate later — if W3-10 ever versions daily/tutorial content, `genVersion`
   is already plumbed through `LevelSession` and only those two call sites need updating.
3. **`LevelSession.genVersion` stores the version a board was actually generated with**, taken
   directly from `createLevelSession`'s `version` parameter, rather than recomputing
   `levelGenVersion(index)` again inside the `board_mount` log effect. `SaveSystem.genSwitchLevel`
   cannot change between session creation and the log effect in the same tick, so this makes no
   difference today, but avoids a future drift bug once W3-10 makes v2 content actually differ from
   v1 (recomputing later could theoretically read a value that changed in between, or double up on
   the DEV_GEN_VERSION/PERF_MODE branching logic in two places).
4. **Two test files beyond the Files list gained assertions/tests**: I extended existing `it`s in
   `gameSessionLifecycle.test.ts` (adding `.genVersion` checks to sessions the file already builds)
   rather than adding new ones, and added two source-order guard tests plus one `describe` block —
   all in the file the brief already lists indirectly via "GameScreen.tsx" test coverage patterns
   established by W3-05 (the `stampGenSwitchLevel` source-order test lives in this exact file). I
   judged this necessary because `App.tsx` cannot run under node-jest (same limitation W3-05 hit for
   its own App.tsx wiring) and ruling F28 is a binding, testable behavioral requirement — leaving it
   with zero test coverage would repeat the "App wiring... has no runtime test" gap W3-05 flagged as
   a concern for itself. `src/__tests__/perfMode.test.ts` was extended for the same reason (it is
   the existing home for `perfMode.ts`'s pure-function tests).
5. **`GameScreen.tsx`'s board_mount call was rewritten as a single object-literal line** specifically
   to keep the file's total line count at 1341 (unchanged from before this task; `wc -l` before and
   after), so `contrastAudit.ts`'s pinned `${GS}:NNN` line numbers (23 distinct line numbers, 37
   occurrences across 22 `USAGES` rows — `grep -oE '\$\{GS\}:[0-9]+' src/ui/contrastAudit.ts | ...
   | uniq | wc -l`, EXECUTED) needed no re-pointing, and `contrast.test.ts`'s "every usage row names
   a real site" suite (which dynamically reads each pinned line and regex-checks its content) passed
   unchanged. This was a deliberate style choice to reduce risk, not an oversight — the controller
   note explicitly allowed re-pointing if I shifted lines, but avoiding the shift entirely is
   strictly safer.
