## Performance: the exit burst, 0.144 vs BASE (EXECUTED; POLISH-T10 `pace.mjs` method, `scripts/pace507.mjs`)

- **Why 0.144, not "the widest":** the widest candidate is 0.26, which is BASE's own value (the override inlines the
  same number; its only extra work is one `Number()` at module load). The comparison that can move per-frame cost is
  the candidate furthest from BASE, 0.144 (also the one whose smaller cap moves `endMs` earliest). Every candidate is
  thinner than BASE, so none draws more pixels (INFERRED).
- Method per run: install -r, relaunch the PERF build (level 167, fit), "202 left" + camera registration, then the first
  27 exits of the `findHint` solve order, each: `gfxinfo reset`, 150 ms, one tap, 1100 ms, `framestats`. Arms P = BASE
  (`w507-base-L167`), A = 0.144 (`w507-0.144-L167`), N = BASE again (same-APK null); 10 rounds, order rotating
  PAN / ANP / NPA; installed sha logged per run (`perf/run-log.txt`), host load 1.9–6.1. Analysis
  `scripts/paceab507.py` (POLISH-T12's `paceab12.py` metrics; the first exit frame is #0 in every arm since POLISH-T12
  Part B), exact permutation test over the 10 + 10 run values (`perf/paceab507.md`, `perf/paceab507.json`).
- **Reconciliation:** frames / expected at 60 Hz: P 3832 / 3844, A 3825 / 3845, N 3840 / 3860 (27 exits x 10 runs
  each; the few missing frames are host stalls in 3 runs). 27/27 exits happened in every run (175 left at the end).
  One run (A7) was in the emulator's slow RenderThread mode (per-run RT median 8.24 ms): round 7 hit a host stall that
  also stuffed 6 exits of P7.

|---|---|---|---|---|---|---|

| first exit frame missed vsync | 7.4 % | 5.6 % | 5.6 % | −1.9 pp | −1.9 pp | 1.00 |
| frames per exit | 14.30 | 14.30 | 14.30 | 0.00 | 0.00 | 1.00 |

| frames > 33.3 ms per exit | 0.00 | 0.09 | 0.00 | +0.09 | 0.00 | 0.25 |
| RT median / p95 (ms) | 4.07 / 12.33 | 4.19 / 15.90 | 3.90 / 9.58 | +0.13 / +3.57 | −0.16 / −2.75 | 0.95 / 0.48 |

- **Verdict: no difference detectable; not a proof of "no slower".** No metric of A differs from BASE with p < 0.25,
  and every A − P is of the same size as the same-APK null's |N − P| on the medians (RT median +0.13 vs −0.16; first
  exit frame +0.10 vs −0.34). The tails (p95, > 16.7 ms) are dominated by buffer-stuffing episodes that hit every arm
  (stuffed exits P 17, N 21, A 28 of 270; A7 alone has 13) and grew with host load over the session. In the two quietest
  rounds (1 and 2, no stuffed exit in any arm) A − P = +0.07 / +0.05 ms RT median, the same as N − P there (+0.06 /
  +0.01). Paired by round, the first-exit-frame RT A − P has median +0.05 ms, N − P −0.15 ms.
  INFERRED: a thinner stroke rasterises fewer pixels, so the expected sign is ≤ 0.

## Decisions

1. **Two PERF builds per candidate, not one.** `EXPO_PUBLIC_PERF_LEVEL` is inlined at build time and a PERF build
   boots straight into that level with persistence off, so one build cannot record both index 167 and index 137.
   8 candidate builds (+ BASE) instead of 4; each is the same source with a different level.
2. **The fit camera** (META_ZOOMED_CAMERA unset in the capture builds, as in W2-04/W2-05/W4-06/W5-04/W2-06): the
   brief's "at fit" is then the opening camera; the zoomed pass is a real pinch (~1.7x), registered per run.
3. **1080x2340 recordings** instead of P-02's 720x1560: the trail at fit is 5–10 device px wide, and halving it made
   0.144 vs 0.18 hard to judge; the emulator encodes 1080x2340 and every exit burst still has 11–17 frames at ~16.6 ms
   (max gap in a burst 35 ms).
4. **Exit-burst perf on the PERF level-167 builds** (the recording builds) rather than POLISH-T10's level 1 at the
   zoomed opening camera: same per-exit method and analysis; a denser board, fit camera, and no extra builds.
5. **Tiles chosen by position, not time**: the recorder's frame phase differs per recording (VFR), so a fixed time
   showed the arrows at different places; the sheet uses the first frame in which the arrow is N cells out.

## Concerns

1. **Perf is inconclusive, not a pass.** See the verdict: the null spread on this loaded host (other sessions on the
   Mac, load 4–6) is wider than any effect a stroke width could have. The owner rule ("nothing gets slower") is met
   only in the weak sense "no slowdown detectable"; a quiet-host rerun (`scripts/run-pace507.sh`) would tighten it.
2. **The zoomed pass is not the identical camera in every recording**: the same injected pinch registered at 63.2–63.9
   px per cell in three recordings and 61.0 in the 0.18 one (−4 %); the same arrows are tapped (registration), but the
   0.18 zoomed tiles are 4 % smaller.
3. The 0.144 candidate equals `STROKE`: a leaving arrow then has the resting arrows' weight, and only motion separates
   it from the field (see the Star rows). UNVERIFIED-DEVICE: weight perception on a physical panel; iOS not built.
4. The disk was at 0.6 GB when this batch started; `android/app/build` (786 MB; its only output APK is identical to
   `artifacts/W4-11/apk/arrows-testads-W4-11.apk`) was deleted to pass the 1.2 GB floor (GLOBAL allows it). The next
   gradle build is a full one.
