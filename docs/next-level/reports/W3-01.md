## What I implemented

1. `scripts/analysis/difficulty-probe.ts` (new) — a CLI that imports only
   `src/core` (`LevelGenerator`, `BoardLogic`, `Difficulties`, `ShapeLibrary`,
   `DotNetRandom`; no React, no `src/ui`). For each level it:
   - generates the level with the shipping `LevelGenerator.generate`;
   - walks the board to empty, at each step removing the first arrow (in
     `board.arrows()` order) for which `board.canExit` is true;
   - accumulates the uniform-sampling search-cost proxy from the brief at
     every state: `scanTaps += (n+1)/(k+1)`, `blockedTaps += (n-k)/(k+1)`,
     where `n` = arrows remaining, `k` = arrows currently clearable;
   - asserts the walk empties the board in exactly `arrowCount` removals
     (throws and exits non-zero otherwise) — the in-probe reconciliation
     the brief asks for.
   - Modes: default per-level rows, `--per-tier`, `--bands`,
     `--shape-report`, `--tier-report`, `--capacity`, `--clamp-shortfall`.
     Flags: `--levels a-b` (displayed, 1-based; every row also prints the
     0-based index), `--version 1|2` (`2` exits non-zero with "generator v2
     not implemented" — v2 lands in W3-05), `--viewport WxH` (adds a
     `cellPt = 0.94·min(W/cols, H/rows)` column, matching
     `BoardView.tsx:59,241`), `--json`.
   - Always prints the brief's honesty-bound header verbatim above the
     table/JSON.
2. `src/core/levelGenerator.ts` — added the `targetCells` seam the brief
   calls for (F25 controller amendment: the brief's Change section needs it
   but its Files list omitted this path). `GeneratedLevel` now also carries
   `targetCells: number`, the `cfg.minCells..maxCells` value `generate`
   already draws before sizing the board. This is the existing local
   variable exposed on the return object — no new RNG draw, no change to
   the RNG consumption sequence, no change to any other field. Used by
   `--clamp-shortfall` to compare the drawn target against the mask's
   actual cell count.
3. `package.json` — added `"analysis:probe": "tsx scripts/analysis/difficulty-probe.ts"`.
4. `docs/level-curve-baseline-2026-09-17.md` (new) — the committed v1
   baseline: every mode run over the ranges named in the brief's Context,
   with the git SHA it was run at, plus a "Decisions" section for judgment
   calls the brief left open.

## Decisions

Recorded in full, with the evidence for each, in
`docs/level-curve-baseline-2026-09-17.md`'s "Decisions" section:

1. **Median convention** for even-sized samples: "higher median"
   (`sorted[floor(n/2)]`, 0-based) — the only convention I tried that
   reproduces every tier/band scan-median number in the brief exactly.
   Nearest-rank (this repo's existing convention in `tier-bands.ts`) and
   the two-point average both undershoot the Hard-tier number by 5-11.
   This is the one place I had to reverse-engineer the brief's intended
   formula rather than read it off directly; I'm flagging it because a
   future reader extending `--per-tier`/`--bands` should keep using the
   same `median()` helper rather than reintroducing nearest-rank.
2. **`--bands` boundaries** generalize the brief's fixed 1-240 breakpoints
   as fixed cumulative fractions (1/8, 1/4, 1/2, 3/4, 1) of whatever
   `--levels` range is given, since the brief only specifies boundaries for
   one specific range.
3. **`--version` defaults to 1** when omitted (not made an error); no
   acceptance command exercises omission.
4. **`worst n/k`, `minClearable`, and `--tier-report`'s pairwise overlap**
   are defined here (not given target values in the brief) — see the
   baseline doc for the exact definitions used.

None of these seemed to admit two materially different readings that would
change what later W3 tasks consume (arrow counts, clearable%, scan/blocked
sums, capacity cells, clamp-shortfall listing) — those are all
brief-specified and exactly reproduced. The median convention is the one
judgment call with a real fork; I resolved it empirically against the
brief's own numbers rather than guessing, per the brief's Verification
section 3.

## Self-review findings

- Removed an unused `BoardLogic` import from the probe (caught before
  first commit).
- Confirmed the golden-checksum tests in `levelGenerator.test.ts` still
  pass after adding `targetCells`, since F25's amendment explicitly warns
  "the reviewer re-runs the golden checksums" — I ran them myself first
  rather than leaving that solely to review.
- Considered re-deriving `targetCells` in the probe via a parallel
  `DotNetRandom` replay (duplicating `generate`'s RNG sequence) instead of
  adding a field to `GeneratedLevel`. Rejected: a parallel replay risks
  silent drift from the real generator if `generate`'s RNG-consumption
  order ever changes, whereas exposing the already-computed local variable
  on the return object is guaranteed to match by construction and is a
  smaller, more obviously-safe diff.
- Checked for full-object equality assertions on `GeneratedLevel` elsewhere
  in the codebase (`toEqual`/`toMatchObject` on a whole generated level)
  that an added field could break: none found (`grep` across
  `src/core/__tests__`, `src/ui/__tests__`).
