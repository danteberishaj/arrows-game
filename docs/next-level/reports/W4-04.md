# W4-04 — Dev-only time-to-clear instrument (`[measure-clear]` console sink)

Implementer report, 2026-09-25. Resumes the partial work from 2026-09-21 that the controller put back
in the working tree. The brief's binding amendments apply: ruling F09 makes this a `__DEV__` console
sink over W6-06's `level_end` with no counters of its own, and ruling F10 forbids reading `__DEV__` in
`src/perfMode.ts`. Raw evidence is in `artifacts/W4-04/` (gitignored): `bundle-grep.txt`,
`bundlegrep.sh` and `web-reconciliation-console.txt`.

## Outcome

In a dev build started with `EXPO_PUBLIC_MEASURE_CLEAR=1`, a cleared campaign or daily board logs
exactly one line:

`[measure-clear] mode=<campaign|daily> id=<levelIndex|day> shape=<name> arrows=<n> taps=<n> ms=<n> heartsLost=<n>`

The line is built from W6-06's `level_end`, joined to its `level_start` to get `shape` and `arrows`.
Nothing is persisted, nothing appears on screen, and nothing goes over the network. An Android
release export built without the env var contains zero bytes of the string. Two web runs reconcile
exactly (see below).

## Decisions

1. **`taps` is W6's `level_end.taps` (exit + blocked + ghost + miss).** I did not narrow it to the
   brief's original "removals + blocked". F09 says to print `level_end` with no separate counters.
   On a clear `tapsExit === arrows`, so `taps − arrows` counts every non-removal tap, and a miss on
   empty board space is also a mistaken tap. Both runs had ghost = miss = 0, so this choice did not
   affect the reconciliation. The sink's doc comment now states this.
2. **`ms` is W6's `durationMs`, measured from `level_start` (board load), not from the first tap as
   the pre-amendment brief said.** F09 rules out a second timer. For a visual-search game, the look
   before the first tap is arguably part of the time to clear. Also documented in the sink.
3. **The `MEASURE_CLEAR` flag itself does not include `__DEV__`.** F10 allows "dev-only flags live
   in the dev sink", and App's `__DEV__` branch is the only caller. The controller's positive
   control (a release export with the env var must contain the string) depends on this shape. If
   the flag also required `__DEV__`, the release positive control would read 0 and prove nothing.
4. **I did not interact with the simulated ad.** I reloaded the page instead of pressing its Close
   button.

## Concerns

- **Daily mode is not exercised end to end.** It has unit tests only (`mode=daily id=2450`).
  Nothing launches a daily board yet, because W4-06 is not done. For `id=<day>` to be the day
  number that W4-05 checks against `generateDaily(day).arrowCount`, W4-06 must pass the day as the
  `levelIndex` argument of `LevelAggregator.start()`. This is INFERRED; W4-06's review should check
  it.
- **For W4-05, `ms` includes the lose panel and ad after an earned continue.** W4-05's protocol
  ("cold, without hints") should also say "no continues", or drop rows where `heartsLost` equals
  `heartsMax`.
- **Silent-loss risks, INFERRED from reading App.tsx.** If `TELEMETRY_TRANSPORT` is ever turned on
  in a dev build, `Telemetry.useSink(httpSink.send)` replaces the dev console sink, and the
  `[measure-clear]` lines stop appearing with no error. The same happens if the remote telemetry
  kill bit is set (`Telemetry.configure({ disabled: ... })`). Today the flag is hard-coded `false`
  and the kill bit read `bits=0` in this run.
- **Only the web runs were executed.** Native dev builds use the same JS path. No
  UNVERIFIED-DEVICE claim is made, and the brief asks for none.
- **The web runs changed the preview browser's own storage.** Level progress in its localStorage
  advanced to Level 3 (dev preview only; no device or emulator was used).
