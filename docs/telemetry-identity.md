# Telemetry identity (W6-05)

## What the id is

The install id is two 31-bit halves — `arrows_tel_install_hi` and
`arrows_tel_install_lo`, P-01's rows 24-25 — generated by `Math.random()`
inside the app the first time `src/telemetry/identity.ts`'s `ensureIdentity()`
runs (see `App.tsx`, once per install, right after `initSaveSystem()`
resolves, and never under `PERF_MODE`). Together they give 62 bits, plenty to
tell installs apart without a UUID library.

It is **random and app-generated, not derived from any device identifier.**
It is not the Android advertising id, not `expo-application`'s install/instance
id, not a hardware or account identifier, and nothing in `src/telemetry/`
reads any of those (`grep -rn "getAdvertisingId\|expo-application\|DeviceInfo"
src/telemetry` returns 0 hits). Two installs that happen to roll the same
62-bit pair are indistinguishable by design — that is a privacy property, not
a bug.

`arrows_tel_session_count` (row 26) is a plain cold-start counter,
incremented once per launch by `nextSessionIndex()`, in the same call site.

## What the draft proposed instead, and why it was rejected

The pre-flight draft proposed a separate `arrows_tel_` AsyncStorage namespace
holding a UUID string and a JSON event queue, plus a rule excluding
`arrows_tel_*` keys from Android Auto Backup. Both are rejected:

- A string UUID needs a UUID dependency or a hand-rolled generator; an int
  pair does not, and every other persisted value in this app is already an
  int (`src/core/saveSystem.ts`'s `IntStore` contract).
- A second AsyncStorage namespace is a second persistence system, with its
  own hydrate path, its own test coverage, and a second place a key can be
  written without being read back (the exact failure P-01's key registry
  exists to prevent).
- Per-key exclusion from Auto Backup is not something Android can do here —
  see below.

## Why excluding these keys from Auto Backup is impossible

Auto Backup rules (`android:fullBackupContent` in the manifest) select
**files**, not individual key-value pairs inside a file. Every
`@react-native-async-storage/async-storage` key — every one of P-01's 29
keys, including the three telemetry-identity ones — lives in the same single
SQLite file, the `RKStorage` database:

```
node_modules/@react-native-async-storage/async-storage/android/src/main/java/
  com/reactnativecommunity/asyncstorage/ReactDatabaseSupplier.java:25
  public static final String DATABASE_NAME = "RKStorage";
```

A backup rule can only ever say "back up `RKStorage` or don't" — it cannot
open the database and drop three rows out of it.

Editing the manifest to add such a rule wouldn't survive anyway: `android/`
is a generated folder, wiped and regenerated by `expo prebuild` on every
build. It is gitignored:

```
.gitignore:41
/android
```

so a hand-edited `AndroidManifest.xml` or `@xml/backup_rules` file placed
there is discarded the next time anyone runs `expo prebuild`, with no CI
check to catch the loss.

The only other lever is turning Auto Backup off entirely
(`android:allowBackup="false"`). That would also delete the backup of
players' actual progress — level, streak, shape collection, everything
P-01's other 26 keys hold — which they get today "for free" through
`allowBackup="true"` on the generated manifest. Trading real progress backup
for telemetry-id backup exclusion is the wrong trade.

## The accepted trade-off

Auto Backup restores the whole `RKStorage` database onto a new device (a
phone upgrade, a reinstall after uninstalling), including the install id and
session count. **A restored install therefore counts as the same install** —
the id does not reset just because the physical device changed. This slightly
undercounts distinct devices in any install-based metric (a phone upgrade
looks like zero installs instead of one), and it is accepted: it is a much
smaller distortion than losing real player progress would be, and it matches
how the app already treats every other Auto-Backed-up key.

This document, and the trade-off above in particular, is the input W6-13
uses when it writes the player-facing disclosure text.

## When this leaves the device

Nothing here sends the id, the session count, or any event anywhere.
`src/telemetry/telemetry.ts`'s only sink today is `noopSink`. W6-14 is the
first module that reads the id off `SaveSystem` and attaches it to an
outgoing event, and even then that transport ships with its endpoint flag
OFF and no endpoint configured. The id does not actually leave the device
until W6-15 turns telemetry on for real (endpoint live, consent gated,
disclosure reviewed).
